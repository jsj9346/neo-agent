## 1. 경계 — 패키지와 의존성

- 패키지 위치: `packages/gate`. 의존성 예산: **`@neo-agent/core` 정확히 1개** (훅 계약 타입 소비).
- **금지 모듈**: `node:fs`·`node:child_process`·`node:net`·`node:tls`·`node:http`·`node:https`·`node:sqlite`·`node:dgram`·`node:worker_threads`
  게이트는 순수 판정 로직이다. 파일시스템(allowlist 영속화)·사용자 대화(프롬프트)·경로 실체 판정(classifier)은 전부 주입받는다. 이 금지는 예산 게이트로 검사한다 — 판정 모듈이 스스로 프로세스를 스폰하거나 네트워크에 나가는 경로를 기계적으로 차단하는 것이 분리의 목적이다. **2026-08-24 개정 둘.** ① 문장 머리에 볼드로 붙어 있던 선언을 불릿 앵커 형태로 맞췄다 — 열 문서가 제각기 다른 머리로 금지를 선언하던 상태를 한 문자열로 닫아 문서↔게이트 대조를 기계가 재게 한 개정이고, 표기를 `node:` 접두로 통일하는 근거는 `PROVIDERS.md` §2.1의 2026-08-14 선례가 든다. ② `node:dgram`·`node:worker_threads`를 열거에 더했다. 게이트는 그전부터 둘을 막고 있었고 문서만 그 사실을 안 들고 있었다. 근거는 앞의 네트워크 금지와 같다 — UDP 소켓도, 워커 스레드가 자기 컨텍스트에서 여는 소켓도 «판정 모듈은 스스로 밖으로 나가지 않는다»를 돌아가는 경로이므로, 함께 막지 않으면 차단이 반쪽이 된다. 워커는 특히 이 패키지에서 값이 없다: 게이트에 남는 계산은 유계 정규식 판정뿐이고(§2 위험 패턴), 그것을 다른 스레드로 옮길 이유가 없다.
- `packages/tools`와 무의존(양방향). 공유 계약(`PathClassifier`, 게이트 프로필 테이블)은 구조적 타입 호환으로 만나고, 결합은 호스트(CLI)의 배선 한 곳이다(§4). **측정 단위는 `src/**`의 임포트와 매니페스트 `dependencies`** — 통합 계약 확인용 테스트 전용 devDependency(오늘: `tools` 쪽의 `@neo-agent/gate`)는 위반이 아니다 (2026-08-11 명문화, `TOOLS-INTERFACE.md` §1과 같은 규칙 · 근거: `plans/20260811-axis4-premise-verify-report.md` F-1/J-1).
- 코어와의 접점은 `beforeToolCall` 훅 하나다(CORE-INTERFACE §7). 코어는 게이트를 모르고, 게이트는 이벤트 스트림·루프를 모른다.

## 2. 판정 파이프라인 — 4계층 + 매트릭스

한 도구 호출에 대한 판정은 아래 순서로 흐른다. **순서가 계약이다** — 순서를 바꾸면 우회가 생긴다(예: allowlist를 위험 패턴보다 먼저 보면 위험 명령이 학습된 키로 통과한다).

```
0. denied 차단      — classifier가 "denied"(크리덴셜 경로)면 즉시 block.
                      모드 무관, 승인으로도 불가. 도구 자체 강제(TOOLS-INTERFACE §3)의 이중화
1. 하드라인 블록리스트 — 모드 무관, 항상 평가. 걸리면 즉시 block
2. 사용자 deny 규칙   — 모드 무관. 난독화 정규화 후 글로브 매칭. 걸리면 block
3. 모드 확인         — "off"면 여기서 allow (denied·하드라인·deny 규칙 뒤라는 위치가 계약)
4. 위험 패턴 플래그   — 유계 필러 정규식. 차단이 아니라 플래그:
                      자동 허용과 allowlist 숏컷을 무효화하고 프롬프트에 경고를 싣는다
4b. 오염 플래그       — 이 런에서 이미 source: "network" 결과가 나왔으면 같은 효과.
                      (2026-08-08 추가 — WEB-ACCESS.md §5)
5. 정책 매트릭스     — 자동 허용 판정 (SAFE-DEFAULTS §1: 워크스페이스 안 파일 읽기,
                      그리고 memoryWrite — 2026-08-09 추가).
                      **위험 플래그가 없을 때만** 해당하면 allow
6. 영구 allowlist    — 위험 플래그가 없을 때만 매칭. 걸리면 allow
7. 승인 프롬프트     — 주입된 ApprovalPrompt에 위임.
                      allow-once → allow / allow-always → allowlist 학습 + allow / deny → block
```

**2026-08-06 순서 개정 2건** (구현 중 발견, 사용자 확인 후 반영):

- **deny 규칙을 모드 확인보다 앞으로.** 초판은 `off`가 deny 규칙까지 껐다. deny 규칙은 승인 모드와 **독립된 사용자 의사표시**이고, `off`의 의미는 "매번 묻지 마라"이지 "내가 금지한 것을 풀어라"가 아니다. 설정 하나를 끄면 다른 설정이 함께 꺼지는 은닉된 결합은 가시성 원칙(ARCHITECTURE §2.6) 위반이기도 하다. 이제 `off`를 넘어서는 것은 denied·하드라인·deny 규칙 셋이다.
- **위험 패턴을 정책 매트릭스보다 앞으로.** 초판은 자동 허용이 위험 패턴보다 앞이라, 워크스페이스 안의 `id_rsa`·`credentials.json` 같은 파일이 **경고 없이 조용히 읽혔다**(클론한 저장소에 키가 커밋돼 있는 경우가 실재한다). 자동 허용의 근거는 "읽기는 마찰 대비 이득이 없다"인데, 위험 플래그가 붙은 읽기는 그 전제가 성립하지 않는다. 마찰은 플래그된 파일에만 생긴다.

**계층별 규정:**

- **하드라인(1)** — 의도적으로 최소(루트 FS 파괴·블록 디바이스 덮어쓰기·셧다운급만, SAFE-DEFAULTS §1). 구체 목록은 구현 시 확정하되 **"최소" 원칙이 계약이다** — 넓히면 "어차피 다 막네"가 되어 `off` 옵트인의 의미가 사라진다.

  **하드라인은 판정 대상의 종류로 건너뛰지 않는다** (2026-08-06 명문화). 셸 명령뿐 아니라 **파일 쓰기·편집의 경로**도 평가한다 — 금지되는 것은 특정 도구가 아니라 **결과**이기 때문이다. `dd of=/dev/sda`를 막으면서 `write_file({path: "/dev/sda"})`를 열어두면 같은 파괴에 다른 문으로 도달하고, "승인으로도 불가"라는 하드라인의 정의가 실효를 잃는다(QA 검증에서 발견). 읽기는 대상이 아니다 — 계약이 금지하는 것은 덮어쓰기다.
- **deny 규칙(2)** — 문법은 글로브. 매칭 전에 난독화 정규화를 적용한다: **비가시 유니코드 검사 → NFKC 정규화의 순서 고정**(hermes `threat_patterns.py` 기법 — 순서를 바꾸면 전각 동형이의어 우회가 뚫린다), 인용부호 삽입 변형(`git st""atus`)·백슬래시 변형(`r\m`) 정규화. **글로브 매칭에 정규식을 쓰지 않는다** — 와일드카드가 리터럴로 갈린 규칙(`**a**b**c**`)이 세제곱 백트래킹을 만들고, 판정 대상 텍스트는 모델이 제어하므로 그것이 곧 게이트 정지 경로다. 최악 시간이 보장되는 매칭(와일드카드 DP 등)을 쓴다.
- **위험 패턴(4)** — 정규식은 **유계 필러**(`(?:\w+\s+){0,8}` 형태)만 쓴다 — ReDoS 방지. 구체 패턴 목록은 구현 시 확정(크리덴셜 경로 접촉 명령이 여기 포함된다 — TOOLS-INTERFACE §3의 셸 한계 보완). 플래그는 **자동 허용(5)과 allowlist(6) 양쪽을 무효화**한다.
- **오염 플래그(4b)** (2026-08-08 추가) — 런 중 `ToolResult.source === "network"`인 결과가 하나라도 나오면, **그 런의 남은 모든 도구 호출**이 위험 플래그와 **똑같은 취급**을 받는다: 자동 허용(5)과 allowlist(6)가 무효화되고 경고가 프롬프트에 실린다. 차단은 아니다.

  **경고는 "이 런이 외부 페이지를 가져왔다"는 취지가 사용자에게 읽혀야 한다** (2026-08-09 명문화). 문구는 구현 재량이되 위험 패턴 경고와 구분 가능해야 하며, **게이트는 그 경고를 식별할 안정된 값을 export한다** (2026-08-09 추가 — QA-C C-9). 문구가 재량인데 검사가 문구에 걸리면 **재량이 아니게 된다** — 문구를 고칠 때마다 테스트가 깨지고, 그러면 "구분 가능해야 한다"는 요구가 실제로는 "이 문장을 유지해야 한다"로 굳는다. 식별자를 export하면 문구는 자유롭게 고치면서 구분 가능성만 계약으로 검사된다. 위험 패턴 경고가 이미 `위험 패턴(<id>) — …` 꼴로 id를 싣는 것과 같은 방향이다 — 사용자가 *"왜 학습해 둔 명령을 또 묻지?"*를 알 수 없으면 마찰이 이유 없는 마찰이 되고, 이유 없는 마찰은 승인 피로를 거쳐 무조건 allow로 간다. 그것이 게이트가 실제로 무력화되는 경로다(ARCHITECTURE §2.6 가시성의 적용). [QA-C 판정 C-5]

  **`GateLayer`에 오염 식별자를 두지 않는다** (2026-08-09). 4b는 **플래그이지 출구가 아니어서** 오염된 호출은 계층 5·6을 건너뛰고 7(프롬프트)에서 나간다 — verdict에 나타날 수 없는 값을 유니온에 넣으면 테스트가 검증할 수 없는 값이 생긴다. 위험 패턴(계층 4)에 대응 식별자가 없는 것이 이미 같은 전례다. 순서 검증은 **이중 실행**으로 한다: 같은 입력을 무오염 `evaluate`로 돌려 `layer`를 확인하고, 오염 상태에서 훅으로 돌려 `{decision, reason}`이 같고 프롬프트에 닿지 않았음을 확인한다(QA-C 실증). `evaluate`에 오염 인자를 더해 계층을 직접 관측하게 하는 안은 기각한다 — 테스트 편의를 위해 판정 함수의 표면을 넓히는 일이고, 이중 실행으로 이미 성립한다. [QA-C 판정 C-6]

  **새 계층이 아니라 기존 기계의 재사용이라는 점이 채택 근거다** — 정책 효과가 위험 패턴과 동일하므로 파이프라인에 분기가 늘지 않고, 프롬프트·경고 표시 경로도 그대로다(Footprint Ladder 1단). 대상이 `web_fetch`가 아니라 **모든 도구**인 이유는 방어 시나리오가 "가져온 페이지가 다음 행동을 지시한다"이고 그 행동은 대개 셸·파일 쓰기이기 때문이다. 수명·한계·오염원의 정본은 `WEB-ACCESS.md` §5.
- **정책 매트릭스(5)** — 자동 허용 대상은 둘이다: **워크스페이스 안 파일 읽기**(`fileRead` + `scope: "inside"`)와 **`memoryWrite`**(2026-08-09 추가 — `MEMORY.md` §5).

  **`memoryWrite`가 자동 허용인 근거는 가시성이 이미 성립하고 마찰이 요구되지 않았다는 것이다.** 승인 매트릭스(SAFE-DEFAULTS §1)가 승인을 요구하는 것은 **되돌리기 어렵거나 범위를 알 수 없는 행동**인데, 메모리 쓰기는 둘 다 아니다 — 몇 KB 상한의 append이고(`MEMORY.md` §6), 사용자가 에디터·`/memory`로 언제든 지울 수 있으며, CLI가 도구 호출과 결과를 그대로 렌더링하므로 사용자가 저장된 내용을 본다. `write_file`이 승인 대상인 이유(비가역 덮어쓰기)가 여기엔 없다. `ARCHITECTURE.md` §2.6이 요구하는 것은 가시성이지 마찰이 아니다.

  **등록하지 않는 것은 중립이 아니다.** 미등록 도구는 `unknown`으로 fail-closed이므로(§3), `memoryWrite`를 등록하지 않으면 **메모리 저장마다 승인 프롬프트가 뜬다** — 즉 "물린 선택지"가 아무것도 안 함으로써 기본값으로 실현된다. 분류를 등록하되 판정을 자동 허용으로 두는 것이 그 판단과 정합한다.

  **자동 허용에 예외를 만들지 않는다** — 위험 플래그(4)·오염 플래그(4b)가 있으면 `memoryWrite`도 다른 자동 허용과 똑같이 무효화되어 프롬프트로 간다. 오염 런에서는 도구 자신이 별도로 거부하므로(`MEMORY.md` §5) 사용자가 허용해도 저장되지 않는다. **이 이중 마찰은 수용하되, 프롬프트가 그 사실을 말한다**(아래).

  **오염 런의 `memoryWrite` 프롬프트는 "허용해도 저장되지 않는다"를 경고로 싣는다** (2026-08-09 추가 — QA-B 판정 B-5). 이것 없이는 계약이 **자기 원칙을 한쪽에서만 지킨다**: 계층 4b가 오염 시 `allowAlwaysKey`를 지우는 근거가 정확히 *"키를 만들어 프롬프트에 실은 뒤 응답만 무시하면 사용자에게는 선택지가 보이는데 눌러도 아무 일이 없다 — 가시성 원칙 위반"*인데, 오염 런의 `memoryWrite`는 **같은 양태**다(허용 버튼이 보이고, 눌러도 저장되지 않는다).

  차이는 하나뿐이고 그것만으로는 부족하다 — 4b 쪽은 **같은 컴포넌트가** 선택지를 만들고 무시하지만, 여기서는 게이트가 허용을 **정직하게 이행**하고 그 뒤 **다른 컴포넌트**(도구)가 **사유를 밝히며** 거부한다. 사후에는 설명이 있다. 그러나 **사용자가 버튼을 누르는 시점에는 아직 모른다**, 그리고 가시성 원칙이 보호하려는 것은 바로 그 시점의 판단이다. 그래서 사전 고지를 계약으로 둔다.

  **면제(4b를 `memoryWrite`에 한해 끄는 것)는 여전히 기각이다** — "4b는 플래그이지 출구가 아니다"(판정 C-6)를 뒤집을 뿐 아니라, 오염 방어가 **도구 한 곳**에만 남아 나중에 그 검사가 사라지면 조용히 무방비가 된다. 마찰을 없애는 대신 **마찰의 이유를 보이게** 한다 — 이유 없는 마찰이 승인 피로를 부르는 것이지 마찰 자체가 문제가 아니다(계층 4b의 같은 논리).
- **allowlist(6)** — `allow-always` 응답으로만 자란다. **셸 연산자(`&&`·`;`·`|`·리다이렉션 등)를 포함한 복합 명령은 allowlist 매칭 대상이 아니다**(hermes `_has_allowlist_shell_operator` 대응) — `ls`를 학습시킨 뒤 `ls; rm -rf`가 통과하는 숏컷을 차단한다. 이런 요청은 `allowAlwaysKey` 없이 프롬프트로 가고, "항상 허용" 선택지 자체가 제공되지 않는다.
- **프롬프트(7)** — deny는 `{ decision: "block", reason }`으로 모델에게 보인다(침묵 거부 금지, CORE-INTERFACE §7). 프롬프트 대기 중 abort 시그널이 오면 프롬프트를 취소하고 block한다(중단 의미론은 코어가 처리).

## 3. 판정 입력 — 게이트가 보는 것

게이트는 도구 구현을 모른다. 도구 호출을 판정 가능한 형태로 옮기는 것은 **프로필 테이블**(설정 데이터)이고, 경로의 실체 판정은 **주입된 classifier**다.

```typescript
/** 게이트가 요구하는 경로 판정 인터페이스.
 *  packages/tools의 WorkspaceBoundary가 구조적으로 만족한다 — 임포트 없는 호환.
 *  도구 실행과 반드시 같은 판정기 인스턴스를 배선한다 (판정 불일치 방지) */
interface PathClassifier {
  resolve(input: string): { path: string; scope: "inside" | "outside" | "denied" };
}
// `"."`은 워크스페이스 루트로 해석된다 — 셸의 `cwd` 미지정 기본값을 게이트가
// 자체 상수로 갖지 않고 classifier에게 물어보기 위한 계약이다. 게이트가 루트 값을
// 따로 알기 시작하면 도구와 판정이 어긋날 수 있다(2026-08-06 명문화).

/** 도구 이름 → 판정 분류. **각 도구 패키지가 자기 도구의 정본 테이블을 export한다**
 *  (packages/tools → TOOL_GATE_PROFILES 4종, packages/web → WEB_TOOL_GATE_PROFILES 2종,
 *   packages/memory → MEMORY_TOOL_GATE_PROFILES 1종).
 *  병합은 호스트(CLI)의 배선 한 곳이다 — TOOLS-INTERFACE §5 */
type GateToolProfile =
  | { kind: "fileRead" | "fileWrite" | "fileEdit"; pathParam: string }
  | { kind: "shellExec"; commandParam: string; cwdParam?: string }
  | { kind: "webFetch"; urlParam: string }           // 2026-08-09 추가
  /** 경로 인자가 없는 도구다. `contentParam`은 **표시 전용**이며 판정 입력이 아니다 (아래 절) */
  | { kind: "memoryWrite"; contentParam: string }    // 2026-08-09 추가
  /** 경로 인자가 없는 도구다. `queryParam`도 **표시 전용**이다 — 같은 근거 (아래 절) */
  | { kind: "webSearch"; queryParam: string };       // 2026-09-02 추가

/** 파이프라인이 소비하는 판정 대상 */
type GateSubject =
  | { kind: "fileRead" | "fileWrite" | "fileEdit"; path: string; scope: "inside" | "outside" | "denied" }
  | { kind: "shellExec"; command: string; cwd: string }
  /** origin = 스킴+호스트+포트. allowlist 학습 단위이며 URL 전체가 아니다 (WEB-ACCESS §6) */
  | { kind: "webFetch"; url: string; origin: string }
  /** 판정 대상은 "이 도구가 불렸다"는 사실 하나다 — 인자를 읽지 않는다 (아래 절) */
  | { kind: "memoryWrite" }                          // 2026-08-09 추가
  /** 같은 형태다. 학습 키의 정의역이 원소 하나라 게이트가 질의에서 판정할 것이 없다 (아래 절) */
  | { kind: "webSearch" }                            // 2026-09-02 추가
  | { kind: "unknown"; toolName: string };
```

- **프로필에 없는 도구는 `unknown`이다 — fail-closed.** 매트릭스 자동 허용·allowlist 없이 항상 프롬프트로 간다. 새 도구를 추가하면서 프로필 등록을 잊어도 조용한 자동 허용이 되지 않는다.
- `shellExec`의 `scope` 판정은 없다 — 명령 문자열은 경로로 환원되지 않는다. 셸은 언제나 승인 대상이다(매트릭스).

### `webFetch` 분류 (2026-08-09 추가 — `WEB-ACCESS.md` §6의 요구)

`WEB-ACCESS.md` §6은 `web_fetch`의 allowlist 학습 단위를 **`스킴+호스트+포트`**로 규정했다. 그 학습이 성립하려면 게이트가 URL을 그 단위로 읽을 수 있어야 하고, 분류가 없으면 `unknown`으로 떨어져 **fail-closed지만 학습이 영영 불가능**해진다(`allowAlwaysKey`가 없으면 "항상 허용" 선택지 자체가 제공되지 않는다 — §4). 같은 호스트를 매번 승인하게 되면 §6이 "호스트 단위가 URL 전체와 도메인 접미사 사이의 유일한 지점"이라 판정한 결론이 실현되지 않는다.

- **게이트의 URL 파싱은 학습 키 산출을 위한 것이지 보안 판정이 아니다.** SSRF 판정의 유일한 소유자는 `packages/web`이다(`WEB-ACCESS.md` §4 — 판정기가 둘이면 어긋난다). 게이트는 전역 `URL`로 파싱해 `origin`을 뽑을 뿐이고, **파싱 실패는 `unknown`(fail-closed)으로 떨어진다.** 게이트의 파싱 결과는 차단/허용 판정에 쓰이지 않으므로 "판정기가 둘"이 되지 않는다.
- **정책 매트릭스(계층 5)는 무변경이다** — `webFetch`는 자동 허용 대상이 아니고, 학습은 계층 6(allowlist)에서만 일어난다. 최초 호스트는 항상 프롬프트다(`WEB-ACCESS.md` §6 표).
- `webFetch`의 `scope` 판정은 없다 — 경로 판정기의 관할이 아니다. `shellExec`과 같은 이유로 언제나 승인 대상이다.

### `memoryWrite` 분류 (2026-08-09 추가 — `MEMORY.md` §5의 요구)

`MEMORY.md`가 메모리 쓰기를 `remember` **1종·1액션**으로 닫으면서, 게이트에 이 도구의 분류가 필요해졌다. **등록하지 않으면 `unknown`으로 떨어져 메모리 저장마다 프롬프트가 뜬다** — 그것은 설계가 명시적으로 물린 결과이므로(§2 계층 5), 분류를 등록하고 판정을 자동 허용으로 둔다.

- **subject에 인자 필드가 없다 — 판정 대상은 "이 도구가 불렸다"는 사실 하나다.** `remember`의 인자는 `content` 하나이고 **경로 인자가 아예 없다**(`MEMORY.md` §4.1 — 대상 파일은 `deps.dir`로 고정이고 모델 입력에서 파생되지 않는다). 그래서 `pathParam`·`urlParam`에 대응하는 것이 없다. `shellExec`·`webFetch`에 `scope` 판정이 없는 것과 같은 자리 — 게이트가 읽을 수 있는 판정 축이 그 도구에 존재하지 않을 때 축을 발명하지 않는다.
- **프로필은 `contentParam`을 갖는다 — 표시 전용이고 판정 입력이 아니다** (2026-08-09 정정, QA-B 판정 B-1). 이 문서의 초판(같은 날)은 "프로필과 subject 양쪽에 인자 필드가 없다"(`0514335`)고 썼는데, 그것은 **두 가지 다른 것을 뭉뚱그린 과잉 조임이었다.** 판정 표면(subject)과 표시 표면은 파이프라인에서 이미 분리돼 있고(`SubjectResolution.subject` vs `.primary`), §3이 요구하는 "`display`는 저장될 내용을 보여야 한다"는 후자다. 프로필에 필드가 없으면 게이트는 `"content"`라는 **인자 이름을 스스로 알아야** 하고, 그것은 "게이트는 도구 구현을 모른다"(§3 머리)를 정면으로 깬다. `pathParam`·`commandParam`·`urlParam`이 전부 "어느 인자가 무엇인가"를 **설정으로** 넘기는 것과 같은 자리다.

  ```typescript
  | { kind: "memoryWrite"; contentParam: string }   // 프로필: 표시용 인자 이름
  | { kind: "memoryWrite" }                          // subject: 판정 입력 없음
  ```
- **판정·매칭의 1차 대상(`primary`)은 `content`가 아니라 도구 이름이다** (2026-08-09, 판정 B-1의 귀결). `primary`는 표시에만 쓰이는 값이 아니라 **계층 2(deny 규칙)와 계층 4(위험 패턴)의 매칭 대상**이다. 여기에 메모리 본문을 넣으면 두 가지가 깨진다:
  1. **deny 규칙이 산문에 걸린다.** 사용자가 명령·경로를 겨냥해 쓴 `*.env*` 같은 규칙이 *"`.env` 파일을 선호한다"* 는 메모에 걸려 **계층 2에서 우회 불가로 차단**된다. 계층 2는 모드보다 앞이라 `off`로도 안 풀린다.
  2. **위험 패턴이 산문에 걸린다.** 구현은 셸이 아닌 모든 분류에 `"path"` 목록을 적용하므로(`pipeline.ts` 계층 4), `~/.ssh/id_rsa`를 **언급만 한** 메모가 플래그된다. 크리덴셜 경로 패턴은 *접촉하는 명령*을 잡으라고 만든 것이지 그것을 *말하는 문장*을 잡으라고 만든 것이 아니다.

  그래서 `primary`는 `unknown`과 같이 **도구 이름**으로 두고, `content`는 **표시 본문으로만** 흘린다. 부수 귀결(의도한 것): 사용자는 deny 규칙 `remember`로 메모리 도구 자체를 막을 수 있다 — `unknown` 도구가 이미 그렇게 동작하고, 도구 단위 금지는 사용자의 정당한 의사표시다.
- **표시 위조 탐지는 `content`에 적용되고, 위조 흔적은 다른 분류와 똑같이 자동 허용을 무효화한다** (판정 B-3). `content`는 모델이 제어하는 문자열이고, **메모리는 이후 모든 세션의 시스템 프롬프트에 실린다** — 비가시 문자·동형이의 문자가 들어간 문자열을 마찰 없이 영속시키는 것은 게이트가 막으려는 바로 그 경로의 가장 오래 가는 형태다. 위조 탐지는 **탐지 기반 차단이 아니라 표시 정직성**이므로 `MEMORY.md` §8이 기각한 "내용 위협 스캔"과 다르다 — 무엇도 차단하지 않고 사용자에게 보이는 것을 실제와 같게 만들 뿐이다.
- **표시 상한 초과로 인한 잘림도 자동 허용을 무효화한다 — 특례를 만들지 않는다** (2026-08-09, 판정 B-6). 잘림은 "사용자가 본 것과 저장될 것이 다르다"의 한 형태이고, 위조 탐지가 보호하려는 것이 바로 그것이다. 기존 경고(*"표시가 길어 잘렸다 — 전체 내용을 확인하지 않은 채 허용하지 않는다"*)가 이미 마찰의 이유를 말한다.

  **여기에는 B-5 같은 사전 고지를 달지 않는다. 그 차이가 판정의 핵심이다** — 오염은 게이트가 **확실히 아는 사실**이다(오염 런에서 도구는 저장하지 않는다, `MEMORY.md` §5). 반면 "이 길이를 도구가 받아줄 것인가"는 **게이트가 모르는 것**이다: 항목 상한은 `packages/memory`의 값이고, 게이트가 그것을 알면 상한이 바뀔 때마다 게이트가 따라 바뀌어야 하는 숨은 결합이 생긴다. **아는 것은 말하고 모르는 것은 말하지 않는다** — 승인 화면이 아는 것보다 더 말하면 그 자체가 거짓말이라는 §4의 규율이 여기서는 침묵을 요구한다.
- **`content`를 문자열로 읽지 못하면 `unknown`으로 떨어뜨리지 않는다** (판정 B-2). 분류는 `memoryWrite`로 유지하고, **읽지 못했다는 사정을 `warnings`에 싣고 플래그 처리**해 자동 허용을 무효화한다. `unknown`으로 보내지 않는 이유는 불투명 origin에서와 **같다**(§4): 그쪽 `display`가 *"게이트 프로필에 등록되지 않았다"*는 **거짓 사유**를 보인다. 승인 화면이 거짓말하면 게이트 전체가 무의미하다. fail-closed는 지켜지되 그 통화가 **오분류가 아니라 마찰**이다 — 무엇이 저장되는지 보여줄 수 없으면 조용히 허용하지 않는다.
- **`scope` 판정도 없다.** 대상은 언제나 `~/.neo-agent/memory/`이고 그곳은 classifier가 `denied`로 판정하는 영역이다(`TOOLS-INTERFACE.md` §3). 만약 `memoryWrite`를 경로로 환원해 classifier에 물으면 **계층 0(denied 차단)에 걸려 항상 block된다** — 파일 도구를 막기 위한 판정을, 그 막힘을 전제로 설계된 전용 도구에 적용하는 것은 판정의 오용이다. 인자를 읽지 않는 것이 이 오용을 구조적으로 막는다.
- **`allowAlwaysKey`를 주지 않는다.** 자동 허용 대상이라 학습할 것이 없고, 키를 주면 오염·위험 플래그로 프롬프트에 도달했을 때의 "항상 허용"이 **그 예외 상황을 영구 학습**해 버린다. 불투명 origin에 키를 주지 않는 것과 같은 기계다(§4).
- **`display`는 저장될 내용을 보여야 한다.** 자동 허용이라 평소엔 화면에 프롬프트가 뜨지 않지만, 플래그로 프롬프트에 도달했을 때 사용자가 **무엇이 저장되려는지** 못 보면 그 승인은 §2 계층 4b가 만들려던 판단 기회가 아니다. 표시 위조 탐지(§4)는 다른 분류와 동일하게 적용된다 — `content`는 모델이 제어하는 문자열이다.

### `webSearch` 분류 (2026-09-02 추가 — `WEB-ACCESS.md` §6의 요구)

`WEB-ACCESS.md` §6이 `web_search`를 **매번 승인**으로 정하면서 게이트에 이 도구의 분류가 필요해졌다. 판정의 근거는 그 문서가 들고(*"학습이 방어를 하나도 안 준다 — 검색 엔드포인트는 상수 하나라 호스트 단위 학습 키의 정의역이 원소 하나이고, 첫 승인이 그것을 즉시 소진한다"*), 여기가 정하는 것은 **그 판정을 게이트가 어떤 모양으로 이행하는가**다. 프로필이 어느 테이블에 사는지는 같은 문서 §6의 「프로필이 사는 자리」가 든다.

- **subject에 인자 필드가 없다 — 판정 대상은 "이 도구가 불렸다"는 사실 하나다.** `webFetch`의 subject가 `url`·`origin`을 드는 것은 **`origin`이 학습 키의 정의역**이기 때문인데, `WEB-ACCESS.md` §6이 그 정의역을 원소 하나로 확인하고 **키 자체를 없앴다.** 게이트가 질의에서 판정할 것이 남지 않는다. `shellExec`·`webFetch`에 `scope` 판정이 없는 것과 같은 자리 — **게이트가 읽을 수 있는 판정 축이 그 도구에 존재하지 않을 때 축을 발명하지 않는다.**

- **`allowAlwaysKey`를 주지 않는다.** 위 문장의 직접 귀결이다. 키가 없으면 "항상 허용" 선택지가 **애초에 서지 않고**, 그것이 `WEB-ACCESS.md` §6이 *"새 정책 계층이 아니라 기존 기계의 재사용"*이라 부른 이행이다. `memoryWrite`가 키를 안 받는 것과 기계는 같고 근거가 다르다 — 저쪽은 *학습할 것이 없어서*(자동 허용 대상), 이쪽은 *학습해도 방어가 안 늘어서*다.

- **정책 매트릭스(계층 5)는 무변경이다.** `webSearch`는 자동 허용 대상이 아니다. 매트릭스가 자동 허용 **대상의 열거**이므로 **안 넣는 것이 곧 승인**이고, 코드에서는 그것이 **분기를 안 쓰는 것**으로 이행된다. `scope` 판정도 없다.

- **`primary`는 도구 이름이고, 질의는 표시 본문(`displayBody`)으로만 흐른다** — `memoryWrite` 판정 B‑1의 근거가 그대로 온다. `primary`는 표시용 값이 아니라 **계층 2(deny 규칙)·계층 4(위험 패턴)의 매칭 대상**이고, 검색 질의는 산문이다. 여기에 질의를 넣으면 사용자가 명령·경로를 겨냥해 쓴 `*.env*`가 *".env 관리법"* 검색을 **계층 2에서 우회 불가로 차단**하고(모드 `off`로도 안 풀린다), `~/.ssh/id_rsa`를 **언급만 한** 질의가 플래그된다. 위험 패턴은 그 경로에 *접촉하는 명령*을 잡으라고 만든 것이지 그것을 *말하는 문장*을 잡으라고 만든 것이 아니다.

  **여기서는 그 근거가 한 걸음 더 강하다.** 플래그가 사는 이유는 자동 허용과 학습 키를 지우는 것인데, 이 분류에는 **지울 것이 둘 다 없다**(매번 승인 · 키 없음). 즉 질의를 `primary`에 넣어 얻는 것은 **이미 무조건 주어져 있고**, 치르는 것은 오탐뿐이다.

  부수 귀결(의도한 것): 사용자는 deny 규칙 `web_search`로 검색 도구 자체를 막을 수 있다 — `memoryWrite`·`unknown`이 이미 그렇게 동작하고, 도구 단위 금지는 사용자의 정당한 의사표시다.

  이로써 `webSearch`는 **표시 본문이 판정 대상과 갈리는 두 번째 분류**가 된다. `SubjectResolution.displayBody`는 이미 있고 분기 조건도 *"`displayBody`가 있는가"*라 **분기가 늘지 않는다.**

- **표시 위조 탐지는 질의에 돈다 — 다만 귀결이 `memoryWrite`와 다르다.** 질의는 모델이 제어하는 문자열이고 **승인이 유일한 방어**인데, 비가시·동형이의 문자가 섞이면 사용자가 승인한 문자열과 실제로 나가는 문자열이 갈린다 — `WEB-ACCESS.md` §6의 *"승인 화면은 질의 문자열 전체를 보인다"*가 그 순간 거짓이 된다.

  저쪽에서는 위조 흔적이 **자동 허용을 무효화**하지만 여기엔 무효화할 것이 없으므로, 남는 효과는 **경고가 프롬프트에 함께 실리는 것**뿐이고 그것이 이 분류에서 위조 탐지가 하는 전부다. **값이 없는 것이 아니다** — §4의 규율은 **표시 정직성**이지 차단이 아니다. 무엇도 막지 않고 사용자가 보는 것을 실제와 같게 만들 뿐이라는 성격이 여기서 가장 순수하게 드러난다.

  **표시 잘림 경고는 구조적으로 뜨지 않는다** — `WEB-ACCESS.md` §3.2가 `query` 상한을 400자로 두고 게이트의 표시 상한은 4096자다. 그 관계가 **결합이 아니라 관찰**이라는 것(400을 4096의 함수로 정의하지 않는다)은 그 절이 판정 B‑5를 근거로 이미 든다. 게이트 상한이 400 아래로 내려가는 날 뜨는 것은 조용한 실패가 아니라 **기존 잘림 경고**다.

- **`query`를 문자열로 읽지 못하면 `unknown`으로 떨어뜨리지 않는다** — 판정 B‑2와 같은 근거다. `unknown`의 `display`는 *"게이트 프로필에 등록되지 않았다"*는 **거짓 사유**를 보이고, 승인 화면이 거짓말하면 게이트 전체가 무의미하다. 분류는 `webSearch`로 유지하고, **표시 본문을 비우고**(비우지 않으면 `primary`=도구 이름이 표시 본문으로 흘러 승인 화면이 *"질의: web_search"*라고 스스로 위조한다), 읽지 못했다는 사정을 `warnings`에 싣는다.

  **`flagged`는 세우지 않는다 — 여기가 `memoryWrite`와 갈리는 유일한 자리다.** 저쪽에서 그 필드가 하는 일은 자동 허용과 학습 키를 지우는 것인데 이 분류에는 둘 다 없어서, `flagged: true`는 **아무것도 바꾸지 않는다.** 효과 없는 상태를 세우면 다음 사람이 *"이건 왜 있나"*를 묻고 그 답이 «없다»면 그것은 그냥 표면이다. fail-closed는 이미 매번 승인으로 무조건 지켜진다 — `memoryWrite`가 `flagged`로 사는 마찰을 이쪽은 **기본값으로** 갖는다.

  **이 한 줄은 `WEB-ACCESS.md` §6의 매번 승인 판정에 물려 있다.** 그것이 뒤집히면 여기도 다시 판정한다. 다만 그 문서가 남긴 트리거(승인 피로)는 판정이 아니라 **CLI 표면**을 열기로 이미 정해져 있다(`kanban.md` `K-415`).

- **표시 라벨 하나가 는다** — `KIND_LABEL`에 `webSearch`, 본문은 `질의: <query>` **한 줄**이다. `memoryWrite`처럼 다음 줄부터 내리지 않는 이유는 질의가 400자 상한의 단문이라서다. 라벨 테이블이 `Record<GateSubject["kind"], string>`이라 **누락은 컴파일 에러**이므로, 이 항은 실물을 강제하는 것이 아니라 **그 기계가 이미 잡는다는 사실**을 적어 둔다.

- **오염 런에서 추가로 하는 일이 없다.** 검색은 오염을 **만드는** 쪽이고(`ToolResult.source: "network"`), 오염 플래그가 하는 일(자동 허용·키 무효화)은 이 분류에 처음부터 없다. 남는 것은 계층 4b의 기존 `TAINT_WARNING`이 경고에 함께 실리는 것뿐이며, `memoryWrite`가 받는 **사전 고지**(오염 런에서 도구가 저장을 거부한다)에 대응하는 것은 없다 — 검색은 오염 런에서 거부되지 않는다. **게이트가 아는 것만 말한다**는 판정 B‑5의 규율이 여기서도 침묵을 요구한다.


## 4. 공개 인터페이스와 배선

```typescript
type ApprovalMode = "manual" | "off";     // SAFE-DEFAULTS §1이 정본. 닫힌 유니온

interface ApprovalRequest {
  toolCallId: string;
  toolName: string;
  subject: GateSubject;
  /** 위조 탐지 처리를 마친 표시 문자열 — CLI는 가공 없이 그대로 표시한다 */
  display: string;
  /** 위험 패턴·비가시 문자 탐지 등 경고. 프롬프트에 함께 표시 */
  warnings: readonly string[];
  /** "항상 허용" 선택 시 allowlist에 학습될 키. 없으면 그 선택지를 제공하지 않는다 */
  allowAlwaysKey?: string;
}

type ApprovalResponse = "allow-once" | "allow-always" | "deny";

interface ApprovalPrompt {
  ask(req: ApprovalRequest, signal: AbortSignal): Promise<ApprovalResponse>;
}

interface AllowlistStore {
  has(key: string): boolean;
  add(key: string): void;                  // 영속화는 구현체(호스트)의 몫
}

interface ApprovalGateConfig {
  mode: ApprovalMode;
  denyRules?: readonly string[];
  toolProfiles: Readonly<Record<string, GateToolProfile>>;
  classifier: PathClassifier;
  allowlist: AllowlistStore;
  prompt: ApprovalPrompt;
}

/** 반환이 곧 코어 훅 — 배선은 new Agent({ hooks: createApprovalGate(config) }) 한 줄 */
function createApprovalGate(config: ApprovalGateConfig): {
  beforeToolCall: NonNullable<AgentHooks["beforeToolCall"]>;

  /** 2026-08-08 — 오염 추적(§2 계층 4b). 호스트가 도구 결과와 런 시작에서 각각 호출한다 */
  noteToolResult(result: Pick<ToolResult, "source">): void;
  resetTaint(): void;

  /** 2026-08-09 — 현재 런의 오염 여부. 게이트 밖에서 오염을 소비하는 도구가 읽는다 */
  isTainted(): boolean;
};
```

- **오염 추적은 훅을 더 갖지 않고 평범한 메서드로 노출한다** (2026-08-08). `afterToolCall`을 게이트가 소유해 버리면 출력 후처리(트렁케이션)라는 원래 소비자와 충돌해 호스트가 합성을 강요받는다(`CORE-INTERFACE.md` §7 — 훅 소비자는 각각 하나로 확정돼 있다). 메서드로 두면 호스트가 `afterToolCall`에서 `noteToolResult`를, `agent_start`에서 `resetTaint`를 부르면 되고, **게이트는 여전히 코어 타입만 알고 이벤트 스트림도 전송도 모른다.** 런 경계 지식은 호스트에 남는다.

- **`isTainted()`는 가산 노출이지 새 상태가 아니다** (2026-08-09 — `MEMORY.md` §5의 요구). 오염 상태는 이미 게이트가 계층 4b를 위해 들고 있고, 지금까지 **쓰기 메서드만**(`noteToolResult`·`resetTaint`) 노출돼 있었다. 읽기를 열 뿐이므로 **파이프라인 출구도 계층도 늘지 않는다.**

  **왜 게이트가 오염의 소유자로 남는가** — 오염을 소비하려는 쪽(`remember`)이 자기 오염 상태를 따로 들면 게이트의 4b와 **두 개의 진실**이 생기고, 둘이 어긋나는 순간 어느 쪽이 맞는지 판정할 근거가 없다. 상태는 한 곳에 두고 읽기만 연다.

  **호출자는 값이 아니라 함수로 배선한다** — `MEMORY.md` §4.1의 `isRunTainted: () => boolean`이 그 형태다. 도구가 게이트 인스턴스를 값으로 들면 (1) 도구 패키지가 게이트를 임포트하게 되어 `packages/memory`의 예산이 깨지고, (2) 도구가 게이트보다 먼저 만들어지는 배선 순서에서 참조가 성립하지 않는다. 호스트가 `() => gate.isTainted()`로 늦은 바인딩을 만든다.

  **오염 소비의 강제 지점은 게이트가 아니라 도구다.** `remember`의 거부를 게이트 계층으로 옮기면 4b가 "플래그"에서 "출구"로 성격이 바뀌어 판정 C-6을 뒤집게 되고, 도구가 소유하면 **게이트 모드가 `off`여도 거부가 유효하다**는 이득이 온다 — 크리덴셜 denylist가 게이트와 무관하게 동작하는 것과 같은 자리다(`TOOLS-INTERFACE.md` §3).
- **`webFetch`의 `allowAlwaysKey`는 `webFetch:<origin>`이다** (2026-08-09). **`origin`의 표기는 전역 `URL`의 `origin` 직렬화 그대로다** — 기본 포트는 **생략**되고(`https://example.com`), 비기본 포트는 나타난다(`https://example.com:8443`). 표기를 우리가 발명하지 않는 이유는 (1) 포트를 덧붙이는 코드가 그 자체로 또 하나의 정규화 규칙이 되고, (2) 이 키는 `~/.neo-agent/allowlist`에 **영속**되므로 나중에 표기를 바꾸면 사용자의 학습이 통째로, 그리고 이유 없이 무효가 되기 때문이다(`CLI-INTERFACE.md` §10). 요구는 "기본 포트가 정규화된다"이고 — `https://example.com/`과 `https://example.com:443/`이 같은 키 — 플랫폼 직렬화가 그 요구를 구성으로 만족한다. [QA-C 판정 C-3]
- **경로·쿼리는 키에 들어가지 않는다**(URL 전체면 쿼리가 바뀔 때마다 학습이 무효가 되어 아무것도 학습되지 않는다). **도메인 접미사로 넓히지 않는다** — `https://example.com`과 `https://sub.example.com`은 다른 키이며, 서브도메인 탈취에 열지 않기 위해서다. 근거 정본은 `WEB-ACCESS.md` §6이고, 같은 문서가 **호스트 단위 학습이 쿼리스트링 유출을 막지 못한다는 것을 인정**한다 — 그 구멍을 좁히는 것은 §2 계층 4b(오염)다.
- **불투명 origin(`origin === "null"`)에는 키를 주지 않는다** (2026-08-09). `file:///a`·`data:,x`는 전역 `URL`로 **파싱에 성공**하지만 origin이 대상을 식별하지 못한다 — 순진하게 `url.origin`을 키로 쓰면 서로 다른 모든 불투명 URL이 `webFetch:null` **한 키**로 묶여, `file:///a`를 한 번 허용한 사용자가 `file:///home/user/.ssh/id_rsa`까지 허용한 셈이 된다(§7이 첫 토큰 키를 배제한 바로 그 실패 양태다). **분류는 `webFetch`로 유지하고 `allowAlwaysKey`만 제공하지 않는다** — 셸 연산자 포함 명령과 **같은 기계**다(§2 계층 6). `unknown`으로 떨어뜨리지 않는 이유는 그쪽 `display`가 "게이트 프로필에 등록되지 않았다"는 **거짓 사유**를 보이고 URL이 화면에서 사라지기 때문이다: 승인 화면이 거짓말하면 게이트 전체가 무의미하다. **게이트가 스킴 정책을 갖는 안은 기각한다** — 스킴 판정은 `packages/web`의 관할이고(`WEB-ACCESS.md` §4), 게이트가 그것을 겸하면 "판정기가 둘"이 된다. [QA-C 판정 C-4]
- **`shellExec`의 `allowAlwaysKey`는 `shell:<cwd>:<정규화된 명령>`이다 — 작업 디렉터리가 키에 들어간다** (2026-09-09 · `K-598`). 초판(2026-08-06)은 `shell:<정규화된 명령>` 하나였고, 그래서 **승인 화면이 보여주는 것보다 넓은 것을 학습했다.** `display`는 `shellExec`에 **언제나** `작업 디렉터리:` 줄을 싣는데(아래 표시 계약) 학습 키가 그것을 버렸으므로, 사용자는 「이 디렉터리에서 이 명령」을 승인하고 게이트는 「어디서든 이 명령」을 배웠다 — §7이 첫 토큰 키를 배제하고 바로 위 항이 불투명 origin에 키를 안 주는 것과 **같은 실패 양태**이며 근거도 같다: *승인한 적 없는 것을 통과시키는 쪽이 나쁘다.*

  **폭이 워크스페이스를 넘는다는 것이 판정을 갈랐다.** allowlist 파일은 `~/.neo-agent/allowlist` **하나**이고 워크스페이스마다 갈리지 않는데(`CLI-INTERFACE.md` §10), 워크스페이스 루트는 **neo-agent를 띄운 디렉터리**다. 그래서 옛 키 `shell:npm test`는 사용자가 이 에이전트를 띄우는 **모든 프로젝트에서** 자동 통과했다. `npm test`·`make`·`./x.sh`처럼 명령이 파일시스템을 거쳐 해석되는 경우 **같은 문자열이 디렉터리마다 다른 프로그램**이고, 그것은 이 레포 자신(모노레포)에서 이미 참이다.

  **마찰은 판정이 갈리는 자리에만 는다.** `cwd` 미지정은 워크스페이스 루트로 해석되므로(§3 `PathClassifier` 계약의 `"."`) 루트에서 도는 명령의 키는 **값 하나로 안정**된다. 실측(2026-09-09): 실사용 세션의 `shell` 호출 12건이 **전부 `cwd` 미지정**이었다 — 이 개정이 오늘의 사용에 더하는 프롬프트는 **0**이고, 프롬프트가 느는 자리는 모델이 실제로 디렉터리를 옮긴 자리, 즉 판정이 실제로 달라야 하는 자리뿐이다. 이것이 §2 계층 6의 저울(*"학습이 좁아 마찰이 늦게 줄더라도"*)을 이번에는 **치르지 않고** 좁히는 근거다.
- **키는 평문이고 `cwd`는 해석된 절대 경로다 — 해시로 만들지 않는다** (2026-09-09). OpenClaw 2.0의 `sha256:cwd-argv:v1:` 지문이 같은 문제를 푸는 선행이지만(`plans/20260909-kanban-itil-openclaw2-review.md` §3.2 #1) **표기는 채택하지 않는다**: (1) allowlist 파일은 사용자가 읽고 지울 수 있어야 하고 그것이 학습을 회수하는 **유일한 수단**인데(게이트는 파일을 재읽기하지 않는다 — §5), 해시면 무엇을 지우는지 알 수 없어 가시성 원칙(`ARCHITECTURE.md` §2.6)이 깨진다. (2) 나머지 키가 전부 평문이라 한 파일에 두 방언이 생긴다. **워크스페이스 상대 경로도 기각한다** — 상대면 서로 다른 워크스페이스의 같은 상대 위치가 **한 키**가 되어 위 항이 든 결함을 다른 옷으로 재생산한다. 절대 경로는 파일 도구 키(`fileWrite:/ws/src/a.ts`)와 같은 규율이고, 워크스페이스를 옮기면 학습이 무효가 되는 성질도 그쪽과 같다.
- **`cwd`에 `:` 또는 개행이 있으면 키를 주지 않는다** (2026-09-09). **새 계층이 아니라 §2 계층 6이 이미 쓰는 기계의 네 번째 사용**이다(셸 연산자 · 불투명 origin · `memoryWrite`/`webSearch`). 근거 둘:
  - **단사성.** `shell:<cwd>:<명령>`이 (cwd, 명령) 쌍을 유일하게 표현하려면 `cwd` 필드가 `:`을 갖지 않아야 한다. 아니면 `cwd`가 `/ws:a`인 `npm test`와 `cwd`가 `/ws`인 `a:npm test`가 **둘 다 `shell:/ws:a:npm test`**가 되어 한쪽 승인이 다른 쪽을 통과시킨다 (**2026-09-09 정정** — 초판이 든 예시 `(/ws/a, npm test)` / `(/ws, a:npm test)`는 실제로는 `shell:/ws/a:npm test`와 `shell:/ws:a:npm test`로 **갈린다.** 규칙과 가드는 옳았고 예시만 틀렸다 — 충돌하려면 `:`이 `cwd` **안**에 있어야 한다. 독립 QA가 잡았다: `plans/20260909-gate-cwd-key-qa-report.md`) — 좁히러 온 개정이 넓히는 자리다. 보장이 서면 첫 `:`이 언제나 경계이므로 **명령 쪽은 `:`을 자유롭게 가져도 된다.**
  - **한 줄 1키.** 개행이 들어가면 `CLI-INTERFACE.md` §10의 파일 포맷이 깨진다. 명령 쪽은 셸 연산자 판정이 `\n`을 이미 잡아 키를 주지 않으므로, 이 규칙으로 **개행이 들어갈 수 있는 세 자리 중 둘이 선다** — 셋째(파일 도구 경로)는 아래 항이 든다. (**2026-09-09 정정** — 이 문장은 대칭을 **둘 사이**의 것으로 적어 열거를 거기서 닫았고, 그래서 파일 도구 경로가 아무 가드도 없이 남았다. 근거: `plans/20260909-allowlist-file-verify-report.md` D-1.) POSIX 경로는 NUL을 가질 수 없으므로 NUL은 규칙에 넣지 않는다.
- **파일 도구 경로가 개행을 갖거나 양끝이 트림으로 변하면 키를 주지 않는다** (2026-09-09 · `K-606`·`K-607`). 새 계층이 아니라 §2 계층 6이 이미 쓰는 기계의 **다섯 번째 사용**이다(셸 연산자 · 불투명 origin · `memoryWrite`/`webSearch` · `cwd` 문법). 근거 둘과 경계 하나:
  - **한 줄 1키.** POSIX 경로는 개행을 가질 수 있고 경로 판정기가 그것을 그대로 돌려준다. 개행이 든 키는 allowlist 파일에서 **두 줄**이 되고, 뒤 줄은 그 자체로 유효한 키 모양이라 **사용자가 승인한 적 없는 대상이 영구 학습된다** — 2026-09-09 실측: `fileWrite:/ws/a\nfileWrite:/etc/shadow`가 발급됐고, 다음 세션에서 `fileWrite:/etc/shadow`가 계층 6을 통과했다. 승인한 키 쪽은 반대로 사라진다. §7이 첫 토큰 키를 배제하고 위 항들이 불투명 origin·넓은 셸 키를 배제한 것과 **같은 실패 양태**이고 근거도 같다: *승인한 적 없는 것을 통과시키는 쪽이 나쁘다.*
  - **트림 불변.** allowlist 파일 구현은 줄을 트림해 읽는다 — 손편집 관용이고, 손편집이 학습을 회수하는 유일한 수단이라 그 관용이 계약이다(`CLI-INTERFACE.md` §10). 그래서 게이트는 **트림에 불변인 키만** 내야 한다. 양끝이 공백인 키를 발급하면 `add`는 성공하는데(경고도 없다) 다음 세션의 `has`가 거짓이 되고, 중복 차단이 갈려 같은 키가 **세션마다 한 줄씩** 쌓인다 — §5의 「추가만」이 「지워지지 않는 중복 누적」이 된다.
  - **`:`은 막지 않는다 — `cwd`와의 비대칭은 의도된 것이다.** 파일 키는 첫 `:`이 경계이고 그 뒤가 전부 경로라 단사성이 이미 선다. `cwd`가 `:`을 막는 것은 **뒤에 필드가 하나 더 오기 때문**이고, 같은 금지를 경로에 걸면 `:`을 가진 정상 경로가 이유 없이 학습 불가가 된다.
  - **대가와 의도적 비결과.** 걸렸을 때의 대가는 다른 자리와 같다 — *"이 경로는 항상 허용으로 학습되지 않는다"*뿐이고 안전한 방향의 오탐이다. **사유를 사용자에게 표시하지 않는다** — **셸 연산자**와 같은 처리다(2026-09-09 정정: 초판이 여기에 불투명 origin을 함께 들었는데 **그쪽은 반대로 사유를 싣는다** — 그 항이 「거짓 사유를 보이는 것」을 근거로 정직한 표시를 요구했기 때문이다. 독립 QA F-3이 잡았다). 이 항이 사유 없는 쪽의 모집단을 「모델이 제어하는 임의 경로」로 넓힌다는 것이 새로운 부분이다. `ARCHITECTURE.md` §2.6이 요구하는 **기록된 의도적 비결과**로 여기 남기고, 표시 여부의 재판정은 §2 계층 6이 진다.

- **옛 형식 키의 마이그레이션을 만들지 않는다** (2026-09-09). 옛 `shell:<명령>`은 새 키와 **거의 언제나** 매칭되지 않고 파일에 죽은 줄로 남는다 — 새 키는 `shell:` 뒤에 절대 경로가 오고 그 뒤에 `:`이 이어지는 모양이라, 옛 키가 그 모양이 되려면 **학습된 명령 자체가 `<절대경로>:<나머지>` 꼴**이어야 한다. 그 좁은 겹침을 무시하는 근거는 아래 실측이지 「불가능하다」가 아니다. 지우는 코드를 두지 않는 이유는 §5가 allowlist를 **추가만** 하는 것으로 못박았기 때문이다 — 삭제·재작성 경로를 열면 그 계약이 깨지고 얻는 것은 죽은 줄 몇 개의 정리뿐이다.

  **실측(2026-09-09): `~/.neo-agent/allowlist`가 존재하지 않는다.** 이 규칙이 오늘 적용되는 모집단은 **공집합**이고, 그래서 위 origin 항이 경계한 *"사용자의 학습이 통째로, 그리고 이유 없이 무효가 되기 때문이다"*가 지금은 아무에게도 일어나지 않는다. **이 개정을 지금 하는 근거가 그것이다** — 실사용이 시작되면 그 값이 0을 벗어나고, 같은 개정이 그때는 실제 비용을 갖는다.

  **재도입 트리거**: *"키 형식을 다시 바꾸는 개정이 생겼고, 그 시점의 `~/.neo-agent/allowlist` 줄 수가 0이 아닐 때"* — 그때 마이그레이션 수단을 다시 판정한다.
- **표시 위조 탐지는 게이트 책임이다** (OpenClaw `exec-approval-command-display` 재작성, REUSE-MAP §2.2 채택 확정). `display`를 만들 때 비가시 문자·동형이의 문자를 탐지해 가시 표기로 이스케이프하고 `warnings`에 싣는다.

  **모집단은 「표시본에 실리는 모든 모델 제어 문자열」이고, `shellExec`에서 그것은 명령과 `cwd` 둘이다** (2026-09-09 명문화 — 독립 QA V-1·V-2). 이 항이 «`display`를 만들 때»라 적은 것이 처음부터 그 뜻이었으나 구현은 명령 쪽에만 돌고 있었고, `cwd`는 비가시 문자 이스케이프만 따로 타 **동형이의 문자가 원문 그대로 화면에 나오고 경고도 안 붙었다.** 2026-09-09 개정이 `cwd`를 **영속 학습 키의 일부**로 만들면서 그 구멍이 화면을 넘어 allowlist까지 이어졌다 — 위조된 `cwd`가 든 키가 「항상 허용」으로 학습될 수 있었다. **`cwd`의 위조 흔적은 명령의 것과 똑같이 `spoofed`를 세운다** — 즉 자동 허용과 학습 키를 무효화한다(§2 계층 4·6과 같은 합류). `warnings`는 어느 쪽에서 왔는지 구분 가능해야 한다 — 문면은 구현 재량이되 «명령의 위조»와 «작업 디렉터리의 위조»가 화면에서 갈리지 않으면 사용자가 무엇을 다시 봐야 하는지 알 수 없다. CLI가 이걸 다시 가공하면 위조 탐지가 무의미해진다 — **CLI는 그대로 표시만 한다.** 승인 UI가 거짓말하면 게이트 전체가 무의미하다.
- **텍스트의 수신자가 언어를 정한다** (2026-08-06 명문화). `reason`은 모델에게 도구 에러로 전달되므로(CORE-INTERFACE §7) **영어**로 쓴다 — 도구 구현의 에러 텍스트가 이미 영어라, 한 트랜스크립트 안에서 언어가 갈리면 모델이 보는 실패 서술이 일관되지 않는다. 반대로 `display`·`warnings`는 CLI가 사용자에게 보여주는 것이므로 **사용자 언어**를 쓴다. 두 필드가 한 객체에 있다고 해서 같은 언어여야 하는 것이 아니다 — 읽는 쪽이 다르다.
- 웹 UI 도입 시 바뀌는 것은 `ApprovalPrompt` 구현 하나다 — 게이트 모듈은 그대로다(CORE-INTERFACE §7의 배치 근거가 이 계약으로 실현된다).

## 5. 동결과 allowlist의 예외

- `mode`·`denyRules`·`toolProfiles`·`classifier`는 **생성 시 동결**된다(SAFE-DEFAULTS §4 — 시작 시 1회 읽기). 세션 중 이 값들을 바꾸는 공개 API는 존재하지 않는다.
- **allowlist는 동결의 명시적 예외다** — 세션 중 **추가만** 일어난다. 방향이 약화(허용 확대)지만 원천이 사용자의 명시적 프롬프트 응답(`allow-always`)이므로 허용한다. `AllowlistStore.add`는 게이트의 프롬프트 응답 처리 경로에서만 호출한다 — 도구·훅·모델 산출물이 프로그래밍적으로 allowlist를 넓히는 경로를 만들지 않는다(코드 리뷰 기준).
- 게이트는 allowlist 파일을 다시 읽지 않는다(재읽기 = 세션 중 설정 변경 경로). 추가는 메모리와 스토어에 동시에 반영되고, 외부 편집의 적용 시점은 다음 프로세스 시작이다.

## 7. 미결 — 이 문서가 정하지 않은 것

- **하드라인·위험 패턴의 구체 목록** — 구현 시 확정. 계약은 "하드라인 최소 원칙"(§2)과 "유계 필러만"(§2)이다.
- ~~**allowlist 키 정규화 규칙**~~ — 2026-08-06 구현 확정: 셸은 **정규화된 명령 전체**(`shell:npm run build`), 파일 도구는 **해석된 절대 경로**(`fileWrite:/ws/src/a.ts`). **2026-09-09 개정: 셸 키는 `shell:<cwd>:<정규화된 명령>`이다** — 작업 디렉터리가 키에 들어간다(§4 · `K-598`). 옛 `shell:<명령>`은 사용자가 neo-agent를 띄우는 **모든 워크스페이스**에서 통과했고, 승인 화면이 이미 보여주는 `작업 디렉터리:`를 학습이 버리는 형태였다. 2026-08-09 추가: `web_fetch`는 **origin**(`webFetch:https://example.com` — 전역 `URL.origin` 직렬화 그대로이므로 기본 포트는 생략된다. §4). 첫 토큰을 키로 삼으면 `git status`를 허용한 사용자가 `git push --force`까지 허용한 셈이 된다 — 학습이 좁아 마찰이 늦게 줄더라도, 승인한 적 없는 것을 통과시키는 쪽이 나쁘다. 연산자 포함 명령의 학습 불가(§2)는 계약 그대로다. **2026-09-09 추가 — 학습 불가 사유는 하나가 아니다**: 파일 도구 경로가 개행을 갖거나 양끝이 트림으로 변하면 그 경로도 키를 얻지 못한다(§4 · `K-606`·`K-607`).
- **워크스페이스 밖 `cwd`에도 학습 키를 주는가** (2026-09-09 신설 — `K-603`). 게이트는 `shellExec`에 `scope` 판정을 하지 않으므로(§3) `cwd`가 `outside`여도 키가 만들어지는데, 도구는 **실행 직전에** 그 `cwd`를 거부한다(`TOOLS-INTERFACE.md` §3의 재판정). 즉 **학습은 되고 실행은 안 되는 키**가 생길 수 있다. 이 자리는 이번 개정이 만든 것이 아니라 **드러낸 것**이다 — 옛 키는 `cwd`를 안 담았으므로 관측할 표면이 없었다. 갈래 둘: 게이트가 `outside`에 키를 안 주거나(불투명 origin과 같은 기계), 그대로 두고 「게이트는 격리가 아니라 실수 방지 장치」(`REUSE-MAP.md` §2.2)로 남긴다.
- **deny 규칙 글로브의 방언** — 구현 시 확정(`*`/`**`/`?` 지원 범위).
- ~~**allowlist 영속화 위치·포맷**~~ — 2026-08-06 해소: `CLI-INTERFACE.md` §10 (`~/.neo-agent/allowlist`, 한 줄 1키, 시작 시 1회 로드 — denylist 안이라 에이전트가 도구로 자기 allowlist를 넓힐 수 없다).
