## 1. 언어: TypeScript — 왜 Python이 아닌가

두 레퍼런스가 서로 다른 언어(OpenClaw=TS, hermes=Python)라 어느 쪽을 골라도 절반의 참조는 언어가 어긋난다. 갈림길은 `ARCHITECTURE.md` §3.1(구)에 정리했던 대로 **UI 비중**이었고, 다음 근거로 TypeScript로 확정한다.

**1. UI/UX 우선 원칙이 언어를 결정한다.** 프로젝트 규칙(CLAUDE.md)이 사용자 친화적 UI/UX를 우선한다고 선언한다. TypeScript는 CLI → 웹 UI → 데스크톱(필요 시)을 한 언어로 간다. Python을 고르면 UI를 얹는 순간 어차피 두 언어 체제가 되고, 개인 1인이 유지보수하는 프로젝트에서 두 언어 체제는 그 자체가 비용이다.

**2. 가장 되돌리기 어려운 원칙의 참조 구현이 TypeScript다.** 확정 원칙 1번(§2.1 — 에이전트 코어는 전송 계층을 모른다)의 최고 선례가 OpenClaw `packages/agent-core/`다. 코드를 복사하지는 않지만(재작성 원칙), 경계 설계·이벤트 유니온·큐 기반 상태 머신을 같은 언어로 옆에 두고 대조하며 재작성할 수 있다는 것은 실질적 이점이다. 반대로 hermes에서 가져올 것들(승인 게이트 5계층, SSRF connect 직전 재검증, 압축 세션 분기)은 **알고리즘과 정책**이라 언어를 건너 재작성해도 잃는 것이 적다.

**3. 컴플라이언스 타입 강제(§2.2)는 TypeScript가 자연스럽다.** "근거가 공식 문서가 아니면 **작성 자체가 불가능**해야 한다"는 원칙은 discriminated union + 리터럴 타입으로 **컴파일 타임**에 게이트를 만들 수 있다. Python(pydantic)은 런타임 검증이라 한 단계 늦다. IDEA-002가 이 경로로 구현된다.

**4. 생태계가 필요한 방향과 일치한다.** MCP SDK 정본이 TypeScript다(Footprint Ladder 5단). 메시징을 공식 봇 API로만 쓴다는 원칙상 Telegram/Discord/Slack SDK도 TS가 1급이다. Anthropic·OpenAI 공식 SDK는 양쪽 다 있으므로 무차별. Python의 강점(AI/ML 라이브러리)은 로컬 모델 학습·추론을 할 때 의미가 있는데, 우리는 모델을 API로만 접근하므로 해당 없다.

**포기하는 것** — hermes 참조 코드와의 언어 일치. 단 위 2번대로, 잃는 것은 코드가 아니라 대조의 편의다. hermes에서 가져올 목록은 전부 정책·알고리즘 수준이며 `docs/hermes-agent-architecture.md`에 파일·줄번호로 고정되어 있으므로 재작성 원본으로는 충분하다.

## 2. 런타임: Node.js 24 LTS+, 빌드 스텝 없음

- **Node 24 LTS를 최소선**으로 한다. 개발 머신은 25.2.1로 확인. 24를 최소선으로 하는 이유는 두 가지가 24에서 안정권에 들었기 때문이다 — `node:sqlite` 내장, 네이티브 타입 스트리핑.
- **빌드 스텝을 두지 않는다.** `.ts`를 Node가 직접 실행한다(타입 스트리핑, 이 머신에서 동작 확인). tsconfig에 `erasableSyntaxOnly: true`를 켜서 스트리핑 불가능한 문법(enum, namespace, 파라미터 프로퍼티)을 컴파일 에러로 강제한다 — 어차피 셋 다 안 쓰는 게 현대 TS 관례다.
- 타입 검증은 실행과 분리해 `tsc --noEmit`으로 한다. 실행이 타입을 안 본다는 것은 검증 게이트가 별도로 반드시 있어야 한다는 뜻이다(CI·pre-commit).
- 폴백: 네이티브 스트리핑이 막히는 상황(데코레이터 필요 등)이 오면 `tsx`를 dev 의존성으로 추가한다. ~~번들링·배포 형태는 배포가 필요해질 때 결정한다~~ → **2026-08-09 확정** (`DISTRIBUTION.md`): 빌드 산출물을 만들지 않고 **링크 설치** 하나로 간다.
  > **이 절이 몰랐던 제약이 실측으로 드러났다.** 타입 스트리핑은 `node_modules` 아래의 실제 `.ts` 파일에 대해 **거부**된다(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`) — 심볼릭 링크 경유만 realpath 해석으로 통과한다. 즉 "빌드 스텝 없음"은 **워크스페이스·링크 설치에서만 성립하는 성질**이고, npm publish는 그 자체로 빌드를 강제한다. 이 문서의 "빌드 스텝을 두지 않는다"는 그래서 배포 형태와 분리 불가능한 결정이었다(`DISTRIBUTION.md` §2.1).

## 3. pnpm 워크스페이스: 경계를 패키지로 강제

§2.1(코어의 전송 계층 비의존)은 규칙만으로는 지켜지지 않는다. **코어를 별도 패키지로 두면 의존성 방향이 `package.json`에 드러나** 경계 침범이 리뷰에서 걸린다. OpenClaw가 `packages/agent-core/`로 증명한 방식이다.

- 최소 구성: `packages/core`(에이전트 루프 — 의존성 목록이 리뷰 대상) + 앱 패키지(코어를 워크스페이스 의존으로 소비).
- 구체 레이아웃(앱 패키지가 CLI인지 웹인지, 몇 개인지)은 MVP 범위 결정(§2.8, 확정 — CLI 하나) 후에 잡는다. **스캐폴딩을 미리 하지 않는다**는 기존 결정 유지.

## 4. 스키마/검증: Zod v4

- 툴 정의는 결국 JSON Schema로 모델에 전달된다 — Zod v4는 `z.toJSONSchema()`를 내장한다. 스키마 한 벌로 런타임 검증 + 툴 정의 생성을 겸한다.
- MCP 공식 SDK가 Zod 기반이라 Footprint Ladder 5단(MCP)에 도달했을 때 마찰이 없다.
- OpenClaw의 TypeBox는 와이어 프로토콜 코드젠(JSON Schema → Swift)이라는 그쪽 요구에서 나온 선택이다. 우리는 다중 클라이언트 코드젠 요구가 없다. 생기면 그때 재검토한다.

## 5. 상태 저장: SQLite (`node:sqlite`)

- **내장 모듈이라 네이티브 의존성이 0이다** (better-sqlite3류의 빌드 문제 원천 차단). 이 머신에서 FTS5와 **트라이그램 토크나이저**(한국어 검색의 전제, IDEA-004) 동작을 확인했다 (SQLite 3.51.1).
- `node:sqlite`는 아직 experimental 표기가 있으나, API 표면이 좁고(DatabaseSync/prepare/exec) OpenClaw가 이미 실전 사용 중인 선례가 있다. 변경이 오더라도 흡수 범위가 작다.
- 쿼리 빌더(Kysely)는 **지금 넣지 않는다.** 스키마가 커져 raw SQL이 부담이 되는 시점에 도입을 검토한다. 스키마 경계는 2026-08-06 확정됐다(`SESSION-STORE.md` — DB 1개, 테이블 3개, raw SQL로 충분). ~~FTS5 도입 시점만 미결~~ → **2026-08-07 채택 확정** (`SEARCH.md`, 스키마 v3) — 실측해 둔 trigram 전제가 소비자를 만났다.

## 6. 모델 접근: 공식 SDK + API 키만

- 1차 프로바이더는 Anthropic(`@anthropic-ai/sdk`). 추가 프로바이더는 해당사 **공식 SDK + 공식 엔드포인트 + API 키**로만 붙인다.
- User-Agent·클라이언트 식별자는 neo-agent로 정직하게 보낸다. 이 원칙의 타입 레벨 강제는 IDEA-002 경로로 구현한다.
- Api/Provider 분리(OpenClaw식) 채택 여부는 스택 결정이 아니라 설계 결정 — 교체 지점은 `CORE-INTERFACE.md` §8(`ModelClient`)로 확정, 이원화는 보류(ARCHITECTURE §2.9).
