## 1. 전제 — 이것은 우리의 첫 실제 보안 경계다, 그러나 완전하지 않다

`SAFE-DEFAULTS.md` 머리와 `CORE-INTERFACE.md` §7이 반복해 온 선언 — *"여기 있는 어떤 것도 보안 경계가 아니다. 유일한 경계는 OS다"* — 에서 승인 게이트·denylist·경로 판정은 전부 실수 방지 장치였다. **샌드박스는 그 OS 경계를 처음으로 실제로 세운다.**

그러나 완전하지 않다. 두 가지를 정직하게 적는다.

- **Docker 데몬은 호스트 root 권한으로 돈다.** 컨테이너를 띄우는 행위 자체가 root 권한 데몬에 요청하는 것이고, 컨테이너 탈출은 곧 호스트 장악이다. OpenClaw 자신의 선언을 계승한다: *"This is not a perfect security boundary, but it materially limits filesystem and process access when the model does something dumb"*.
- **샌드박스 대상은 셸뿐이다**(§6). 파일 도구는 여전히 호스트에서 돈다.

## 2. 경계 — 패키지와 교체 지점

- 패키지 위치: **`packages/sandbox`**. 의존성 예산: **`zod` + `@neo-agent/core` 정확히 2개.**
- **허용 내장 모듈**: `node:child_process` 하나다 — docker CLI 호출이 이 패키지의 본업이다.
- **금지 모듈**: `node:fs`·`node:https`·`node:http`·`node:net`·`node:tls`·`node:sqlite`·`node:dgram`·`node:worker_threads`
  샌드박스가 파일이나 네트워크에 직접 닿을 이유가 없다 — 예산 게이트(`scripts/check-core-budget.mjs`)가 검사한다. **2026-08-24 개정 둘.** ① 허용과 금지가 한 줄에 있던 것을 두 불릿으로 갈랐다 — 열 문서의 금지 선언을 한 앵커 문자열로 닫아 문서↔게이트 대조를 기계가 재게 한 개정이다(`PROVIDERS.md` §2.1과 같은 형태이고, `node:` 접두 통일의 근거도 그 절의 2026-08-14 선례가 든다). ② `node:tls`·`node:dgram`·`node:worker_threads` 셋을 열거에 더했다. 게이트는 그전부터 셋을 막고 있었고 문서만 그 사실을 안 들고 있었다.
  **`node:tls`의 근거는 아래 `node:net` 금지와 같은 자리에서 나온다.** `node:net`을 막는 이유는 Docker HTTP API를 쓰려면 유닉스 소켓에 직접 붙어야 하고 소켓 접근 코드를 갖는 것 자체가 §1의 위험을 우리 코드 안으로 들이는 일이기 때문인데, **같은 API는 원격 데몬 상대로 TCP+TLS로도 열린다**(`--tlsverify` 구성). `node:net`만 막고 `node:tls`를 열어 두면 로컬 소켓 문은 닫고 원격 데몬 문은 연 상태가 되어, 이 절이 «CLI 호출로 못박는다»고 정한 결정이 반쪽만 강제된다. 원격 실행 백엔드를 안 만든다는 것은 §7이 이미 판정했으므로 이 패키지가 TLS를 스스로 열 자리는 애초에 없다.
  **`node:dgram`·`node:worker_threads`의 근거는 앞의 네트워크·파일 금지와 같다.** UDP 소켓도, 워커 스레드가 자기 컨텍스트에서 여는 소켓·파일 핸들도 위 금지를 돌아가는 경로이므로, 함께 막지 않으면 차단이 반쪽이 된다. 워커는 특히 이 패키지에서 값이 없다 — 실행은 컨테이너 안에서 일어나고 이쪽에 남는 것은 `docker` 프로세스를 기다리는 일뿐이다.
- **`packages/tools`를 임포트하지 않는다.** `ShellExecutor` 계약(`TOOLS-INTERFACE.md` §4)을 **구조적 타입 호환**으로 만족시킨다 — 게이트가 `PathClassifier`를 임포트 없이 만족시키는 것과 같은 패턴이며, 배선은 CLI 한 곳이다. **측정 단위는 `src/**`의 임포트와 매니페스트 `dependencies`** — 타입 호환 확인용 테스트 전용 devDependency(`sandbox`의 `@neo-agent/tools`)는 위반이 아니다 (2026-08-11 명문화, `TOOLS-INTERFACE.md` §1의 J-1과 같은 규칙).
- **Docker HTTP API가 아니라 `docker` CLI를 호출한다.** API를 쓰려면 유닉스 소켓에 직접 붙어야 하는데(`node:net` 필요) 그건 이 패키지에 금지된 모듈이고, 소켓 접근 코드를 갖는 것 자체가 §1의 위험을 우리 코드 안으로 들이는 일이다.

### 흔적(🧬) 회수 — 인터페이스는 바뀌지 않는다

`SAFE-DEFAULTS.md` §2가 2026-08-06에 남긴 흔적은 *"셸 도구는 실행 백엔드를 직접 품지 않고 **실행자(executor) 경계 뒤에서 호출하도록 설계한다** — 샌드박스 도입이 셸 도구 재작성이 아니라 실행자 교체가 되도록"*이었다.

**이번 설계는 `ShellExecutor` 인터페이스를 한 글자도 바꾸지 않는다.** `HostShellExecutor` → `DockerShellExecutor` 교체이고, `packages/tools`의 셸 도구 코드는 무변경이다. 흔적 채택(🧬) 등급이 실제로 회수된 두 번째 사례다(첫 번째는 `parent_session_id` → 압축).

## 3. 기본값과 조건부 노출

```typescript
type SandboxMode = "on" | "off";   // 닫힌 유니온. auto 없음
```

- **기본값은 `"on"`이다.** `SAFE-DEFAULTS.md` §2 약속 1의 이행 — `off`가 기본인 채로 출시되는 일은 없다.
- **`"on"`인데 Docker가 없으면 셸 도구를 등록하지 않는다**(숨긴다, 실패시키지 않는다 — `REUSE-MAP.md` §2.3 "사용 불가 도구는 실패시키지 말고 숨긴다"). 시작 시 두 갈래를 명시한다: **Docker 설치** 또는 **명시적 `sandbox: "off"` 옵트아웃**(호스트 실행 선택).
- **두 갈래 안내는 시퀀스 5b에서 낸다 — 시작 배너가 아니다** (2026-08-09 판정 — QA-C C-7). 시작 단계의 경고는 이미 전부 자기 단계에서 나간다(저장소 권한·WAL 경고, 컨텍스트 창 경고). 같은 성격의 것이 배너에만 있으면 **판정이 일어난 자리와 그 귀결이 보이는 자리가 갈리고**, 배너는 REPL 진입 시점(8단계)이라 `startCli`만 부르고 REPL에 들어가지 않는 호스트에서는 **안내가 조용히 사라진다.** 등록된 도구 목록은 배너에 남는다 — `CLI-INTERFACE.md` §2가 "시작 화면에 보여야 한다"로 규정한 것이 그쪽이다.
- **`probeDocker` 자신이 던지면 기동을 실패시킨다 — 불가용으로 흡수하지 않는다** (2026-08-09 판정 — QA-C C-8). `probeDocker`의 계약이 **부재·권한 없음·무응답을 전부 판정으로 흡수하는 것**이므로, 그럼에도 예외가 나왔다면 그것은 Docker의 상태가 아니라 **우리 코드의 결함이거나 배선 실수**다. 흡수하면 그 버그가 **조용히 "셸 도구 없음"으로 나타나** 사용자는 원인이 Docker에 있다고 믿는다. 위의 "숨긴다, 실패시키지 않는다"는 **Docker가 없는 정상 상황**에 대한 규정이지 우리 코드가 깨진 상황에 대한 규정이 아니다 — 후자에는 `CLI-INTERFACE.md` §2의 "부분 기동 상태를 만들지 않는다"가 적용된다.
- **`probeDocker`의 불가용 `reason`은 진단용이지 사용자 문구가 아니다** (2026-08-09 판정). 사용자에게 보이는 안내의 정본은 `CLI-INTERFACE.md`이고(위 두 갈래), docker의 영문 stderr를 그대로 화면에 흘리면 "다음 행동"을 안내하지 못한다. **다만 감추지도 않는다** — CLI는 자체 안내 문구를 쓰고 `reason`을 원인 진단으로 덧붙인다. 미설치와 권한 없음은 사용자가 할 일이 전혀 다르므로(`apt install docker` vs `usermod -aG docker`), 원인이 안 보이면 두 갈래 안내가 실제로는 한 갈래만 가리키는 셈이 된다.

  > **2026-08-09 실측** — 이 구분은 가정이 아니다. 개발 VPS에서 `docker --version`은 성공하지만(클라이언트 바이너리) 데몬 접촉은 `permission denied`로 거부됐다(사용자가 `docker` 그룹에 없음). **`docker --version`과 `docker version`은 다른 명령이고, 전자는 가용성 판정의 근거가 될 수 없다** — "버전만이 아니라 데몬 접촉까지 확인"이라는 위 계약이 왜 그렇게 쓰였는지의 실증이다.
- **판정 상한은 30초다 — 그리고 이것은 실측 대상이 아니다** (2026-08-12 확정 · 조정 가능 세부). 계약은 여전히 *"상한이 존재한다"*이지 수치가 아니다.

  **왜 실측이 아닌가**: 이 값은 컨테이너 자원 수치(§8 — 메모리·pids)와 **성격이 다르다.** 그쪽은 *"`--pids-limit 256`이 실제로 포크를 막는가"*라는 **경험적 성질**이라 재는 것 말고 답할 방법이 없다. 이쪽은 *"데몬이 매달렸을 때 사용자를 얼마나 기다리게 할 것인가"*라는 **오차 방향의 선택**이고, 아무리 재도 답이 나오지 않는다. 원래 §8이 둘을 한 항목에 묶은 것이 분류 착오였다(§8의 정정 참조).

  **왜 30초인가 — 짧은 쪽이 더 나쁘다.** 위 두 항목이 정한 오차 방향이 그대로 적용된다: 상한이 짧으면 **느리지만 살아 있는 데몬**을 불가용으로 오판하고, 그 결과는 셸 도구가 통째로 사라지는 것이다(사용자는 이유를 알 수 없다). 반대로 상한이 길 때의 비용은 **이미 고장 난 Docker에서만** 발생한다. 정상 경로가 이 값을 소모하는 일은 없다 — 2026-08-09 실측에서 컨테이너 1개를 통째로 띄우는 데 median 205~213ms였고 `docker version`은 그보다 싸다.

  **감수하는 비용을 적어 둔다**: 데몬이 매달리면 **시작 시퀀스 5b가 최대 30초 동안 조용히 멈춘다.** 진행 표시를 넣지 않는 이유는 그것이 기동 경로에 새 표면을 만들기 때문이고(사다리에서 더 높은 단계는 표면을 안 만드는 것이다), 이 정지는 조용한 **실패**가 아니라 조용한 **대기**다 — 끝나면 반드시 판정이 화면에 나간다(§2.6이 금지하는 것은 결과가 없는 쪽이다). **트리거**: 매달린 데몬에서의 기동이 실사용에서 관측되면 진행 표시를 재검토한다.
- **이미지 실재 프로브 — 로컬 조회 하나이고 기동은 이것을 부르지 않는다** (2026-09-06 신설 · `K-519`). `sandboxImage`가 이 호스트에 실재하는지를 보는 자리를 이 절이 연다. **드는 것은 아래 넷뿐이고 새 타입도 새 필수 동작도 만들지 않는다.**

  1. **로컬 조회다.** 이미지가 이 호스트에 있는가만 보고 **`pull` 경로를 갖지 않는다.** 진단이 이미지를 내려받으면 점검하려고 친 명령이 호스트를 바꾸는 일이 되고, 그 금지는 `CLI-INTERFACE.md` §5.1 계약 5가 이름으로 든다.
  2. **`probeDocker`의 규율을 그대로 상속한다.** 던지지 않고 판정으로 흡수하며, 상한이 **존재**하고(수치는 조정 가능한 세부다 — 위 30초 항목과 같은 성격이라 실측 대상이 아니다), 불가용 `reason`은 진단용이지 사용자 문구가 아니다.
  3. **`docker` CLI와의 유일한 접점은 `packages/sandbox/src/docker.ts`다.** §2가 그 파일에 건 계약 — HTTP API가 아니라 CLI를 부른다는 것과 금지 모듈 목록 — 이 그대로 걸린다.
  4. **소비자는 오늘 `doctor` 하나다 — 시작 시퀀스 5b는 이 프로브를 부르지 않는다.** 기동은 이미지 부재를 여전히 컨테이너 실행 시점에 만나고(§4 — `docker run`의 실패를 실행 실패로 승격), 이 신설이 그 동작을 바꾸지 않는다. **그래서 §8의 「이미지 부재 시 시작 안내」 미결은 닫히지 않는다.**

  **축의 정본은 이 절이 아니다.** 무엇을 `problem`으로 셀지, 판정이 화면에 어떻게 나갈지는 `CLI-INTERFACE.md` §5.1이 든다 — 이 절이 지는 것은 프로브가 무엇을 하고 무엇을 하지 않는가다.
- **진입점을 부르는 테스트는 그 경로가 닿는 프로브를 반드시 주입한다 — 게이트가 강제한다** (2026-08-10 판정 D-1 · 2026-09-06 `doctor` 착지로 확장). 주입하지 않은 테스트는 게이트의 결과를 테스트 머신의 Docker 설치·데몬 상태·권한에 종속시킨다. 같은 테스트가 어느 머신에서는 셸 4종을, 다른 머신에서는 5종을 보게 되고 — **머신에 따라 갈리는 게이트는 게이트가 아니다.**

  | 진입점 | 닿는 프로브 | 근거 |
  |---|---|---|
  | `startCli` | `probeDocker` | 시작 시퀀스 5b가 반드시 Docker 가용성을 판정한다(`sandbox` 기본값이 `"on"`이다) |
  | `runCli` | `probeDocker` · `probeSandboxImage` | argv에 따라 `startCli`로도 `runDoctor`로도 내려간다 |
  | `runDoctor` | `probeDocker` · `probeSandboxImage` | 진단은 시작 시퀀스를 타지 않고 두 프로브를 직접 부른다(`CLI-INTERFACE.md` §5.1 계약 1) |

  **`startCli`에 `probeSandboxImage`가 없는 것은 누락이 아니다.** 위 이미지 프로브 항 4가 *"시작 시퀀스 5b는 이 프로브를 부르지 않는다"*로 정한 그대로다 — 닿을 수 없는 프로브의 주입을 요구하면 그것은 오탐이다. 반대로 `runCli`에 그것이 있는 것은 **argv를 정적으로 볼 수 없기 때문**이고, 그래서 게이트는 닿을 수 있는 쪽으로 넘어진다(같은 과요구가 `probeDocker`에도 이미 있다 — `runCli(["--help"])`는 5b에 닿지 않는다).

  > **2026-09-06 이전에는 `startCli` 한 행뿐이었다.** `doctor`가 서면서 `runCli`가 `startCli`를 안 타고도 프로브에 닿는 갈래를 얻었고, 그 사이 `runCli`만 이름으로 드는 테스트 둘(`first-run.qa.test.ts`·`first-run-rename.qa.test.ts`)은 5b의 docker 판정에 실제로 닿으면서도 모집단 **밖**이었다. 규율은 지키고 있었으나 게이트가 요구하지 않는 상태였고, 그것은 잊는 날 조용히 통과한다는 뜻이다. **같은 날 이 호스트의 docker가 가용해졌다**(`29.6.2`) — 그전까지 주입을 잊은 테스트가 우연히 결정적이었던 것은 데몬이 어차피 없었기 때문이다.

  규율로만 두지 않는 이유는 **실패가 보이지 않기 때문**이다. 주입을 잊어도 테스트는 통과하고 느려질 뿐이라 `ARCHITECTURE.md` §2.6의 최상위 심각도(silent failure)에 해당한다. 그래서 `scripts/check-core-budget.mjs`가 교차 파일 검사 5번으로 강제한다.

  **계약과 그것을 재는 기계는 단위가 다르다 — 기계는 근사다.** 위 문장이 **계약**이고 그 단위는 **호출**이다(진입점을 부르는 자리마다 주입한다). 검사가 실제로 재는 것은 **파일** 단위다 — 위 표의 이름을 드는 `packages/cli/test/*.test.ts`(명명 임포트와 네임스페이스 임포트 둘 다 대상이다)에 **주입의 흔적이 파일 어딘가에 있는가**를 보고, 대상이 0건이면 그것도 실패다(검사가 죽은 상태와 통과를 구분한다). **0건은 이름별로 잰다 — 합집합이 아니다.** 합집합으로 재면 `startCli`가 개명돼도 `runCli` 호출자가 남아 있는 한 게이트가 초록이고, 그 축은 조용히 죽는다. 그래서 한 파일 안에 주입 호출과 미주입 호출이 섞이면 게이트는 통과한다. **계약이 파일 단위로 느슨해진 것이 아니라, 기계가 호출 단위 계약을 파일 단위로 근사하는 것이다.**

  근사이므로 어긋나는 자리가 남고, 그것이 아래 "못 잡는 것" 목록이 존재하는 이유다 — 목록은 늘어나는 항목의 나열이 아니라 **이 거리의 목록**이다.

  **실해가 없음이 마지막으로 전수 확인된 것은 대상이 9파일이던 때다** (2026-08-10 독립 검증 F-6 — 2026-09-06 현재 `startCli` 19곳·`runCli` 10곳·`runDoctor` 1곳이라 그 수는 그때의 기록이다). 그 9파일은 전부 파일당 rig/harness 하나를 두고 모든 `startCli` 호출이 그것을 지났다(호출이 25개인 파일도 마찬가지라, 호출 수와 `probeDocker` 언급 수의 불일치는 위반의 신호가 아니다). 스파이 하네스가 전체 스위트에서 docker 스폰을 **0회** 관측한 것이 그 뒷받침이다. 그럼에도 두 단위의 거리를 문면에서 지우지 않는다 — 지우면 막지 못하는 것을 막는 것처럼 보이게 된다(`DISTRIBUTION.md` §8 D-3).

  **주입의 형태는 하나가 아니다.** 공용 헬퍼(`packages/cli/test/probe-docker.ts`)를 들이거나, 그 헬퍼를 쓰지 않을 이유가 있으면 자체 스텁을 `factories.probeDocker`에 넣는다 — 후자는 독립 검증 테스트가 다른 작성자의 하네스에 의존하지 않으려는 정당한 사유다(`distribution-qa-b.contract.test.ts`). 계약은 **주입했는가**이지 어느 파일을 임포트했는가가 아니다.

  **정적 검사가 못 잡는 것을 전부 적어 둔다** — 목록이 있으면 읽는 사람은 그것을 **완전한 목록**으로 읽으므로, 늘어날 때도 줄어들 때도 함께 고친다. **이 목록의 정본은 여기다**(게이트 주석이 같은 목록을 갖고, 나머지 문서는 서술하지 않고 이 절을 가리킨다 — 2026-08-10 독립 검증 C-V1).

  1. **대상 선정이 보는 표기는 둘뿐이다** — 명명 임포트 바인딩(`import { startCli }`, 별칭·여러 줄 포함)과 네임스페이스 **점 접근**(`import * as w` 후 `w.startCli`). 그 밖의 표기는 **같은 파일에서 직접 부르는데도** 대상에서 빠진다. 2026-08-10 실측으로 확인된 것: `w?.startCli(...)`(옵셔널 체이닝) · `w["startCli"](...)`(계산 접근) · `const { startCli } = w`(네임스페이스 구조 분해) · `const { startCli } = await import(...)`(동적 import). **형태를 쫓아 정규식을 넓혀도 끝나지 않는다** — 그래서 넓히는 대신 여기 적는다.
  2. 진입점을 헬퍼로 감싸 **간접 호출**하는 파일 — 테스트 파일에 `startCli`가 아예 안 나와 대상에서 빠진다. 1번이 *표기*의 문제라면 이쪽은 *파일 경계*의 문제다.
  3. factories를 **다른 파일에서 조립**해 넘기는 파일 — 주입은 했는데 그 이름이 이 파일에 없어 **오탐**(위반으로 잡힘)이 난다.
  4. **주입 여부 판정이 파일 전체의 텍스트 매칭**이라(식별자 + `:` · `,` · `}`), 주입이 아닌 언급(`const { probeDocker } = resolveFactories()` 같은 구조 분해, 단정, 타입 표기)만 있어도 통과한다.
  5. **실물 bin을 스폰하는 기동**은 주입할 표면 자체가 없다 — 자식 프로세스는 부모의 `factories`를 물려받지 않으므로 그 기동은 실제 docker에 닿는다. 판정이 파일 단위라, 같은 파일의 인프로세스 호출이 주입을 갖고 있으면 그 스폰은 잡히지 않는다(`distribution-qa-b.contract.test.ts`가 그 형태다 — 2026-09-06 T-010이 doctor 갈래를 그 파일에 더하면서 드러났다). 4번이 «주입 아닌 언급이 통과한다»라면 이쪽은 «주입할 자리가 없는 호출이 통과한다»다.

  > **한때 "네임스페이스 임포트는 통째로 안 잡힌다"가 이 목록에 있었고, 2026-08-10에 파서 확장으로 그중 점 접근 형태를 닫았다.** 검사는 네임스페이스 바인딩을 따로 모은 뒤 소스에서 `<바인딩>.startCli` 사용을 찾는다 — 그 임포트가 바인딩하는 이름은 `w`이지 `startCli`가 아니라서, 명명 임포트 파서에 한 형태를 더하는 것으로는 닫히지 않는다. **닫힌 것은 그 한 형태뿐이고 나머지는 1번에 남아 있다** — 같은 날 독립 검증(F-V1)이 *"닫았다"*를 조건 없이 적은 것을 발견해 여기까지 좁혔다.

  **2번을 정적으로 닫지 않는다** (2026-08-10 판정 D-3). 닫으려면 게이트가 테스트의 임포트를 열어 **임포트 그래프를 따라가야** 하고, 그러면 계약("주입했는가")과 기계 사이의 거리가 지금보다 훨씬 멀어진다 — 아래에서 근사라고 명시한 바로 그 거리다. "한 단계만 따라간다"는 절충도 근거가 없다(두 단계 헬퍼는 다시 빠져나간다). 그런 파일은 현재 0건이고, 생기면 하네스로 관측한다.

  즉 **계약("주입했는가")과 기계("그 이름이 그 모양으로 파일 어딘가에 있는가") 사이에 거리가 있다.** 다섯은 성격이 갈린다 — 1번은 **형태를 쫓아도 끝나지 않는 것**, 2번은 닫을 수 있지만 **닫지 않기로 판정한 것**, 3·4번은 **정적으로 닫히지 않는 것**, 5번은 **주입할 표면이 애초에 없는 것**이다. 실제로 0회인지를 재는 것은 `scripts/spy-docker/`의 하네스이며, 정적 검사는 **"잊었는가"를 막고** 하네스는 **"정말 0회인가"를 잰다** — 막지 못하는 것을 막는 것처럼 보이게 두지 않는다.
- **감지 기반 자동 전환(`auto`)은 없다.** 같은 설정이 머신마다 다른 보안 수준이 되는 것은 §2.6(가시적 결과) 위반이다 — `SAFE-DEFAULTS.md` §2 약속 2의 이행.
- 모드는 다른 보안 설정과 같이 **시작 시 1회 읽고 동결**한다(`SAFE-DEFAULTS.md` §4).

### 프롬프트 캐시와의 접점 — 도구 목록은 세션 중 바뀌지 않는다

조건부 노출은 **세션 시작 시 1회 판정**이다. `ARCHITECTURE.md` §2.4(프롬프트 캐시 보존)와 `CORE-INTERFACE.md`가 `tools`를 생성 시 동결로 두고 setter를 주지 않는 것이 그것을 이미 강제한다.

**따라서 세션 중 Docker가 죽어도 셸 도구는 목록에서 사라지지 않는다.** 그때는 도구가 실행 실패로 보고한다(에러 텍스트에 Docker 부재를 명시). 도구 목록을 동적으로 줄이는 것은 캐시를 깨는 일이고, 그 비용이 "쓸 수 없는 도구가 목록에 남는" 비용보다 크다. 이 귀결을 명시해 두는 이유는, 나중에 누군가 이것을 결함으로 보고 "고치려" 할 수 있기 때문이다.

## 4. 컨테이너 계약

### 하드닝 기본값

`SAFE-DEFAULTS.md` §2 약속 3이 지정한 기준선(OpenClaw `validate-sandbox-security.ts`의 값)을 그대로 이행한다.

| 설정 | 값 | 근거 |
|---|---|---|
| `--network` | **`none`** | §5. 웹은 `web_fetch`라는 감사된 문 하나로만 |
| `--read-only` | 루트 파일시스템 읽기 전용 | 워크스페이스 마운트만 쓰기 가능 |
| `--cap-drop` | `ALL` | 개인용 셸 명령에 리눅스 capability가 필요할 일이 없다 |
| `--security-opt` | `no-new-privileges` | setuid 경유 권한상승 차단 |
| `--user` | **호스트의 uid:gid** | 컨테이너가 만든 파일이 root 소유가 되면 호스트에서 고칠 수 없다. 사용성이자 안전 |
| `--pids-limit`, 메모리 상한 | 유계 | 포크 폭탄·메모리 고갈이 호스트를 끌고 내려가지 않게. 수치는 §8 |
| `--memory-swap` | **`--memory`와 같은 값** | 2026-08-09 구현에서 추가. **지정하지 않으면 docker 기본이 메모리의 2배**라, `--memory 1g`만 준 컨테이너가 실제로는 2g까지 쓴다 — 상한을 걸었다고 믿는데 실질이 두 배인 상태다. 같은 값을 주어 스왑을 0으로 만든다 |
| `/tmp` | tmpfs | 읽기 전용 루트의 보완. 컨테이너 종료 시 사라진다 |

**`--user`의 귀결: 컨테이너 안에 그 uid의 계정 항목이 없다** (2026-08-10 실측). 호스트 uid를 그대로 넣는데 기본 이미지(§8)의 `/etc/passwd`에는 그 번호의 사용자가 없다 — debian 계열은 1000번 사용자를 이미지에 만들지 않는다. 그래서 **사용자명을 passwd에서 조회하는 명령이 실패한다**: `whoami`가 `cannot find name for user ID 1000`으로 exit 1. 홈 탐색은 `HOME=/tmp`가 이미 정하므로 영향이 없고, 파일 소유권·권한은 이름이 아니라 번호로 판정되므로 워크스페이스 쓰기도 영향이 없다.

**고치지 않는다.** passwd 항목을 넣으려면 실행마다 호스트에 임시 파일을 만들어 `/etc/passwd`에 바인드 마운트해야 하는데, 읽기 전용 루트에 호스트 파일을 하나 더 붙이는 대가가 "이름 조회가 되는 것"보다 크다. env로도 못 고친다 — `whoami`는 `USER`·`LOGNAME`이 아니라 passwd를 읽으므로, 그 변수들을 전달하지 않는다는 위의 결정과 무관하게 결과가 같다. 이미지를 uid 1000이 있는 것으로 바꾸는 것도 답이 아니다: **호스트 uid는 사용자마다 다르므로** 1001인 사용자에게서 같은 문제가 재발한다.

실패는 크고 정확하다(exit 1 + 원인이 적힌 stderr) — `ARCHITECTURE.md` §2.6이 금지하는 조용한 실패가 아니다. 다만 **모델은 이것을 이상 징후로 읽었다**(2026-08-10 실측: *"일반적이지 않은 상황 … 사용자 정보가 시스템에 제대로 등록되지 않았거나"*). 그럼에도 **도구 설명에는 넣지 않는다** — 도구 설명은 매 API 호출에 실리고(§2.4·§2.5), 이 오독의 비용은 혼란스러운 한 문장이지 잘못된 행동이 아니다. 앞의 "`cd`·`export`가 남지 않는다"를 도구 설명에 넣은 것과 갈리는 지점은 **모델이 그것을 모르면 틀린 명령을 만든다**는 것이다. 여기엔 그런 후속 행동이 없다. **트리거**: 사용자명 조회 실패가 도구의 오작동으로 이어지는 사례가 실측되면 도구 설명 한 줄을 재검토한다.

### 워크스페이스는 호스트와 **같은 절대 경로**로 마운트한다

경로 번역 계층을 만들지 않기 위해서다. `WorkspaceBoundary`(`TOOLS-INTERFACE.md` §3)가 판정해 넘겨준 호스트 절대 경로를 그대로 `cwd`로 쓸 수 있고, 셸 출력에 찍힌 경로를 사용자가 호스트에서 그대로 열 수 있다. 번역 테이블이 생기면 그것이 또 하나의 판정기가 되고, **판정기가 둘이면 어긋난다**는 것은 이 프로젝트가 경로·SSRF 양쪽에서 이미 세운 규칙이다.

### 컨테이너 수명 — 명령 1회당 1개

- 명령마다 새 컨테이너를 만들고 끝나면 제거한다(`--rm`). **영속 셸 세션은 없다** — `TOOLS-INTERFACE.md` §6이 bash 영구 세션을 안 넣기로 이미 판정한 것과 일치한다.
- **귀결: `cd`·`export`·쉘 변수가 명령 간에 남지 않는다.** 이것은 샌드박스가 만든 제약이 아니라 원래 계약이지만, 컨테이너에서는 더 눈에 띈다. 도구 설명(모델이 읽는 텍스트)에 명시한다.
- **컨테이너 고아 방지가 계약이다.** timeout·abort 시 `docker run` 클라이언트 프로세스를 죽이는 것만으로는 **컨테이너가 계속 돌 수 있다.** executor는 컨테이너 자체의 종료를 보장해야 한다. `TOOLS-INTERFACE.md` §4의 세 계약(timeout 강제, abort 존중, 출력 유계)이 컨테이너 경계 **너머에서도** 성립하는지는 구현 플랜의 1급 검증 대상이다 — 호스트 실행에서 통과하던 테스트가 여기서 조용히 거짓이 되기 쉬운 지점이다.

  **종료 수단은 `docker kill`이고 실행 식별 라벨은 `neo-agent-run`이다** (2026-08-09 확정 — 조정 가능 세부). `docker stop`을 쓰지 않는 이유는 **기본 유예가 10초**라 timeout을 강제한 직후 `exec` 반환이 그만큼 더 늦어지기 때문이다 — 방금 강제한 상한의 실질을 정리 절차가 깎아먹는다. 호스트 실행자가 SIGTERM 후 유예를 주는 것과 갈리지만 근거가 다르다: 호스트 프로세스는 실제 자원을 쥐고 있을 수 있는 반면, 이 컨테이너는 `--network none`·읽기 전용 루트·명령 1회짜리이고 tmpfs는 어차피 사라진다 — 줄 만한 정리 기회가 없다. 라벨 키는 **실행 간 안정, 값은 실행마다 고유**여야 한다(고아 조회의 유일한 수단이며 `docker ps` 출력에 사용자 눈으로도 보인다). **정리 명령은 그 컨테이너를 지목한다** — `docker stop $(docker ps -q)` 류의 쓸어담기는 사용자의 무관한 컨테이너를 죽인다. **정리 자체에도 상한이 있다**: 정리가 매달리면 `exec`가 매달리고, 상위의 어떤 타임아웃도 그것을 잡지 못한다.
- **`docker` CLI 자신의 실패는 실행 실패로 승격한다** (2026-08-09 판정). `docker run`은 이미지 부재·데몬 오류에서 125로 끝나는데, 컨테이너 안 명령이 진짜 125로 끝날 수도 있어 **원리적으로 코드만으로는 구분되지 않는다.** 그럼에도 승격하는 쪽을 택하는 이유는 **오분류의 방향** 때문이다 — 진짜 125를 실행 실패로 보고하면 모델은 재시도하거나 사용자에게 묻는다(복구 가능). 반대로 docker의 실패를 명령의 실패로 흘리면 모델은 존재하지 않는 버그를 디버깅한다(복구 불가에 가깝다). §3이 이미 "세션 중 Docker가 죽으면 도구가 실행 실패로 보고하고 에러 텍스트에 Docker 부재를 명시한다"고 말한 것의 연장이다. **에러 텍스트에 이 양가성을 명시한다** — 구분이 원리적으로 불가능하다는 사실을 감추지 않는다. `exitCode: 0`으로 흘리는 것(조용한 성공)만은 어떤 경우에도 금지다.
- **명령 문자열은 인자로 싣는다** (`<image> sh -c "<command>"`). stdin 파이프는 `-i`가 필요하고 셸 선택이 이미지 내용과 얽히며 스트림이 하나 더 는다. 인자 노출(`ps`·`docker ps`)은 운영자 1명 맥락에서 무해하고, 그 명령은 어차피 방금 승인 화면에 표시된 것이다. **트리거**: 인자 길이 상한 충돌이 실측될 때 stdin 경로를 재검토한다.

### env는 화이트리스트다

`SAFE-DEFAULTS.md` §3 계약 3(자식 프로세스 env에서 시크릿 제거)이 **여기서 더 강해진다.** 호스트 실행에서는 상속된 env에서 시크릿을 빼는 denylist였지만, 컨테이너는 env가 비어서 시작하므로 **넣을 것만 넣는 화이트리스트**가 자연스럽다. denylist는 빠뜨리면 새고 화이트리스트는 빠뜨리면 불편할 뿐이다 — 오차의 방향이 다르다.

**전달 집합 (2026-08-09 확정 — 조정 가능 세부, T-013 실증 대상):**

| 변수 | 값 | 근거 |
|---|---|---|
| `HOME` | **`/tmp`** (고정) | 읽기 전용 루트에서 홈이 쓰기 불가면 많은 도구가 **조용히** 실패한다 — §2.6이 금지하는 방향이다. `/tmp`는 tmpfs라 쓰기 가능하고 컨테이너와 함께 사라진다. 워크스페이스를 홈으로 두지 않는 이유는 도구가 만드는 캐시·설정 파일이 사용자의 저장소를 오염시키기 때문이다 |
| `LANG` · `TERM` · `TZ` | 호스트 값 통과 | `TERM`이 없으면 일부 도구가 출력을 깨뜨린다. `LANGUAGE`·`LC_ALL`은 `LANG` 하나로 충분하다 |

**`PATH`는 전달하지 않는다.** 호스트 PATH는 컨테이너에 **존재하지 않는 디렉터리**를 가리키고, 이미지의 기본 PATH가 그 이미지에 맞는 값이다. (초판이 예시로 든 "`PATH`·`HOME`·`LANG` 류"에서 `PATH`를 뺀 정정이다 — 예시였지 계약이 아니었다.)

**`USER`·`LOGNAME`·`SHELL`·`PWD`도 전달하지 않는다** — uid는 `--user`가, cwd는 `-w`가 이미 정하고, 이 변수들은 호스트 사용자명을 컨테이너에 노출할 뿐이다.

**호스트 env를 필터링해 넘기는 구조를 쓰지 마라.** 그것은 이름을 아무리 잘 골라도 denylist이고, 이름 패턴에 안 걸리는 변수(`MY_NOTES`·`PROJECT_ROOT`)가 샌다. 넣을 이름을 코드가 나열해야 화이트리스트다.

### 이미지

- **고정 태그를 쓴다. `latest` 금지** — 같은 설정이 시점마다 다르게 동작하는 것은 `auto`를 기각한 것과 같은 이유로 기각한다.
  - **강제 지점은 CLI의 설정 검증 하나다**(시작 에러 — `CLI-INTERFACE.md` §3이 이미 그렇게 규정했다). **실행자는 겸하지 않는다** (2026-08-09 판정): 같은 규칙의 에러가 두 곳에서 나면 문면이 갈리고, 실행자 쪽은 도구 실행 시점에야 터져 사용자 경험이 더 나쁘다. 크리덴셜 denylist가 도구·게이트에 이중화된 것과 다른 점은 그쪽엔 "게이트가 꺼져 있어도 동작해야 한다"는 명시적 요구가 있었다는 것이다(`SAFE-DEFAULTS.md` §1 "승인으로도 불가") — 여기엔 그런 요구가 없고, 실행자의 호출자는 CLI 하나다. **트리거**: 두 번째 호스트(웹 UI 등)가 생겨 실행자를 직접 조립하게 되면 검증이 함께 옮겨가거나 실행자로 내려와야 한다.
- 이미지에 무엇이 들어 있는지(git·node·python 유무)는 사용성을 좌우하지만 보안 계약이 아니다 — 기본 이미지 선정은 §8.
- **이미지가 없을 때의 시작 안내는 이 절의 계약이 아니다 — §8의 미결이다** (2026-08-12 정정). 초판은 여기에(`eed6dc8^`) *"이미지가 없으면 시작 시 안내한다"*를 평서형으로 적었으나, 같은 날(2026-08-09) §8이 실측을 근거로 **이 문서의 계약이 아니라고 판정**하면서 두 절이 정반대를 말하게 됐다. 뒤에 온 판정이 근거를 가졌으므로 그쪽을 따르고 여기서는 문장을 거둔다. **지금 강제되는 것은 태그 형식뿐이다** — CLI 설정 검증이 `latest`·태그 부재·빈 다이제스트를 시작 에러로 막고(위 항목), **이미지의 존재 여부는 기동의 어느 자리에서도 강제되지 않는다.**
  - **2026-09-06 정정 — 실재를 보는 자리 자체는 생겼다.** §3이 이미지 실재 프로브의 계약을 세웠고, 그전까지 이 자리는 실재 판정의 **부재**를 현재형으로 적고 있었고, 그 서술은 프로브가 서는 순간 거짓이 된다. **그럼에도 위 문장의 실질은 그대로다**: 그 프로브는 **기동 밖**이고 소비자가 `neo-agent doctor` 하나이므로(`CLI-INTERFACE.md` §5.1), 이 불릿이 2026-08-12에 거둔 시작 안내 계약은 되살아나지 않는다. 강제 지점은 여전히 태그 형식 하나다.
- 다만 이 사실은 계약이다: **`docker pull`은 호스트가 한다.** 그래서 `--network none`(컨테이너 네트워크)과 무관하며, 이미지 수급이 안 되는 원인을 컨테이너 네트워크 차단에서 찾으면 틀린다.

## 5. `network: "none"`의 귀결 — 정직하게

**기본 상태에서 `npm install`·`git push`·`apt-get`·`curl`이 셸에서 동작하지 않는다.** 이것은 부작용이 아니라 설계 목적이다(`WEB-ACCESS.md` §1 — 웹 경로를 감사된 문 하나로 수렴).

- 사용자는 이 비용을 인지하고 이 기본값을 선택했다(2026-08-08 결정).
- **끄는 경로는 명시적이고 가시적이다** — 설정으로 샌드박스를 `off`(호스트 실행)로 두거나, 네트워크가 필요한 작업을 사용자가 호스트 터미널에서 직접 한다. 후자가 개인 사용 맥락에서 가장 흔한 해법일 것이다.
- **`sandbox: "off"`로 도는 동안 그 사실을 매 기동 표시한다 — 표시 의무가 계약이고 문구는 재량이다** (2026-08-09 명문화 — QA-C C-10). "가시적"이 "설정 파일에 적혀 있다"라면 그것은 가시성이 아니다: 사용자가 config를 다시 열어야 알 수 있고, 한 번 끈 뒤 잊은 채로 도는 것이 정확히 이 계약이 막으려는 상태다. `off`는 **이 프로젝트의 유일한 OS 경계를 끄는 설정**이므로 끈 채로 도는 내내 보여야 한다.
- **컨테이너 네트워크만 선택적으로 켜는 설정은 만들지 않는다.** 그것이 있으면 "잠깐만 켜자"가 기본이 되고 §1의 수렴이 무너진다. 필요하면 샌드박스 자체를 끄게 해서 **무엇을 포기하는지 보이게** 한다.
- 이 귀결은 `TOOLS-INTERFACE.md` §2의 `source: "local"` 고정을 참으로 만든다(`WEB-ACCESS.md` §1).

## 6. 대상은 셸뿐이다 — 파일 도구는 호스트에 남는다

OpenClaw는 `read`·`write`·`edit`·`apply_patch`까지 샌드박스에 넣는다. 우리는 넣지 않는다.

- 파일 도구는 in-process `node:fs` 호출이다. 컨테이너에 넣으려면 파일 연산용 executor 추상을 새로 만들어야 하고, 그것은 `TOOLS-INTERFACE.md` §3이 확정한 **`WorkspaceBoundary`가 경로 판정의 유일한 소유자**라는 구조를 다시 여는 일이다. 셸 executor 교체는 약속돼 있었지만(🧬) 파일 executor는 약속된 적이 없다.
- 파일 도구는 이미 워크스페이스 봉쇄 + 크리덴셜 denylist + 승인 게이트 아래 있다. 셸이 더 위험한 이유는 **경로 판정이 정적으로 불가능**하기 때문이고(`TOOLS-INTERFACE.md` §3 말미 — 셸 명령 문자열에서 크리덴셜 접근을 전부 잡을 수 없다), 그래서 셸이 격리 대상이다.
- **재도입 트리거**: 파일 도구 경유의 실제 사고나, 워크스페이스 밖 쓰기를 자동 허용하고 싶어지는 요구가 생길 때.

> **이 격리에는 소비자가 하나 더 있다** (2026-09-02 추가 — 계약 변경 아님 · `K-427`). `MEMORY.md` §2.1이 메모리를 `~/.neo-agent/memory/`에 두어 얻는 격리는 **파일 도구 3종에 대해서만** 크리덴셜 denylist가 만들고, **셸에 대해서는 이 문서가 만든다** — 기본 구성에서 `~/.neo-agent/`는 컨테이너 안에 아예 없기 때문이다(§4 — 마운트는 워크스페이스 루트뿐, 루트 읽기 전용, `HOME=/tmp`). 위 불릿이 셸을 격리 대상으로 고른 근거(*"경로 판정이 정적으로 불가능하다"*)가 메모리 경로에도 그대로 적용된다는 뜻이고, 그래서 `MEMORY.md`는 셸용 경로 denylist를 따로 두지 않는다.
>
> **귀결 — 마운트 집합이나 조건부 노출을 넓히면 메모리 격리가 함께 얇아진다.** 홈 아래를 컨테이너에 마운트하거나 Docker 불가용에서 호스트 실행으로 자동 폴백하는 변경은(§3이 `auto`를 기각한 자리) 셸에게 메모리 파일을 여는 일이며, 그 순간 `MEMORY.md` §6 예산·§4.3 중복 판정·§5 오염 거부가 우회된다. **소비자가 둘이므로 그런 변경은 두 문서의 동시 개정을 요구한다.** 오늘 열려 있는 갈래는 명시적 `sandbox: "off"` 하나이고, 그 상태는 시작 시퀀스 5b가 경고로 알린다.

## 8. 미결 — 이 문서가 정하지 않은 것

- ~~**기본 이미지**~~ — **2026-08-09 실측 확정: `debian:bookworm-slim`.** 후보 4종(`debian:bookworm-slim` 28.2MB · `ubuntu:24.04` 29.8MB · `alpine:3.22` 3.8MB · `busybox:1.37` 2.2MB)을 `--network none` 컨테이너 안에서 프로브했다. **셸·기본 유틸의 유무로는 갈리지 않는다** — `sh`·`ls`/`cat`·`grep`·`sed`·`awk`·`find`가 4종 모두에 있고, `python3`·`git`은 **4종 모두에 없다**(필요해지면 이미지 선택이 아니라 자체 이미지 빌드 문제다). **실제로 갈리는 축은 `bash` 하나**이고 alpine·busybox는 BusyBox 계열이라 GNU 유틸의 옵션 호환도 좁다 — 모델이 내는 셸 명령은 GNU 관용구를 쓸 가능성이 높으므로 그 차이가 26MB보다 비싸다. **크기 이점이 기동 지연으로 회수되지 않는다**는 것이 결정적이다(아래 항목). `ubuntu:24.04`는 1.5MB 더 크고 얻는 것이 없다.

  **`HOME=/tmp`(§4)가 4종 전부에서 쓰기 가능함을 실증했다** — `--read-only` + `--tmpfs /tmp` 조합이 의도대로 동작한다. 워크스페이스(cwd) 쓰기도 4종 전부 성공.
- ~~**자원 수치**~~ — **2026-08-09 실측 확정: 메모리 `1g` · pids `256` 유지.** 둘 다 의도대로 동작함을 확인했고 바꿀 근거가 나오지 않았다. 계약은 여전히 "유계"이고 이 수치는 조정 가능하다.
  - **`--pids-limit`**: 사용 가능한 자식은 정확히 `limit - 1`이다(셸 자신이 1개를 쓴다 — 256 → 255개에서 `Cannot fork`, 16 → 15개). fork 폭주 시 컨테이너 안 셸이 exit 2로 죽고 **호스트 프로세스 수는 불변**이었다.
  - **`--memory` + `--memory-swap`**: `32m` 상한에서 tmpfs 200MB 쓰기와 익명 100MB 버퍼가 모두 **exit 137(OOM kill)**, 16MB 버퍼는 통과, 기본 `1g` 대조군은 둘 다 통과. **tmpfs 페이지가 컨테이너 메모리 cgroup에 잡힌다**는 것이 확인됐으므로 §4의 `--tmpfs`에 별도 크기 상한을 주지 않은 판단이 유지된다 — 상한이 둘이 되면 작은 쪽이 조용한 실패를 만든다.

  > **2026-08-12 정정 — 이 항목은 세 값을 묶고 있었고 실측은 둘만 다뤘다.** 초판 문면은(`f47b0f3^`) *"**자원 수치** — 메모리·pids·기동 타임아웃 상한"*이었는데 2026-08-09 실측은 앞의 둘만 재고 항목 전체를 닫았다. 셋째는 측정되지도, 확정되지도, 미결로 남겨지지도 않은 채 취소선 안으로 사라졌다 — **열려 있는 물음을 닫힌 것으로 보이게 하는** 형태의 부정확이고, 취소선 아래는 아무도 다시 묻지 않으므로 그냥 사라졌을 것이다. 원인은 **묶음 자체가 잘못**이었다는 것이다: 메모리·pids는 재야 답이 나오는 경험적 성질이지만 판정 상한은 오차 방향의 선택이라 실측 대상이 아니다. **셋째는 2026-08-12에 §3에서 확정했다**(30초 · 근거는 §3). 여기서 되풀이하지 않는다.
- ~~**컨테이너 기동 지연의 실사용 영향**~~ — **2026-08-09 실측. §7의 영속 컨테이너 트리거는 발동하지 않는다.** 명령 1회당 컨테이너 1개로 `echo`를 돌려 **median 205~213ms**(min 176 / max 230), 호스트 bash 직접 실행의 median 3.6ms 대비 ~55배지만 **차이의 절대량이 0.2초**다. **이미지 크기(2.2MB~29.8MB)는 지연에 사실상 영향이 없다** — 로컬에 받아 둔 뒤에는 컨테이너 생성 오버헤드가 지배한다. 영속 컨테이너를 도입하면 생애주기·상태 누출·고아 관리가 전부 새로 생기는데 얻는 것이 명령당 0.2초다.

  **다만 실측이 다른 것을 지목했다 — 문제는 지연이 아니라 첫 실행의 `docker pull`이다.** 이미지가 없으면 `docker run`이 자동으로 받는데 그것이 셸 명령의 timeout 안에서 소모되어, 사용자에게는 **첫 명령이 이유 없이 timeout으로 실패하는 것**으로 보인다. 이미지 부재 시 시작 안내는 이 문서의 계약이 아니고 넣으려면 기동 시 docker 접촉이 하나 더 는다 — 미결로 남긴다(아래).
- **이미지 부재 시 시작 안내** — 위 항목이 새로 연 미결. 기동 시 docker 접촉을 늘리는 안내와, 접촉을 늘리지 않고 **timeout으로 끝난 실행의 stderr에 pull 진행 흔적이 있으면 그 사실을 결과에 싣는** 안이 있다. 후자가 새 docker 접촉 0이다. 트리거: 첫 실행 실패가 실사용에서 관측될 때.

  **2026-09-06 — `doctor`의 `sandbox-image` 축은 이 미결의 무엇을 닫고 무엇을 안 닫는가.** 닫은 것은 하나다: **이미지 실재를 볼 수단이 아예 없다**는 상태가 끝났다 — §3이 그 프로브의 계약을 세웠고 `CLI-INTERFACE.md` §5.1의 축이 그것을 부른다. **안 닫은 것이 이 미결 자체다**: 그 축은 사용자가 `neo-agent doctor`를 쳤을 때만 돌고, 기동은 여전히 이미지 부재를 첫 셸 명령의 timeout으로 만난다. **기동 시 docker 접촉을 늘릴 것인가는 아직 판정하지 않았으므로 위 트리거는 그대로 살아 있다** — 수단이 생긴 것과 기동이 그것을 부르는 것은 다른 결정이다.

  **이 항목이 §4의 계약 문장과 충돌하고 있었다 — 2026-08-12에 §4 쪽을 거뒀다.** §4가 초판부터(`eed6dc8^`) *"이미지가 없으면 시작 시 안내한다"*를 평서형으로 갖고 있었고, 이 미결이 같은 날 늦게 추가되면서 **한 문서가 정반대를 말하는 상태**가 3일간 이어졌다. 실물 확인 결과 그 계약 문장은 **구현도, 미규정 마커도, 하류 정본(`CLI-INTERFACE.md`)도 없었다** — 재는 것이 아무것도 없는 계약은 게이트의 그린을 이행으로 오독하게 만든다. 근거를 가진 뒤쪽 판정(이 항목)을 남기고 §4의 문장을 거둔 이유다. **이미지 존재 여부를 판정하는 코드는 이 판정 시점(2026-08-12)에 어디에도 없었다**(CLI 설정 검증은 태그 **형식**만 본다). **2026-09-06에 그 상태가 끝났다** — §3이 이미지 실재 프로브의 계약을 세웠고 소비자는 `doctor` 하나다. **위 판정은 그대로 선다**: §4의 계약 문장을 거둔 근거는 그 문장이 재는 것을 아무것도 갖지 않았다는 것이었고, 새로 생긴 자리는 **기동 밖**이라 그 문장을 되살리지 않는다.
- **rootless Docker / Podman 환경에서의 uid 매핑** — §4의 `--user` 호스트 uid 전달이 rootless 구성에서 어떻게 동작하는지 미검증.
- **Docker 부재 시 조건부 노출의 사용자 경험** — 셸 없는 에이전트가 실제로 쓸 만한지(파일 도구 + web_fetch만). 안내 문구는 `CLI-INTERFACE.md`가 정본이 된다.
