## 1. 경계 — 패키지와 의존성

- 패키지 위치: `packages/cli`. bin 이름: `neo-agent`.
- **의존성 예산: 워크스페이스 9패키지(`core`·`providers`·`tools`·`gate`·`store`·`compaction`·`web`·`sandbox`·`memory`) 정확히, 외부 런타임 의존성 0.**
  > 2026-08-09 개정 (2차) — `memory` 추가(`MEMORY.md` §4.4). 1차 개정에서 `web`·`sandbox`를 추가했다(`WEB-ACCESS.md` §2·`SANDBOX.md` §2). 그 전 이 줄은 "5패키지"였으나 `compaction`은 2026-08-06 압축 구현에서 이미 배선됐고 이 문장만 갱신되지 않았던 것이다(실측으로 확인 — 예산 게이트의 `cli` 항목이 6개였다). **수치의 정본은 `scripts/check-core-budget.mjs`이고 이 문장은 그것을 서술한다** — 두 번 어긋난 자리이므로 수치를 여기서 세지 말고 스크립트를 본다.
  >
  > 패키지가 늘어도 CLI의 성격은 그대로다: 둘 다 **호스트의 배선 한 곳에서만** 결합하고, CLI 자신은 여전히 네트워크·프로세스 스폰을 직접 하지 않는다(아래 금지 모듈 무변경 — 네트워크는 `web`, 컨테이너 실행은 `sandbox`의 본업이다). 렌더링은 `node:readline` + ANSI 이스케이프 직접 제어로 한다(2026-08-06 사용자 확정). TUI 라이브러리(Ink·pi-tui류)는 넣지 않는다 — 네이티브 의존성 0·빌드 스텝 0 원칙(TECH-STACK)과 정합. ~~**재검토 트리거**: 리치 TUI 요구(패널 분할·마우스 등)가 실측될 때.~~ → **2026-08-20 발동·판정: 프레임워크는 여전히 넣지 않는다**(§7.1·§11). 이 줄의 결론은 그대로이나 **트리거 문면이 부정확했으므로 여기 남긴다** — 예시가 "패널 분할·마우스 등"이었는데 실측된 요구는 그 둘이 아니라 **Claude Code류 렌더링에 대한 친숙성**이었다. 예시를 발동 조건으로 읽으면 정당한 요구가 영원히 트리거를 못 밟고, 넓게 읽으면 예시가 무의미해진다. **다음에 이 자리에 트리거를 쓸 때는 예시가 아니라 판정 기준을 쓴다.**
- **금지 모듈**: `node:net`·`node:tls`·`node:http`·`node:https`·`node:child_process`·`node:sqlite` 임포트 금지 — 네트워크는 providers(SDK 경유), 프로세스 스폰은 tools(executor), DB는 store의 본업이다. CLI가 직접 하기 시작하면 경계가 샌다. 예산 게이트로 검사한다. `node:fs`·`node:os`·`node:path`·`node:readline`·`node:tty`는 허용(본업 — 설정·크리덴셜·allowlist 파일과 터미널). **허용 목록은 닫힌 목록이다** (2026-08-11 확정 — 경계 기계화 QA 판정 ②): 여기 열거되지 않은 내장은 무해해 보여도(`node:crypto`·`node:util`·`node:url` 등) 목록 밖이면 쓰지 않으며, 쓰려면 이 절의 개정이 선행한다. 미규정 내장을 열어 두면 `node:dns`처럼 이 절이 막으려는 결과(네트워크 직결)를 그대로 얻는다 — 폐쇄는 경계 테스트(축 3)가 허용 5종 부분집합 단언으로 기계화하고, 목록을 늘리는 커밋은 그 단언과 이 문장을 함께 고치게 된다.
- **CLI는 유일한 조립 지점(composition root)이다.** 코어·도구·게이트·저장소는 서로를 모른다는 기존 계약들(`CORE-INTERFACE.md` §1, `TOOLS-INTERFACE.md` §1, `APPROVAL-GATE.md` §1, `SESSION-STORE.md` §1)은 전부 "결합은 호스트의 배선 한 곳"을 전제한다 — 그 한 곳이 여기다.
- **조립의 생성자 주입점(`WiringFactories`)은 테스트 표면으로 유지되는 계약이다** (2026-08-06 T-012 명문화). 배선의 계약(누가 같은 인스턴스를 공유하는가, 무엇이 어떤 순서로 불리는가)은 결과물만 봐서는 검증되지 않는다 — 이 주입점이 없으면 QA의 배선 contract 테스트가 성립하지 않으므로, "테스트 전용 표면"으로 보고 지우면 안 된다.
- **`src/index.ts`(배럴)는 런타임 경로가 아니라 패키지 밖 조립·관측 표면이다** (2026-08-11 확정 — W-4/I-2 해소). **bin은 배럴을 지나지 않는다**: `main.ts`가 `./wiring.ts`를 직접 동적 import하는데, 이는 `node:sqlite` 경고 필터가 store 로드보다 먼저 설치돼야 한다는 제약의 귀결이다(`DISTRIBUTION.md` §3.2 · §12). 그래서 배럴이 정하는 것은 *무엇이 실행되는가*가 아니라 **이 패키지가 무엇으로 이루어져 있는가**이고, 나머지 9패키지의 배럴과 같은 지위다 — 다만 CLI는 조립 지점이라 그 위에 호스트가 없고, 그래서 이 배럴의 소비자는 오늘 이 패키지 안의 테스트뿐이다.
  > 2026-08-11 개정 (2차) — 이 자리에 있던(`1325cf0^`) *"오늘의 소비자는 통합 테스트 하네스 하나다"*를 수를 뺀 서술로 바꾼다. 1차 개정(같은 날)이 대응 테스트를 붙이면서 소비자를 둘로 만들어 그 수를 스스로 늙게 했고, §1 기계화가 셋으로 만들었다. **계약 절 안에 수를 적으면 그 절을 검증하는 작업이 그 수를 늙게 만든다** — W-4가 5일간 거짓인 채 남아 있던 것과 같은 양태다. 수가 필요하면 세는 것은 코드이지 문서가 아니다(§1의 *"수치의 정본은 `scripts/check-core-budget.mjs`이고"* 서술과 같은 원리).
  - **소속 기준은 "모듈의 의도된 표면"이지 "현재 소비자 수"가 아니다.** 모듈이 밖에 내놓을 생각이 없는 것(내부 헬퍼·중간 상수)은 올리지 않고, 그 모듈이 무엇을 하는 곳인지 드러내는 표면은 지금 아무도 임포트하지 않아도 올린다. 소비자 수를 기준으로 삼으면 배럴이 테스트 편성에 따라 흔들리고, 심볼마다 *"이건 왜 있고 저건 왜 없나"*를 개별 판정하게 된다 — 그 개별 판정이 정확히 W-4가 5일간 거짓인 채 남아 있던 원인이다(§6).
  - **이 기준은 보호 장치가 아니다.** 패키지는 `private: true`이고 semver 소비자가 없으므로 배럴이 좁아야 지켜지는 것은 없다. 실제 보호는 의존성 예산 게이트(`scripts/check-core-budget.mjs`)와 금지 모듈 목록이 하고, 배럴은 계약 절과 코드 모듈을 잇는 지도 역할을 한다(각 export 줄의 `// §n` 주석이 그 실체다). **재검토 트리거**: 이 패키지 **밖**에 실사용 소비자가 생겨(웹 UI 호스트 등) 배럴이 하위호환 계약이 될 때 — 그때는 기준이 "모듈의 의도"에서 "그 소비자가 필요로 하는 것"으로 바뀐다.

## 2. 프로세스 모델 — 시작·종료 시퀀스

**단일 프로세스, 상주 데몬 없음**(REUSE-MAP §4 기판정 — Gateway+RPC는 웹 UI 시점에 재론). 터미널 하나 = 프로세스 하나 = 활성 세션 하나. 같은 세션을 두 프로세스가 여는 것은 막지 않는다(`SESSION-STORE.md` §9 그대로).

> **2026-08-19 — 재론 시점이 왔고 상주 금지 항이 좁혀졌다.** 위 문장이 예고한 그 재론이다. **`neo-agent serve`로 기동할 때만 상주한다** — 그 외 경로에서는 이 절이 그대로다. 좁힌 것은 상주 금지 하나뿐이고 **단일 프로세스는 유지된다**: `serve`는 포그라운드로 돌며 스스로 데몬화하지 않고 fork·detach·pidfile을 만들지 않는다. 수명 관리는 프로세스 밖(systemd·tmux)의 일이다. 정본은 `WEB-UI.md` §3이고 그 문서가 기동 시퀀스에 **서버 바인드** 단계를 뒤에 더한다 — 저장소 구독보다 뒤여야 하는 이유가 이 절의 렌더러 순서와 같다. `serve`에서는 TTY 부재 거부(`DISTRIBUTION.md` §7)도 걸리지 않는다: 그 판정의 근거가 승인자 부재였는데 여기서는 승인자가 브라우저다.

**시작 시퀀스** (이 순서가 계약이다 — 뒤 단계는 앞 단계의 동결·검증을 전제한다):

```
1. 설정 로드 + 동결          — config.json 1회 읽기 (§3, SAFE-DEFAULTS §4)
2. 크리덴셜 로드             — fail-closed 검사 (§4)
3. 워크스페이스 경계 생성     — cwd의 realpath로 WorkspaceBoundary 생성 (TOOLS-INTERFACE §3)
3b. 메모리 로드              — ~/.neo-agent/memory/MEMORY.md 1회 읽기 → 프로즌 스냅샷
                              (MEMORY.md §2.2·§3.1). 읽기 실패는 기동 실패
4. 저장소 열기               — sessions.db. 권한·WAL 경고 핸들러 주입 (SESSION-STORE §7)
5. 세션 생성 또는 재개        — §6
5b. executor 선택            — sandbox 설정 + Docker 가용성 판정 (SANDBOX.md §3).
                              on+가용 → DockerShellExecutor / off → HostShellExecutor /
                              on+불가용 → 셸 도구를 등록하지 않고 두 갈래를 안내
6. Agent 생성                — 도구 등록 + 게이트를 beforeToolCall에 배선.
                              executor에는 로드된 시크릿 값 목록을 전달 (env 스크러빙 대상)
7. 구독 배선                 — store.attach가 먼저, 렌더러가 나중 (SESSION-STORE §4:
                              "사용자가 화면에서 본 것은 이미 저장된 것").
                              afterToolCall → gate.noteToolResult,
                              agent_start → gate.resetTaint (APPROVAL-GATE §4 오염 추적)
8. REPL 진입
```

- **이 열거는 상태 전이 단계만 담는다** (2026-08-12 추가 — F-1 해소). 여기 오르는 것은 **다음 단계의 전제를 만드는 것**이다: 무언가를 동결하거나(1), 검증하거나(2), 자원을 열거나(4), 객체를 조립한다(6). 그래서 각 항목에 "뒤 단계는 앞 단계를 전제한다"는 위 계약이 걸린다.
  - **고지·경고는 이 목록에 오르지 않는다.** 아무것도 동결하지 않고 아무것도 열지 않으므로 뒤 단계가 그것을 전제하지 않고, 따라서 순서 계약의 대상이 아니다. 고지는 **자기 관심사가 준비되는 단계에 붙어** 나가며, 정본도 이 절이 아니라 각자의 문서다. §2가 이미 그렇게 하고 있다 — 저장소 권한·WAL 경고는 4에 붙고(`SESSION-STORE.md` §7), 셸 판정의 두 갈래 안내는 5b에 붙으며(`SANDBOX.md` §3), 미지 모델의 컨텍스트 창 경고는 6의 조립 중에 나가지만 **열거에는 아예 없다**(`PROVIDERS.md` §3).
  - **`3a`(설치 트리 자기 편집 고지)가 그 예다.** 정본은 `DISTRIBUTION.md` §6이고 그 계약은 충족된다. 구현이 주석에 `3a`라는 번호를 달고 있는 것은 **코드 안의 위치 표시**이지 이 열거의 항목이 아니다 — 고지가 3과 3b 사이에서 나간다는 사실을 코드에서 읽기 쉽게 한 것뿐이다.
  - **왜 목록에 넣지 않는가.** 넣기 시작하면 고지가 하나 늘 때마다 이 열거가 다시 낡고, 그때마다 §2를 고쳐야 한다. 편입 **기준**을 정하는 것은 한 번으로 닫힌다 — 이 절이 §1의 두 자리에서 겪은 *"계약 절 안의 서술이 그 절을 검증하는 작업 때문에 늙는다"*와 같은 형태를 미리 막는다.
- **3b가 4보다 앞인 것이 계약이다** (2026-08-09 추가 — `MEMORY.md` §3.2). 시스템 프롬프트가 스냅샷을 **인자로 필요로 하므로** 프롬프트 조립 전에 로드가 끝나야 하고, 프롬프트는 세션 생성(5)·Agent 생성(6)에 함께 흘러간다. 저장소(4)보다 **앞**인 것은 이득이 있어서다 — 메모리 로드 실패는 기동 실패인데(`MEMORY.md` §2.2: 읽기 실패 ≠ 빈 메모리, 빈 것으로 읽고 첫 쓰기에서 덮으면 메모리가 조용히 소실된다), 이 시점엔 아직 연 자원이 없어 **정리할 것 없이 종료**할 수 있다. 3b의 실패도 §2 말미의 "원인과 다음 행동을 담은 에러로 종료"에 해당한다.
- **5b가 6보다 앞인 것이 계약이다** — 도구 목록은 `new Agent()` 시점에 동결되므로(§2.4 프롬프트 캐시) 등록 여부 판정이 그 전에 끝나야 한다. **세션 중 Docker가 죽어도 도구 목록은 바뀌지 않는다**(그때는 실행 실패로 보고). 이 귀결의 근거는 `SANDBOX.md` §3.
- 도구 수는 구성에 따라 다르다: 파일 3종 + `web_fetch` + `remember`는 항상, `shell`은 5b 판정에 따라 (`remember`는 2026-08-09 추가 — `MEMORY.md` §4.4, 도구 목록 **말미**). 등록되는 도구 집합이 시작 화면에 보여야 한다(§2.6 — 숨겨진 도구가 조용히 빠지면 사용자는 왜 안 되는지 모른다). **이 요구는 2026-08-09 구현에서 실체를 갖는다** — 그 전까지 도구는 항상 4종 고정이라 표시할 변동이 없었다. 도구 등록 **순서는 고정**이다(프롬프트 캐시 바이트 안정성 — `ARCHITECTURE.md` 불변 조건 6): `shell`이 빠져도 남은 도구의 순서는 변하지 않는다.

- 배선 시 `AnthropicClientConfig.fetch`는 채우지 않는다(2026-08-06 기결정 — SSRF·프록시 우회 표면).
- **종료 시퀀스**: `waitForIdle()` → **인플라이트 압축 대기** → `store.close()` → 세션 id와 재개 방법(`neo-agent --resume <id 앞부분>`)을 표시하고 종료한다. 종료가 대화의 끝이 아니라 중단임을 화면에 남기는 것이 목적이다(§2.6 가시성).
  > 2026-08-12 개정 — 압축 대기를 명시한다. **`waitForIdle()`이 이 대기를 대신하지 않는다**는 것이 개정의 전부다: 자동 압축은 `agent.prompt()`가 resolve된 뒤에 불리므로(판정 E-45의 의도된 배치) 압축이 도는 동안 agent는 이미 idle이고, 기다리지 않으면 `store.close()`가 `branchSession`보다 먼저 간다. 압축 컨트롤러는 자기 실패를 삼키므로(`COMPACTION.md` §7 — 던지면 REPL이 "런 실패"로 표시해 실패의 출처가 어긋난다) 그 결과는 **요약의 조용한 소실**이고, §2.6 심각도 순서에서 가장 나쁜 쪽이다. **어긋남은 실측으로 확인됐다** — 이 줄이 `waitForIdle → store.close`였던 동안(`0bb0416^`) §8 `compacting` 행("압축을 기다린 뒤 끝낸다")은 거짓이었다. 두 절이 각자 옳은데 맞물리는 자리에서 갈라진 형태이므로, 한쪽만 읽고 판단하지 않게 §8 표에서 여기를 가리킨다.
  - **마지막 항목은 REPL이 입력 라인을 놓은 뒤에 나간다** (2026-08-20 추가 — K-024 해소). 세션 id와 재개 방법의 표시가 **터미널 반납 뒤**라는 것이 계약이고, 근거는 표시 수단이다: REPL이 열려 있는 동안의 출력은 입력 라인을 걷어냈다 다시 그리는 것을 감싸므로(§7 — 타이핑 중인 입력은 출력에 의해 유실되지 않는다), 반납 전에 인사를 내면 걷어내기에 지워지거나 인사 아래에 죽은 프롬프트 행이 남는다. 둘 다 §2.6 가시성이 금하는 결과이고, 그래서 이 순서는 §12가 위임한 표시 세부(색·프롬프트 문자·표시 범위)가 아니라 계약이다. **반납 자체를 이 열거에 올리지는 않는다** — 열거가 담는 것은 무엇이 언제 나가는가이고, 그것을 이행하는 수단은 코드 쪽 주석이 든다.
- 시작 단계의 실패(크리덴셜 권한, 저장소 손상, 워크스페이스 불일치)는 **원인과 다음 행동을 담은 에러로 종료**한다 — 부분 기동 상태를 만들지 않는다.

## 3. 설정 파일 — `~/.neo-agent/config.json`

동작 설정 전용 파일이다. **시크릿을 두지 않는다**(SAFE-DEFAULTS §3 — hermes 규율). 파일이 없으면 전부 기본값으로 동작한다 — "안 만진 상태가 가장 안전"(§2.3)의 이행.

| 키 | 타입 | 기본값 | 소비처 |
|---|---|---|---|
| `approvalMode` | `"manual" \| "off"` | `"manual"` | 게이트 (SAFE-DEFAULTS §1) |
| `denyRules` | `string[]` | `[]` | 게이트 2계층 |
| `model` | `string` | 구현 시 확정 (기본값 존재가 계약) | providers 어댑터 |
| `compactionAuto` | `boolean` | `true` | 압축 자동 트리거 (`COMPACTION.md` §3) — 2026-08-06 개정·구현 완료 |
| `compactionThreshold` | `number` | `0.75` | 압축 임계 비율. 유효 구간 `0 < t <= 1` — 벗어나면 시작 에러 (E-42 판정: 트리거가 영원히 안 걸리는 값의 침묵 수리는 침묵 실패다) |
| `compactionKeepRecentTurns` | `number` | `2` | 압축 시 원문 유지 user 턴 수. 1 이상의 정수 — 벗어나면 시작 에러 (E-43 판정: 0은 압축이 아니라 대화 초기화이고 그 의도는 `/new`가 표현한다) |
| `sandbox` | `"on" \| "off"` | **`"on"`** | 셸 격리 (`SANDBOX.md` §3). `"off"`는 명시적 호스트 실행 옵트아웃 |
| `sandboxImage` | `string` | 구현 시 확정 (기본값 존재가 계약) | 컨테이너 이미지. **고정 태그 필수 — `latest`는 시작 에러** (`SANDBOX.md` §4: 같은 설정이 시점마다 다르게 동작하는 것은 `auto` 기각과 같은 이유로 기각) |

**메모리에는 설정 키가 없다** (2026-08-09 — `MEMORY.md` §9 M-2 확정). 메모리 디렉터리는 `~/.neo-agent/memory/` **고정**이며 config로 바꿀 수 없다. 문자 상한(§6)도 코드 상수다. 열지 않는 이유는 웹과 다르다 — 웹은 "완화 설정 표면을 만들지 않으면 약화 경로도 없다"였고, 메모리는 **경로가 곧 격리**이기 때문이다(`MEMORY.md` §2.1: `~/.neo-agent/` 아래라서 크리덴셜 denylist가 파일 도구를 전부 막고, 그래서 `remember`가 유일한 문이 된다). 이 키를 열면 사용자가 워크스페이스를 가리킬 수 있고, 그 순간 `write_file` 한 번으로 예산·표시·오염 정책이 전부 우회된다 — **설정 하나가 설계 전체를 무효화하는 경로**다. **재검토 트리거**: 워크스페이스별 메모리 요구가 실측될 때(`MEMORY.md` §9 M-3). 그때도 답은 "임의 경로를 여는 키"가 아니라 격리를 유지하는 별도 설계다.

**웹 도구와 SSRF에는 설정 키가 없다** (2026-08-08). `WEB-ACCESS.md` §4의 판정 결과다 — 완화 설정 표면을 만들지 않으면 약화 경로도 없다. 차단 대역·스킴 제한·홉 상한은 전부 코드 상수이며 config로 만질 수 없다.

- **미지의 키는 시작 시 에러다.** 오타 난 보안 키(`approvalmode` 등)가 조용히 무시되고 기본값으로 도는 것은 침묵 실패다(§2.6). `agentMessageSchema`의 strictObject(SESSION-STORE §2)와 같은 방향.
- 포맷은 JSON(`JSON.parse` 내장, 파서 의존성 0). 파싱 실패도 시작 시 에러.
- 전 키는 시작 시 1회 읽고 동결한다(SAFE-DEFAULTS §4). 세션 중 변경의 적용 시점은 다음 프로세스 시작이다. **동결은 깊은 동결이다** (2026-08-06 T-012 명문화 — QA 독해 지지): `denyRules` 배열이 열려 있으면 `config.denyRules.length = 0` 한 줄로 게이트 2계층이 사라져 "실행 중 게이트를 약화시킬 수 없다"(SAFE-DEFAULTS §4)가 성립하지 않는다.
- 시스템 프롬프트는 CLI 내장 상수다. config 오버라이드는 MVP에 없다 — **트리거**: 커스텀 페르소나 요구 실측(그때 재개 검증 §6의 경고 경로가 이미 있다).

## 4. 크리덴셜 로더 (SAFE-DEFAULTS §3 보호 계약의 구현 소재)

`packages/cli` 내부 모듈이다. 별도 패키지는 과설계(시크릿 1개, 소비 지점 1곳).

**로드 우선순위** (2026-08-06 사용자 확정 — dotenv형 + env 우선):

```
1. 프로세스 env의 ANTHROPIC_API_KEY   — 있으면 파일을 읽지 않는다
2. ~/.neo-agent/credentials           — dotenv형 (KEY=value, # 주석 허용)
```

- env 우선의 근거: 파일 생성 없는 일회 실행(라이브 스모크 전례·CI)이 가능해야 하고, env는 명시적 제공이라 "조용히 다른 키를 쓰는" 경로가 아니다.
- **보호 계약 4개의 이행 지점 분배** (계약 자체는 SAFE-DEFAULTS §3이 정본):
  1. **600 fail-closed** — 로더가 이행. `credentials` 파일이 **존재하면 사용 여부와 무관하게** 권한을 검사하고, 600이 아니면 수정 명령 안내와 함께 기동 거부. env로 키를 받았어도 느슨한 파일의 존재는 노출 사실이므로 검사를 건너뛰지 않는다. 판정 기준은 **노출 비트(group·other)의 존재**다(2026-08-06 T-012 명문화) — SAFE-DEFAULTS §3.1의 괄호("소유자 외 접근 가능")가 기준이며, `0400`처럼 더 좁은 권한은 통과한다. 더 안전하게 잠근 사용자를 거부하는 것은 계약의 목적과 반대다.
  2. 자기접근 차단 — tools의 denylist가 이행(기확정). 로더 추가 작업 없음.
  3. 자식 프로세스 env 스크러빙 — executor가 이행(기확정). **로더는 로드한 시크릿 값 목록을 executor 생성 시 전달한다**(§2 시퀀스 6) — 값 기반 제거가 성립하려면 executor가 값을 알아야 한다.
  4. 워크스페이스 `.env` 무시 — 로더가 구조적으로 이행: 읽는 곳이 위 두 경로뿐이다. `.env` 스캔 코드 자체가 없다.
- 키 부재 시: 두 경로 모두 없으면 설정 방법(파일 생성 예시 포함)을 안내하고 종료한다. 대화형 입력 마법사는 MVP에 없다 — **트리거**: 온보딩 UX 요구 실측.

## 5. 명령 표면 — argv 최소 + 슬래시 중앙 레지스트리

**argv는 최소로 닫는다**: `neo-agent`(새 세션) · `neo-agent --resume <접두>`(재개) · `--help` · `--version`. 그 외 조작은 전부 REPL 슬래시 명령이다. Commander류 프레임워크·지연 커맨드 등록은 쓰지 않는다(REUSE-MAP §2.6 기각 — argv 4개에 프레임워크는 과설계). **닫힌 목록 밖의 argv와 인자 없는 `--resume`은 사용법 에러다**(2026-08-06 T-012 명문화) — §3의 미지 키와 같은 근거(오타의 침묵 무시 차단, §2.6).

**슬래시 명령은 중앙 레지스트리 한 곳에 정의한다**(hermes `COMMAND_REGISTRY`의 축소 재작성). 디스패치·`/help` 출력·탭 자동완성이 전부 이 테이블에서 파생된다 — 정의 한 곳 원칙.

```typescript
interface SlashCommand {
  name: string;                 // "/sessions"
  aliases?: readonly string[];
  description: string;          // /help에 그대로 노출
  run(args: string, ctx: CliContext): Promise<void>;
}
```

MVP 명령 집합 (닫힌 목록 — 추가는 이 문서 개정):

| 명령 | 동작 |
|---|---|
| `/help` | 레지스트리에서 파생한 명령 목록 |
| `/sessions` | `listSessions()` 표시 — id 접두·title·갱신 시각 |
| `/resume <접두>` | 세션 재개 (§6). 현재 Agent 폐기 후 재생성 |
| `/new` | 새 세션 시작. 현재 Agent 폐기 후 재생성 |
| `/delete <접두>` | 세션 soft-delete (§6). 실행 전 확인 1회 |
| `/search <질의>` | 과거 대화 전문 검색 — 결과는 **표시 전용** (`SEARCH.md` §5). 2026-08-07 개정 |
| `/compact` | 수동 압축 — 자동 트리거와 같은 경로, 임계 미달이어도 실행 (`COMPACTION.md` §3·§6). 2026-08-06 개정·구현 완료 |
| `/memory` | 메모리 표시·삭제 — 인자로 하위 동작 (`MEMORY.md` §7.2). 2026-08-09 개정 |
| `/exit` | 종료 시퀀스 (§2) |

- 슬래시로 시작하지 않는 입력은 전부 대화 입력이다. **미등록 슬래시 명령은 에러 표시**(모르는 명령을 대화로 흘려보내면 오타가 조용히 모델에게 간다 — §2.6).
- `/resume`·`/new`는 `waitForIdle()` → 구독 해지 → **새 `Agent` 인스턴스 생성 + 재배선**이다. 코어의 "새 세션 = 새 인스턴스"(CORE-INTERFACE §4 — `reset()` 없음)의 CLI 측 실체다.
- **`/memory`는 명령 1개 + 인자다** (2026-08-09). 하위 동작(`remove <n>`)을 별도 명령으로 등록하지 않는다 — 닫힌 목록을 하나의 관심사로 셋 늘리면 `/help`가 길어지고 탭 완성이 시끄러워지는데, 얻는 것은 없다. 인자 없는 `/memory`는 **디스크 현재 상태**를 항목 번호와 함께 표시하고(스냅샷이 아니다 — `MEMORY.md` §3.1의 두 상태), "이 세션의 프롬프트에는 반영되지 않았음"과 **파일 경로**를 함께 낸다. `remove <n>`의 범위 밖 번호·비숫자 인자는 사용법 에러다(닫힌 목록 밖 argv와 같은 근거 — 오타의 침묵 무시 차단). 정본은 `MEMORY.md` §7.2이고 이 표는 레지스트리 등록 사실을 남긴다.

  **`/memory edit`(`$EDITOR`로 파일 열기)은 두지 않고 경로 표시로 대체한다** (2026-08-09 사용자 확정 — 플랜 D-1). 설계는 이것을 "사용자의 정리 수단 정본"이라 불렀지만, **CLI는 프로세스를 스폰할 수 없다** — §1이 `node:child_process`를 금지 모듈로 두고 그 근거는 "프로세스 스폰은 tools(executor)의 본업"이다. 셸 도구 경유는 더 나쁘다(컨테이너 안이라 편집기도 TTY도 없고 승인 게이트를 탄다). **경계 하나를 편의 한 단계에 내주지 않는 쪽을 택했다** — 잃는 것은 명령 한 번이고, "사용자가 자기 에디터로 편집하는 것이 큐레이션 정본"이라는 §7.2의 실질은 경로만 알려주면 그대로 성립한다. `MEMORY.md` §7.2가 함께 개정됐다.
- **`/search`의 인자는 첫 공백 뒤 전부다** — 질의에 공백이 포함되므로 토큰 분리를 하지 않는다. 빈 질의는 사용법 에러(닫힌 목록 밖 argv와 같은 근거 — 오타의 침묵 무시 차단). 표시는 hit마다 **체인 tip의 접두**·title·날짜·role·스니펫이고, 빈 결과는 "결과 없음"을 명시한다(침묵 종료 금지 — §2.6). 검색 결과가 모델 컨텍스트로 들어가는 경로는 없다(`SEARCH.md` §1 — 노출 표면은 이 명령 하나). 정본은 `SEARCH.md` §4·§5이고 이 표는 레지스트리 등록 사실을 남긴다.

## 6. 세션 수명주기 — 목록·재개·삭제와 검증 노출

- **새 세션**: `createSession({ workspaceRoot, systemPrompt, model })`. 워크스페이스는 항상 프로세스 cwd의 realpath다 — 옵션으로 다른 경로를 받지 않는다(경계 판정 기준과 세션 기록이 어긋날 표면을 만들지 않는다).
- **재개**: `resolveSessionId(접두)` → `loadSession(id, ResumeContext)` → 반환 메시지 배열을 `AgentSessionInit.messages`로 실어 새 Agent 생성.
  - **워크스페이스 불일치 → 저장소가 거부(기확정)를 CLI는 이렇게 노출한다**: 세션에 기록된 워크스페이스 경로를 표시하고 "그 디렉터리에서 다시 실행"을 안내한다. 세션의 워크스페이스를 새 경로로 바꾸는 재지정은 MVP에 없다 — **트리거**: 워크스페이스 이동(디렉터리 rename) 요구 실측.
  - **시스템 프롬프트·모델 불일치 → 경고 후 진행(기확정)**: 주입한 경고 핸들러가 캐시 무효화 사실을 표시한다. 진행을 막지 않는다.
  - **재개 시 과거 대화는 이벤트로 재방출되지 않는다**(2026-08-06 실측 확정). 렌더러는 `loadSession` 반환 배열로 직접 그린다. 표시 범위(마지막 몇 턴)는 구현 세부이되, **재개 직후 "어디까지 진행된 세션인지"가 화면에 보여야 한다**는 것이 계약이다(§2.6) — 빈 화면으로 이어가면 사용자는 어느 대화에 접속했는지 모른다.
- **과거 대화를 그리는 표면은 `renderer.ts`가 소유하고 배럴에 노출된다** (2026-08-11 확정 — W-4/I-2 해소). 이 절이 *"렌더러는 `loadSession` 반환 배열로 직접 그린다"*고만 하고 **그 표면이 어느 모듈에 사는지**를 정하지 않아 열려 있던 항목이다. 라이브 이벤트 렌더러와 재개 트랜스크립트 렌더러는 **같은 모듈**이어야 한다 — 둘은 같은 `OutputSink`에 같은 표기 규약(역할 접두·도구 줄·트렁케이션)으로 쓰고, 한쪽만 바뀌면 **같은 대화가 재개 전후로 다르게 보인다**. 조립(`wiring.ts`)이 소유하는 안을 택하지 않은 이유가 그것이다: 조립은 *언제 그리는가*를 정하고(§2 시퀀스·재개 경로), *어떻게 그리는가*는 렌더러 하나에 모은다.
  - 배럴 노출은 §1의 소속 기준이 결정한다 — 이것은 `renderer.ts`가 무엇을 하는 모듈인지 드러내는 두 표면 중 하나이므로 올린다. **2026-08-06 QA 판정**(*"**내부 전용 확정.** §6의 이행 세부이고"*, `plans/20260806-cli-qa-report.md` §4)**을 이 판정이 대체한다.** 그 판정의 근거(*"소비자는 wiring 하나(같은 패키지)"*)는 2026-08-11 실측에서도 여전히 사실이지만, 결론에 딸린 **배럴에 없다는 사실 주장**은 — 리포트가 문면으로 든 것이 아니라 «내부 전용»이 함축한 것이다 — **판정 시점에 이미 거짓**이었다 — `src/index.ts`가 재수출하고 있었고 판정 대상 사슬의 마지막 커밋(`5c21c0a`)에서 올라갔다. 근거는 맞고 결론이 과했던 경우이며, 개별 심볼 판정을 §1의 기준이 대신한다.
  - **라이브 경로와 일부러 다르게 처리하는 것이 하나 있고 그것은 세부가 아니라 계약이다**: 재개 트랜스크립트는 도구 결과를 **"실행되지 않음"으로 그리지 않는다.** 그 표시는 §7이 `tool_end` 없이 온 것을 비정상 종료의 합성 짝으로 판정한 데서 나오는데, 과거 트랜스크립트에는 애초에 도구 이벤트가 없으므로 같은 규칙을 적용하면 **실제로 실행됐던 도구가 전부 미실행으로 보인다** — 재개 화면 전체가 조용히 거짓이 되는 경로다(§2.6의 반대 방향: 없는 실패를 보여주는 것도 침묵 실패와 같은 값의 오보다). 재개 경로의 실패 판정 근거는 `isError`뿐이다. 두 렌더러가 같은 모듈인 이상 이 차이는 문서에 있어야 한다.
- **삭제**: `/delete`는 `deleteSession(id)`(soft-delete, `active = 0`)를 호출한다 — 2026-08-06 사용자 확정으로 `SESSION-STORE.md` §5에 추가된 계약이다. 물리 삭제 시점은 같은 문서 §9 미결 유지. 실행 전 대상 세션(id 접두·title)을 표시하고 확인을 받는다.
- **자동 압축의 판정 시점은 CLI가 소유한다** (2026-08-06 압축 설계, 같은 날 구현 완료): 런 종료 후 idle과 재개 직후 2곳에서 판정하고, 압축 시 Agent 교체는 `/resume`·`/new`와 같은 "폐기 후 재생성" 경로다. 압축 발생·결과·실패는 침묵하지 않는다. 상세는 `COMPACTION.md` §3·§6·§7.
- **`resolveSessionId`는 입력을 소문자로 정규화한 뒤 접두 매칭한다** (2026-08-06 확정 — `SESSION-STORE.md` §5에 명문화). 근거: id는 `crypto.randomUUID()`가 발급하는 소문자 hex뿐이므로 정규화에 정보 손실이 없고, UUID 표기의 대소문자는 구별 의미가 없다(RFC 9562). 대문자화된 접두를 거부하면 "복사 과정에서 대문자가 된 id"를 이유 없이 막는다. 모호(2건 이상 매칭)하면 후보를 표시하고 에러 — 조용히 하나를 고르지 않는다(기존 계약 그대로).

## 7. 이벤트 렌더링 계약

렌더러는 이벤트 스트림의 구독자다 — 코어 상태를 폴링하지 않고 이벤트만으로 그린다. 이 자리에 나중에 웹 UI가 앉는다(ARCHITECTURE §2.1의 실체). 렌더러 예외는 삼키지 않는다 — 코어 계약(§3)대로 런을 실패시킨다. 렌더링이 안 되는데 대화가 계속되는 것 자체가 침묵 실패다.

| 이벤트 | 렌더링 |
|---|---|
| `message_start`(user) | 사용자 메시지를 포맷해 표시. **제출한 원시 입력 라인은 포맷된 메시지로 대체**된다(아래) |
| `message_update` | `text_delta` 도착 즉시 출력(스트리밍). `thinking_delta`는 시각 구분(dim)해 표시 |
| `message_end`(assistant) | 스트리밍 마감. `stopReason`별 처리(아래) |
| `message_end`(toolResult) | `tool_end`로 이미 렌더된 `toolCallId`면 스킵. **`tool_end` 없이 온 것(비정상 종료의 합성 짝, CORE-INTERFACE §5)은 여기서 표시** — 미실행 사실이 화면에 남아야 한다 |
| `tool_start` | 도구명 + 인자 요약 표시 |
| `tool_end` | 결과 요약(유계 — 전문 덤프 금지). `isError`는 시각 구분 |
| `turn_end` | usage 한 줄(input/output/cacheRead/cacheWrite, dim) — **비용 가시성의 소비 지점**(CORE-INTERFACE §2 "usage는 옵션이 아니다"가 화면에 닿는 곳) |
| `agent_end` | 입력 프롬프트 복귀 |

- **사용자 메시지는 항상 렌더한다.** 제출 시 원시 입력 라인을 지우고 포맷된 메시지로 다시 그린다. 이 규칙 하나로 세 경우가 구분 없이 처리된다 — 직접 친 프롬프트, steer 주입, 그리고 **코어가 주입하는 합성 user 메시지**(턴 한도 grace, CORE-INTERFACE §5). 렌더러가 "내가 만든 메시지"를 추적해 스킵하는 설계는 합성 메시지를 놓친다.
- **`stopReason`은 침묵하지 않는다**: `max_tokens` → 응답이 길이 한도로 잘렸음을 명시. `error` → `errorMessage` 표시. `aborted` → 중단 표시. `end_turn`/`tool_use`만 무표시 정상이다.
- **델타 없이 끝난 어시스턴트 메시지도 내용이 있으면 `message_end`에서 그린다** (2026-08-06 T-012 명문화). 합성·비스트리밍 실패 응답이 여기 해당한다 — 델타만 믿으면 그 내용이 조용히 사라진다(§2.6).
- **`message_start`/`message_end`의 상관은 id로 한다** — 스트리밍 초안과 최종 메시지가 같은 id라는 계약(CORE-INTERFACE §2)의 소비 지점. toolResult 스킵 판정은 `toolCallId`로 한다.
- **부분 인자 스트리밍(`input_json_delta` 대응)은 요구하지 않는다** (CORE-INTERFACE §11 미결의 해소 — 2026-08-06). 도구 호출 표시는 인자 완성 시점(`tool_start`)이면 충분하다. `toolcall` 이벤트의 "인자 완성 시점 방출" 계약은 그대로 유지된다.
- **`tool_update`는 MVP 렌더러가 소비하지 않는다** (TOOLS-INTERFACE §7 미결의 해소 — 2026-08-06). 도구의 `onUpdate` 호출은 불필요로 확정. **트리거**: 장시간 명령의 진행 표시 요구 실측(dev server·빌드 감시 등).
- 스트리밍 중에도 입력 라인은 최하단에 유지되고, **타이핑 중인 입력은 출력에 의해 유실되지 않는다**(계약). 구현 수단(출력 전 입력 라인 클리어·재그리기)은 세부다.
- **표시 문구는 세부이므로 테스트가 그 문면을 리터럴로 고정하지 않는다**(2026-08-17 확정 · `K-010`). 머리는 표시 문구를 조정 가능(세부)으로 분류하는데 테스트가 특정 문자열을 그대로 단언하면 **그 문구가 사실상 계약이 된다** — 문서가 세부라 부르는 것을 기계가 불변으로 지키는 상태이고, 그러면 문구를 다듬는 일이 계약 변경으로 나타난다. 실물이 그랬다: 재개 경로를 재는 블록은 상태 문구를 부분 문자열로 단언했고 라이브 경로를 재는 블록은 정반대로 상태별 출력이 서로 갈리는지를 쟀다 — **한 파일 안에서 정책이 갈렸다.** 테스트가 재는 것은 **구별과 비침묵**이다: 서로 다른 상태가 서로 다른 출력을 낳는가, 그 출력이 비어 있지 않은가. 같은 축의 미규정이 검색 쪽에도 하나 있다(빈 결과 문구 — `packages/cli/test/search.contract.test.ts`의 미규정 마커 B-7). 이 규칙이 그 물음에도 그대로 걸리나 마커의 처분은 `K-004`의 마커 감사가 든다.

  **경계는 파일 종류가 아니라 단언의 의도다**(2026-08-17 정정 · `K-148`). 위 규칙의 첫 문면은 대상을 `계약 테스트`로 적었으나 같은 불릿의 근거·금지 문장은 한정 없이 `테스트`를 썼고, `계약 테스트`는 이 레포의 어느 정본에도 정의된 적이 없다. **파일 이름으로 가르면 두 방향이 함께 샌다** — 규칙이 선언한 코퍼스 안에서도 리터럴이 살아남고(2026-08-17 실측: 계약 테스트 파일 넷에 열다섯 자리), 그 밖에서는 같은 성질의 단언이 규칙과 무관해진다(같은 실측: 아홉 파일 쉰네 자리). 그래서 가르는 축을 옮긴다.
  - **허용 — 리터럴이 구별이나 비침묵을 재는 프로브일 때.** 같은 문면의 있음과 없음을 서로 다른 상태에서 재는 대비쌍, 그리고 테스트가 주입한 데이터가 그대로 통과했는지를 확인하는 단언이 여기 든다. 뒤엣것의 서술은 `packages/cli/test/renderer.contract.test.ts` 머리가 이미 든다 — 그 예외를 파일 종류가 아니라 의도로 적은 것이 이 기준의 원형이다.
  - **금지 — 리터럴이 문면 자체를 고정할 때.** 짝이 없고 주입 데이터도 아닌 단독 리터럴이다. 문구를 다듬으면 그 단언만 깨지고, 깨진 것이 계약인지 세부인지 아무도 못 가른다.
  - 문구 자체가 계약이어야 하는 자리가 나오면 세부에서 떼어 이 절에 **이름으로 든다** — 테스트가 조용히 계약을 만드는 경로는 열지 않는다.

  **이 기준을 재는 기계는 없다**(2026-08-17 판정 시점). 코퍼스는 오늘 손으로 열거되고 그 열거는 이미 한 번 틀렸다 — `K-148` 카드가 든 여덟이 실측 여섯이었다. 소급 처분과 검사기는 `K-151`이 든다. 같은 분류를 `COMPACTION.md`와 `WEB-ACCESS.md`가 각각 독립으로 한 번씩 더 선언했으므로, 이 기준을 문서 공통 규약으로 올릴 자리가 있는지도 그 카드가 함께 든다 — **§7 한 절로는 그 둘의 소관을 못 덮는다.**

### 7.1 하단 고정 영역과 상태줄 (2026-08-20 확정 — 리치 TUI 재검토 트리거의 해소)

§1·§11이 *"트리거: 리치 TUI 요구 실측"*으로 열어 둔 자리가 발동해 내린 판정이다. **트리거는 발동했으나 프레임워크는 들이지 않는다** — 트리거가 물은 것은 *"리치 렌더링이 필요한가"*이고 실측된 답은 예이지만, 그 수단이 프레임워크여야 한다는 것은 트리거가 함의하지 않았다. 근거는 §11의 개정된 세 행과 아래 배치가 함께 든다.

**배치** — 화면은 세 층이고 순서가 계약이다:

```
[ 트랜스크립트 ]  append-only. 스크롤백에 남는다 (종료 후에도)
[ 상태줄      ]  정확히 1행. 고정
[ 입력 라인   ]  최하단
```

- **상태줄은 입력 라인 위다.** §7의 *"스트리밍 중에도 입력 라인은 최하단에 유지"*가 그대로 유지된다 — 상태줄은 그 위에 끼는 것이지 아래에 붙지 않는다. 아래에 붙이면 그 계약 문장이 거짓이 되고, 커서의 정상 위치가 화면 맨 아래가 아니게 된다.
- **하단 고정 영역은 한 단위로 지워지고 그려진다.** 입력 라인을 걷는 경로가 상태줄을 함께 걷고, 되그리는 경로가 함께 되그린다. 두 영역에 각자의 클리어 경로를 주면 지우는 행 수와 그린 행 수가 어긋나 **겹쳐 그린다** — readline이 감싸인 라인에서 겪는 선재 결함과 같은 형태이고(§8 구현 주석의 2026-08-06 실측), 그 결함을 우리가 새로 만드는 것이 된다.
- **상태줄은 정확히 한 행이다.** 폭을 넘으면 감싸임이 생기고 `cursorUp` 기반 계산이 전부 틀어진다. 넘치면 **자른다.** 폭에 따라 항목을 줄이는 다단 분기(hermes는 셋을 둔다 — `cli.py:5915-5984`)를 두지 않는 이유는 분기마다 재는 자리가 늘고, 그 분기들이 §12의 "표시 세부"에 속해 계약 테스트가 잡지 못하기 때문이다.
- **시계를 두지 않는다.** 상태줄의 갱신은 **이벤트로만** 일어난다. 경과 시간·스피너 같은 시간 기반 항목은 싣지 않는다 — 그것을 실으면 타이머가 필요하고, 타이머는 §7 머리의 *"코어 상태를 폴링하지 않고 이벤트만으로 그린다"*를 깬다. 이 규칙이 스피너를 이번 범위에서 뺀 것과 같은 근거이고, 둘은 함께 열려야 한다(§11).
- **상태줄은 코어를 호출하지 않는다.** 실을 수 있는 값은 두 종류뿐이다 — (a) 시작 시 동결된 설정(§3), (b) 구독 중인 이벤트가 실어 온 것(§7 표). 이 밖의 값이 필요해지면 그것은 상태줄의 문제가 아니라 이벤트 계약의 문제다.
- **`approval-wait`에서는 상태줄도 함께 걷힌다.** 그 상태의 정의가 *"REPL에게서 입력 소유권을 넘겨받는 프롬프트"*(§8)이고, 소유권이 넘어간 동안 하단에 우리가 무엇을 그리면 승인 프롬프트와 겹친다. 승인 표시 무가공(§9)은 그 자리에 우리 것이 없을 때만 성립한다.
- **TTY가 아니면 그리지 않는다.** 라인 모드 강등 경로(`approval-ui.ts`와 `wiring.ts`가 이미 각자 가진 TTY 분기 — 전자는 `isTTY !== true`로, 후자는 `isTTY === true`일 때만 `setRawMode`를 집는 형태로 같은 것을 판정한다)에서는 상태줄이 없다 — 커서 제어가 성립하지 않는 곳에 고정 영역을 그리면 이스케이프가 그대로 섞여 나간다. 설치된 bin은 §7(`DISTRIBUTION.md`)이 이미 거부하므로 이 분기가 닿는 곳은 모의 스트림뿐이다.
- **종료 시퀀스에서 입력 라인과 함께 걷힌다** — §2의 2026-08-20 계약("마지막 항목은 REPL이 입력 라인을 놓은 뒤에 나간다")이 그대로 적용된다. 세션 id와 재개 방법은 상태줄이 걷힌 **뒤**에 나간다. 걷지 않으면 인사 위에 죽은 상태줄이 남는다.

**상태줄은 어떤 고지의 유일한 출구가 아니다** — 이 절에서 가장 값진 규정이다. `SANDBOX.md` §3의 2026-08-09 판정(QA-C C-7)이 배너에 대해 이미 같은 것을 정했다: 두 갈래 안내를 배너에 두지 않은 이유가 *"배너는 REPL 진입 시점(8단계)이라 `startCli`만 부르고 REPL에 들어가지 않는 호스트에서는 안내가 조용히 사라진다"*였다. **상태줄은 배너보다 더 REPL 안쪽에 산다** — 같은 함정에 더 깊이 빠진다.

따라서 상태줄이 하는 일은 **고지가 아니라 지속**이다. 고지는 판정이 일어난 자리에서 이미 나갔고(권한·WAL 경고는 4단계, 셸 두 갈래는 5b, 도구 집합은 시작 화면), 상태줄은 **그것이 스크롤로 밀려난 뒤에도 계속 보이게** 한다. 상태줄이 값을 더하는 자리가 정확히 거기이고, 그 밖의 자리에서 값을 더한다고 주장하면 그것은 다른 절이 할 일을 이 절이 뺏은 것이다.

**내용** — 최소 보장은 계약, 문면은 세부다:

| 항목 | 출처 | 갱신 계기 | 지위 |
|---|---|---|---|
| 승인 모드가 `off`임 | config 동결 (§3) | 없음(고정) | **계약** |
| 셸이 호스트에서 도는 중임(`sandbox: "off"`) | 5b 판정 동결 | 없음(고정) | **계약** |
| 모델 | config 동결 (§3) | 없음(고정) | 세부 |
| 컨텍스트 사용량 | `turn_end`의 usage (§7 표) | `turn_end` | 세부 |
| 세션 id 접두 | 세션 생성·재개 (§6) | `/new`·`/resume` | 세부 |

**앞의 둘만 계약인 근거는 §2.6의 심각도 순서다.** 그 둘은 *"안전한 기본값에서 명시적으로 내려온 상태"*이고(승인 게이트 기본 정책은 `SAFE-DEFAULTS.md` §1, 샌드박스 기본 `on`은 같은 문서 §2), 보호가 꺼져 있는데 화면에 아무 표시가 없는 것이 곧 silent failure다. 나머지 셋은 없어도 사용자가 틀린 판단을 하지 않는다 — 모델과 사용량과 세션 id는 **모르면 물어보면 되는 것**이지 모른 채로 위험해지는 것이 아니다.

**두 계약 항목이 켜져 있을 때(기본값일 때)는 표시하지 않는다.** 상태줄은 «정상이다»를 말하는 자리가 아니다 — 안전한 기본값이 §2.3의 *"안 만진 상태가 가장 안전"*이므로, 그 상태를 매 순간 선언하면 표시가 소음이 되고 정작 내려간 순간의 대비가 죽는다.

**측정** — 이 절에서 테스트가 재는 것은 §7 말미의 기준 그대로 **구별과 비침묵**이다: 승인 모드가 `off`인 세션과 `manual`인 세션의 상태줄 출력이 서로 갈리는가, `off`인 쪽이 비어 있지 않은가. 문면을 리터럴로 고정하지 않는다. 추가로 이 절이 재야 하는 것이 둘 더 있고 둘 다 문면과 무관하다 — **상태줄이 정확히 한 행인가**(폭보다 긴 입력을 주고 잰다), **하단 영역을 걷은 행 수와 그린 행 수가 같은가**.

## 8. 입력 상태 머신

입력 스트림의 소유자는 상태에 따라 하나뿐이다. 닫힌 상태 4개 (2026-08-06 압축 구현에서 `compacting` 추가 — E-44 판정):

```
idle-input      — 활성 런 없음. 입력 제출: 슬래시면 명령 디스패치, 아니면 prompt()
run-active      — 활성 런 진행 중. 입력 제출: steer() 시도 → throw(런 닫힘 구간 경합)면
                  prompt()로 재시도 (CORE-INTERFACE §4가 제시한 패턴의 이행).
                  슬래시 명령은 거부 + 안내 (중단 후 사용)
approval-wait   — 프롬프트가 입력을 소유. 유효 응답만 수리 (§9), 그 외 재프롬프트
compacting      — 압축 진행 중 (COMPACTION §6). 제출은 거부 + 안내(거부된 줄은 히스토리에
                  남는다 — E-46 판정), Ctrl+C는 요약 호출 취소(런 abort가 아니다).
                  `approval-wait`에 얹지 않는 이유: 그 상태는 "입력 소유권을 넘겨받는
                  프롬프트"로 명문화돼 있는데 압축은 무엇도 묻지 않는다
```

- `approval-wait`의 소유자는 게이트 승인 프롬프트만이 아니다(2026-08-06 T-012 명문화) — `/delete`의 확인 프롬프트(§6 "실행 전 확인 1회")처럼 **REPL에게서 입력 소유권을 넘겨받는 모든 프롬프트**가 이 상태를 쓴다. 확인 중 친 글자가 새 대화 입력으로 제출되는 것을 막는 메커니즘은 하나여야 한다.

- **Ctrl+C**: `run-active`·`approval-wait`에서 `abort()` — 진행 중인 것과 예약한 것 전부 취소(코어 §4의 의미론 그대로), 승인 대기 중이면 프롬프트 취소 → block(게이트 §2). `idle-input`에서 종료 시퀀스(§2).

- **Ctrl+D(EOF)** (2026-08-12 구현 판정 명문화 — 파생 빈칸의 확정). 원리는 하나다: **더 이상 입력하지 않겠다**. 대기 중인 물음이 없으면 그대로 수리하고, 걸려 있으면 수리하지 않는다 — 승인에는 기본 선택이 없으므로(§9) EOF를 답으로 읽으면 **사용자가 하지 않은 결정을 지어내는** 것이 된다.

  | 상태 | Ctrl+D | 근거 |
  |---|---|---|
  | `idle-input` | 종료 시퀀스(§2) | 물음이 없다. 셸의 EOF 관례 그대로 |
  | `run-active` | 종료 시퀀스(§2) — `waitForIdle()`이 런을 기다린 뒤 끝낸다 | 진행 중인 것을 버리지 않는다. **중단이 목적이면 그 키는 Ctrl+C**(abort)다 |
  | `compacting` | 종료 시퀀스(§2) — 압축을 기다린 뒤 끝낸다 (대기 지점은 §2가 열거한다) | 위와 같다. 압축만 취소하려면 Ctrl+C(`COMPACTION.md` §6) |
  | `approval-wait` | **무효 키 — 재프롬프트**(§9) | 물음이 걸려 있고 기본 선택이 없다 |

  `approval-wait`만 다른 것은 **구조가 이미 그렇게 만들어져 있다** — 그 상태에서는 REPL이 readline을 떼고 승인 UI가 입력을 소유하므로(§9 이양) EOF가 애초에 REPL에 도달하지 않는다. 규약이 아니라 구조가 이 구분을 강제하며, 이양 중 Ctrl+C만 REPL이 계속 감시하는 것과 같은 배치다.

  **EOF가 언제 전달되는지는 이 문서가 정하지 않는다** — readline 관례(빈 줄에서만)이며 구현 세부다. 계약은 "EOF가 REPL에 도달했을 때 무엇을 하는가"까지다.
- steer가 "interrupt-and-redirect"(hermes 채택 항목)의 이행이다: 스트리밍 중 타이핑 → Enter가 곧 진행 중 끼어들기다. 별도 모드 전환 키는 없다.
- 탭 자동완성은 슬래시 명령에만 동작한다(레지스트리 파생). 입력 히스토리는 프로세스 메모리만 — 영속화 **트리거**: 세션 넘는 히스토리 요구 실측.
- 멀티라인 입력은 MVP에 없다(단일 라인 + Enter 제출). **트리거**: 붙여넣기·장문 입력 마찰 실측.
- **`/search`는 상태를 추가하지 않는다** (2026-08-07) — 읽기 전용 조회라 `idle-input`에서 디스패치되고 동기 완료된다(`SEARCH.md` §5). 상태는 계속 4개 닫힌 목록이다. 명령이 늘 때마다 상태가 느는 것이 아니라, **입력 소유권이 REPL에서 넘어갈 때만** 상태가 는다는 것이 이 절의 기준이다.

## 9. 승인 프롬프트 UI (SAFE-DEFAULTS §6·APPROVAL-GATE §7 미결의 해소)

`ApprovalPrompt` 구현은 CLI가 소유한다. 게이트 계약(APPROVAL-GATE §4)의 소비 지점:

- **`display`는 가공 없이 그대로 표시한다.** 색상·테두리 장식은 `display` 문자열 **밖**에만 붙인다 — 문자열 내용을 자르거나 정규화하거나 재포맷하면 게이트의 위조 탐지(비가시·동형이의 문자 이스케이프)가 무의미해진다. 여러 줄 `display`의 줄 앞 접두(들여쓰기·테두리)도 "밖의 장식"이다(2026-08-06 T-012 명문화) — 단 `display`의 각 줄 바이트는 출력에서 보존돼야 하고 줄 수를 바꾸지 않는다.
- `warnings`는 `display` 인접에 시각 강조로 표시한다.
- 선택지: **allow-once / allow-always / deny.** `allowAlwaysKey`가 없으면 "항상 허용"을 제공하지 않는다(게이트 계약 — 연산자 포함 명령 등). 응답 키는 구현 세부이되 **기본 선택(그냥 Enter)은 존재하지 않는다** — 승인은 명시적이어야 한다.
- **특별 취급하는 키는 Ctrl+C 하나다** (2026-08-10 실측 후 명문화). 나머지 제어문자는 전부 무효 키로 재프롬프트하며, **Ctrl+D도 여기 포함되어 EOF·취소 어느 쪽으로도 해석되지 않는다**(다른 상태에서의 Ctrl+D는 §8의 상태별 표). 승인 대기에서 EOF에 의미를 부여하면 그것은 사용자가 하지 않은 결정을 만들어내는 것이다 — "기본 선택(그냥 Enter)은 존재하지 않는다"와 같은 근거이고, `§7`이 닫은 것("TTY가 없으면 거부")과는 다른 사안이다(그쪽은 애초에 물을 수단이 없는 경우다).
- **무효 키를 알렸을 때 사용자가 자기가 무엇을 눌렀는지 알아볼 수 있어야 한다** — 제어·비가시 문자는 이름(`Ctrl+D`·`Enter`)이나 코드포인트(`U+00A0`)로 표시한다. 원시 이스케이프(`""`)는 "무효였다"는 사실만 전하고 "무엇이 무효였는지"를 감춘다(§2.6). **이것은 위의 `display` 무가공 규칙과 충돌하지 않는다** — 가공하는 대상이 게이트가 만든 문자열이 아니라 사용자 자신의 키 입력이므로, 위조 탐지가 지켜야 할 표면이 아니다.
- **abort 시 `ask`는 reject한다 — `"deny"`를 지어내지 않는다**(2026-08-06 T-012 명문화). 사용자가 거부한 것과 런이 끊긴 것은 다른 사실이고, 취소의 block 변환은 게이트 몫이다(게이트 §2 — 게이트는 자체 경주로 프롬프트 구현의 signal 무시까지 방어한다).
- deny 시 CLI는 자체 사유 문자열을 만들지 않는다 — 모델에게 가는 `reason`은 게이트가 만든다(영어, 게이트 §4의 수신자 규칙).
- 승인 대기와 모델 스트리밍은 겹치지 않는다 — 도구 실행이 순차이고 루프가 훅을 await하므로(CORE-INTERFACE §5·§7) 승인 프롬프트가 뜬 시점에 화면은 정지 상태다. 병렬 도구 실행을 MVP에서 뺀 근거("승인 프롬프트가 겹치는 UX는 그 자체가 설계 과제")가 이 단순성으로 실현된다.

## 10. AllowlistStore 파일 구현 (APPROVAL-GATE §7 미결의 해소)

- 위치: **`~/.neo-agent/allowlist`**. 이 위치의 부수 효과는 세션 DB와 같은 구조로 **우연이 아니라 확인한 것이다**: denylist가 `~/.neo-agent/**` 전체이므로 **에이전트가 도구로 자기 allowlist를 넓힐 수 없다**(게이트 §5의 "프로그래밍적 확대 경로를 만들지 않는다"가 파일 수준에서도 성립). 파일을 옮기면 이 보호가 조용히 사라진다.
- 포맷: 한 줄 = 키 하나(UTF-8). 키 형식은 게이트가 정의한다(APPROVAL-GATE §7 — `shell:…`·`fileWrite:…`).
- 시작 시 1회 로드하고 재읽기하지 않는다(게이트 §5 — 재읽기는 세션 중 설정 변경 경로다). `add`는 메모리와 파일 append에 동시 반영.
- **append 실패는 조용히 넘기지 않는다**: 메모리 반영은 유지하되(이번 세션은 유효) "다음 세션에 남지 않는다"는 경고를 표시한다. 안내 없는 부분 성공은 침묵 실패다(§2.6). 경고는 **주입된 핸들러**로 전달한다(2026-08-06 T-012 명문화 — SESSION-STORE §7과 같은 구조: 모듈은 UI를 모르고, 표시는 호스트 몫).

## 12. 미결 — 이 문서가 정하지 않은 것

- **기본 모델 문자열** — 구현 시 확정(§3 — 기본값 존재가 계약, 값은 세부). maxTokens 기본은 어댑터 소유(CORE-INTERFACE §8)라 CLI 관심사가 아니다.
- **표시 세부** — 색상, 프롬프트 문자, 재개 시 과거 대화 표시 범위, usage 표시 형식.
- ~~**`node:sqlite` ExperimentalWarning의 stderr 노출 처리**~~ (2026-08-06 실측에서 CLI로 이월) — **같은 날 해소: `process.on("warning")` 필터**(`5c21c0a`). 억제 수단을 "구현 시 확정"으로 위임했고 구현이 확정했다(`packages/cli/src/main.ts` — `ExperimentalWarning` 중 메시지에 `SQLite`가 든 것만 걸러낸다). **필터 설치가 `node:sqlite` 임포트보다 앞이어야 한다** — 정적 임포트면 경고가 필터보다 먼저 나가므로 저장소 모듈은 동적 임포트로 로드한다(같은 파일의 실측 주석). 다른 실험적 기능의 경고는 그대로 통과시킨다.
- **Windows 지원 범위** — TOOLS-INTERFACE §7과 같은 지위(POSIX 우선). ANSI 제어의 Windows 터미널 검증은 그때.
- **온보딩(키 입력 마법사)** — §4 트리거.
- ~~**TTY 부재 환경(파이프·CI)의 기동**~~ (2026-08-06 CLI 플랜 R-3에서 등재) — **2026-08-09 해소: 명시적 에러로 거부** (`DISTRIBUTION.md` §7). 미룬 근거였던(`6d9019e^`) *"지금 닫으면 스크립트 구동 검증 경로까지 막는다"*는 **검사 위치로 해소된다** — 검사는 `process.*`를 읽는 유일한 곳인 `main.ts`에 있고, 테스트·QA는 `runCli`를 모의 스트림으로 직접 호출하므로 지나지 않는다(실측: `packages/cli/test/`에 실제 bin을 스폰하는 테스트 0건, `isTTY !== true` 라인 모드 강등 분기는 그대로 유지). 남는 손실은 설치된 bin의 파이프 구동뿐이고 그 경로는 애초에 동작하지 않았다. 닫기로 전환한 계기는 배포다 — 설치되면 의도치 않은 맥락(cron·스크립트)에서 실행될 수 있게 된다.
