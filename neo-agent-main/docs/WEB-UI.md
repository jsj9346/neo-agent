# 웹 UI — 서버·프로토콜

**`packages/serve`의 공개 계약, 프로세스 모델, 노출 경계, 화면 자산 반입 규칙의 정본.**

- 상태: 구현 전
- 근거: packages/serve
- 작성일: 2026-08-19
- 최종 개정: 2026-08-20(§2 — 전송 수단과 의존성 예산 확정. §12 미결 하나 소비)

`ARCHITECTURE.md` §2.19의 정본이다. **경계(패키지 의존성, 전송 변환의 자리, 노출 범위)와 계약(무엇이 설정으로도 해제 불가인지, 승인이 어디에 귀속되는지)은 이 문서가 정본**이며, 프레임 이름·포트 번호·타임아웃 수치는 구현 시 조정될 수 있다. 경계·계약을 바꾸려면 devlog에 근거를 남기고 이 문서를 먼저 고친다.

전제는 `SAFE-DEFAULTS.md` 머리와 같다: **여기 있는 어떤 것도 프롬프트 인젝션에 대한 보안 경계가 아니다.** 이 문서가 더하는 것은 네트워크 표면 하나이고, 그 표면의 경계는 §4가 OS(SSH)에 넘긴다.

참조: OpenClaw `packages/gateway-protocol/`·`src/gateway/server-http.ts`·`src/gateway/exec-approval-manager.ts`·`src/plugin-sdk/agent-core.ts`·`src/infra/device-pairing.ts`, hermes `gateway/stream_events.py`·`gateway/run.py` (2026-08-19 실독 — 조사 산출은 `devnotes/20260819-devnote.md` §13.7이 요약을 든다). 복사가 아니라 이해 후 재작성.

## 1. 이 문서가 푸는 문제

`ARCHITECTURE.md` §2.1이 코어의 전송 비의존을 확정했으나 **인터페이스가 CLI 하나뿐이라 그 원칙은 오늘까지 미검증이다.** 소비자가 하나면 "전송을 모른다"와 "전송이 하나뿐이라 몰라도 됐다"가 구분되지 않는다. 웹 UI는 그 구분을 만드는 두 번째 소비자다.

**자리는 이미 예약돼 있다.** `CORE-INTERFACE.md` §3과 `CLI-INTERFACE.md` §7이 각각 이벤트 스트림과 렌더링 계약에 웹 UI가 앉을 것을 미리 적었고, `DISTRIBUTION.md` §10은 미결 **둘**(VPS 상주 · 디자인 시스템 산출물 반입 형태)의 트리거를 웹 UI 착수로 걸어 두었다. **이 문서는 그 둘을 함께 소비한다**(§9·§10) — 웹 UI만 정하고 둘을 남기면 트리거가 발동한 채로 남는다.

**이 문서는 코어 계약을 만들지도 넓히지도 않는다.** 레퍼런스 대비에서 나온 규율이 정확히 그것을 금지한다(§5).

## 2. 경계 — 패키지와 의존성

**신규 패키지는 `packages/serve` 하나다.**

```
packages/serve      ← 이 문서의 대상. HTTP 서버 + 프레임 인코딩 + 정적 자산 서빙
packages/cli        ← `neo-agent serve` 서브명령을 더한다. 조립 지점은 여전히 여기 하나
```

- **`packages/serve`는 `packages/core`의 이벤트 계약에 의존하고, 코어는 `serve`를 모른다.** 역방향 임포트는 존재하지 않는다.
- **`packages/serve`는 `packages/web`과 무관하다.** 이름이 비슷하나 후자는 `web_fetch`(외부 웹 접근·SSRF 판정)이고 이 패키지는 우리 서버다. 두 패키지 사이에 의존이 없다.
- **조립은 `packages/cli`가 계속 독점한다.** `CLI-INTERFACE.md` §1이 CLI를 유일한 조립 지점으로 못박았고 이 문서는 그것을 바꾸지 않는다 — `serve`는 배선을 받는 쪽이지 배선하는 쪽이 아니다.
- 외부 런타임 의존성은 **0이고, 이것은 목표가 아니라 계약이다**(2026-08-20 확정). 전송 수단을 §2.1이, 예산의 실물을 §2.2가, 그 계약이 기계에 어디까지 닿는지를 §2.3이 든다.

### 2.1 전송 수단 — SSE + POST. WebSocket을 쓰지 않는다 (2026-08-20 확정)

**서버→클라이언트는 SSE(`text/event-stream`) 스트림 하나, 클라이언트→서버는 개별 POST다.** WebSocket은 채택하지 않는다 — `ws` 의존성도, 자체 프레임 파서도 두지 않는다.

**§6이 이미 방향을 갈라 놓았고, 그 모양이 그대로 이 전송이다.** 프레임 셋에서 클라이언트가 보내는 것은 `RequestFrame` 하나이고 그것은 *"요청 하나에 정확히 하나"*의 왕복이다. 서버가 보내는 것은 `ResponseFrame`(그 왕복의 반쪽)과 `ServerEventFrame`(밀어내는 스트림)이다. 즉 **양방향 단일 소켓이 파는 능력**(클라이언트→서버 스트리밍, 한 연결에서의 연속 양방향 프레이밍)을 이 프로토콜은 **쓰지 않는다.** 안 쓰는 능력에 값을 치르지 않는다.

**두 갈래의 값이 각각 실물이다:**

| 갈래 | 값 |
|---|---|
| `ws` 의존성 | 외부 런타임 의존성이 **2 → 3**이 된다. 지금 둘은 스키마(`zod`)와 벤더 SDK(`@anthropic-ai/sdk`)로 **대체 불가능한** 것들이고, `ws`는 대체 가능한 편의다. 게다가 공급망 규율이 걸린다 — 정확 핀 + `minimumReleaseAge: 2880` + `blockExoticSubdeps`(`DISTRIBUTION.md` §8)라 릴리스 48시간 안에는 갱신이 **설치 실패**로 나온다 |
| 자체 프레임 파서 | RFC 6455의 필수 항목이 핸드셰이크(SHA-1+base64) · 마스킹 해제(클라이언트 프레임은 **반드시** 마스킹된다) · 길이 3형식(7/16/64비트) · 단편화 continuation · ping/pong · close 코드 · 텍스트 프레임 UTF-8 검증이다. **소켓 위의 파서**이고, 파서 버그는 이 레포가 가장 경계하는 종류의 결함이다 |

**SSE는 둘 다 안 낸다.** 실측(2026-08-20): `node:http` 하나로 45줄에 위 프레임 셋이 그대로 실렸고 버전 불일치 거부까지 동작했다. 브라우저 쪽은 `EventSource`가 표준이라 클라이언트 라이브러리가 **없다** — §9의 *"브라우저가 직접 로드하는 것만"*과 정확히 맞는다.

**§6·§8의 계약이 이 전송에서 더 싸게 성립한다:**

- **버전 불일치가 더 정직해진다.** §6은 버전이 안 맞으면 연결을 닫기로 했다. WebSocket에서 그것은 *열린 뒤의* close 프레임이고, 여기서는 스트림이 **열리기도 전의 HTTP 400**이다. 열렸다 닫히는 것보다 안 열리는 것이 낫다.
- **`EventSource`의 자동 재접속이 §8의 *"갭의 처리는 재접속이다"*를 이미 구현한다.** 우리가 쓸 코드가 아니라 브라우저가 하는 일이 된다.
- **핸드셰이크의 방향만 뒤집힌다.** *"첫 프레임은 반드시 핸드셰이크다"*(§6)는 그대로이고, 클라이언트가 버전을 스트림 요청에 실어 보내고 **서버가 스트림의 첫 이벤트로 스냅샷을 보내는** 형태가 된다.

**레퍼런스가 이 판정을 반증하지 않는다 — 오히려 양쪽이 같은 방향을 가리켰다**(2026-08-20 실독):

- **hermes의 클라이언트 대면 에이전트 스트리밍은 전부 SSE이고 WebSocket이 아니다.** 게이트웨이 범위에서 WebSocket 매치가 0건이다. 사용자 개입(승인 응답·중단·프롬프트 제출)은 전부 **별개의 POST**다 — 우리 §6이 이미 가진 모양과 같다. **더 값진 것은 §7의 존재 증명이다**: hermes의 `/v1/runs`는 SSE 연결과 독립한 백그라운드 태스크로 돌고 승인 대기가 프로세스(스레드)에 귀속하며 연결이 끊겨도 별도 POST로 풀린다. **우리 §7이 요구하는 것이 이 전송 위에서 실제로 돈다.**
- **OpenClaw는 브라우저 UI에 `ws`를 쓰지만 그 게이트웨이가 지는 요구가 우리와 다르다** — 업그레이드 시점의 사전인증·연결 예산·신뢰 프록시 판정, 그리고 프로바이더로 나가는 아웃바운드 realtime 소켓들. 우리는 그중 아무것도 없다(§4가 인증을 없앴고 §11이 팬아웃을 뺐다). **더 결정적인 것은 같은 레포가 SSE도 둔다는 사실**이고 그 근거가 주석에 적혀 있다 — 세션 히스토리 tail(`sessions-history-http.ts`)은 *"WS 풀프로토콜을 구사할 필요 없는 단순 HTTP 클라이언트"*를 위한 저부담 경로다. **우리 소비자가 정확히 그 부류다.**

**hermes에서 가져오지 않는 것도 같은 실독이 짚었다.** 그쪽 `/v1/runs/{id}/events`는 구독자가 **1명뿐**이고 첫 연결이 끝나면 큐를 지워 재접속이 404가 된다. OpenAI 호환 스트리밍 3종은 반대로 **연결이 곧 실행의 생명선**이라 끊기면 런을 인터럽트한다. **둘 다 §8이 명시적으로 거부한 것이다** — 우리는 재접속하면 스냅샷을 받고, 연결이 끊겨도 런은 계속된다. **전송을 가져오는 것이 그 전송에 얹힌 수명 정책까지 가져오는 것이 아니다.**

**전송을 바꾸는 일이 이 문서 밖으로 번지지 않는다.** §5 규칙 4가 *"인코딩은 `packages/serve` 안에만 산다"*를 이미 정했고, 여기에 한 줄을 더한다 — **§6의 `Frame` 유니온은 전송을 모른다.** `sse`·`ws`·`http` 어느 것도 타입에 나타나지 않는다. 그래서 훗날 전송을 바꾼다면 그것은 `packages/serve` 안의 인코더 교체이고 `core`·`cli`·프레임 타입은 손대지 않는다. OpenClaw가 같은 구조를 실증한다 — 전송 무지 프로토콜 상태기계 하나 위에 얇은 전송 어댑터 둘(`packages/gateway-client`의 `protocol-client.ts` ↔ `client.ts`/`browser.ts`).

**포기하는 것을 정직하게 적는다:**

| 잃는 것 | 판정 · 트리거 |
|---|---|
| 클라이언트→서버 스트리밍 | POST 본문 하나가 요청 하나다. §6의 어느 메서드도 오늘 스트리밍 입력을 안 쓴다. **트리거**: 음성 입력처럼 연속 업스트림이 필요한 메서드를 두기로 할 때 |
| 브라우저의 오리진당 HTTP/1.1 연결 6개 상한 | 탭 하나가 스트림 하나를 점유하므로 **탭 일곱째가 매달린다.** 개인 1인 전제에서 실사용 문제가 아니지만 **성질로 존재하므로 적는다.** HTTP/2면 사라지는데 그것은 TLS를 뜻하고 §4가 TLS를 만들지 않았다 |
| 바이너리 프레임 | §6이 JSON이라 무관하다 |
| 비브라우저 클라이언트의 편의 | Node에는 `EventSource` 전역이 **없다**(2026-08-20 실측). 붙이려면 그쪽이 SSE 파서를 갖는다 — 이 자리는 이미 §11의 재도입 트리거가 *"브라우저가 아닌 클라이언트를 붙이기로 판정할 때"*로 들고 있다 |

### 2.2 의존성 예산 — `packages/serve` (2026-08-20 확정)

```
dependencies:  ["@neo-agent/core", "zod"]
```

- **외부 런타임 의존성 0.** `zod`는 새 의존성이 아니라 이미 트리에 있는 것이고, §6이 요구하는 *"알려지지 않은 필드를 거부한다"*를 실제로 재는 수단이다. `core`를 뺀 나머지 패키지 대부분이 같은 둘을 든다.
- **`packages/serve`는 다른 패키지를 직접 들지 않는다.** 조립은 `packages/cli`가 독점하므로(§2) `store`·`gate`·`providers`는 배선으로 들어오지 임포트로 들어오지 않는다.

**허용 내장 모듈** — `node:http`(본업) · `node:fs`(§9의 정적 자산) · `node:path` · `node:url`

**금지 내장 모듈** — `node:https` · `node:net` · `node:tls` · `node:sqlite` · `node:child_process` · `node:dns` · `node:dgram` · `node:worker_threads`

- **`node:https`·`node:tls` 금지가 §4의 *"TLS를 설계하지 않는다"*의 기계 판이다.** 루프백 평문이 결정이므로 TLS 코드를 가질 이유가 없고, 갖지 않는 것이 그 결정을 지킨다.
- **`node:net` 금지** — 루프백 바인드는 `node:http`의 `listen()`이 하므로 raw 소켓이 필요 없다. 다만 이 금지가 WebSocket을 막지는 **않는다**(§2.3).
- **`node:sqlite`·`node:child_process`·`node:dns` 금지** — 저장소는 `store`, 프로세스 스폰은 `tools`, 이름 해석은 `web`의 본업이다. 서버가 그 일을 대신 하기 시작하면 경계가 샌다. `store`·`compaction`이 받는 금지와 같은 근거다.

### 2.3 이 계약을 무엇이 강제하는가 — 그리고 무엇을 강제하지 못하는가

**의존성 예산 게이트가 `ws` 도입을 막는다 — 단, 오늘은 아직 아니다.** `scripts/check-core-budget.mjs`는 `dependencies` 키를 **정확 일치**로 재므로 한 줄만 늘어도 붉어진다. *"예산을 조용히 늘리는 경로를 열지 않는다"*가 이 판정이 겨눈 것이고, 그 경로는 그 게이트가 이 패키지를 재기 시작하면 닫힌다.

**그 시점이 아직 오지 않았다는 것을 여기 적는다.** 게이트의 `PACKAGES` 목록에 `serve` 항이 없고 `packages/serve` 디렉터리 자체가 없다 — 게이트는 `package.json`과 `src/`를 읽으므로 **패키지보다 먼저 항을 넣으면 즉시 붉어진다.** 그래서 §2.2의 예산은 오늘 **이 문서가 정본으로 들고**, 게이트 반영은 그 패키지를 만드는 구현 사이클의 일이다. **이 문단이 있는 이유는 바로 아래 문단과 같다** — "게이트가 막는다"만 적어 두면 다음이 오늘 이미 막히는 것으로 읽는다.

**그러나 임포트 예산은 손수 짠 WebSocket을 막지 못한다 — 실측했다**(2026-08-20):

- `http.Server`의 `upgrade` 이벤트는 **`node:net` 임포트 없이** 완전한 duplex 소켓을 넘겨준다. 금지 목록에 `node:net`이 있어도 소켓은 `node:http`를 통해 들어온다.
- 핸드셰이크의 SHA-1도 **`node:crypto` 없이** 전역 `crypto.subtle.digest("SHA-1", …)`로 계산된다.

**즉 막는 것은 예산이 아니라 §2.1의 판정이고, 그 판정을 재는 기계는 오늘 없다.** 이 문단이 있는 이유는 이 레포가 같은 병리를 이미 만났기 때문이다 — **검사가 실제보다 넓게 주장하는 것이 진짜 결함이었던 자리**가 있고(`packages/providers/test/package-boundary.contract.test.ts` 머리의 한계 서술), `SANDBOX.md` §3의 근사 목록이 같은 규율이다. *"예산이 WebSocket을 막는다"*고 적어 두면 다음이 그것을 완전한 강제로 읽는다.

**근사 검사를 만들지 않는다** (2026-08-20 판정). `packages/serve/src`에서 `upgrade` 리스너나 `Sec-WebSocket` 문자열을 텍스트 스캔하는 것은 가능하나, ① 손수 짠 WebSocket은 **조용하지 않다** — 수백 줄의 가시적 diff이고 이 판정이 겨눈 *"조용한"* 경로가 아니다 ② 그 스캔은 이 레포의 텍스트 스캔이 이미 아는 두 한계(변수 경유·주석 우회)를 그대로 물려받아, **막는다고 주장하면서 못 막는 상태를 새로 만든다.** **재도입 트리거**: `packages/serve/src`에 `upgrade` 리스너가 실제로 나타날 때 — 그때는 판정이 이미 뒤집힌 것이므로 검사가 아니라 이 절의 개정이 먼저다.

## 3. 프로세스 모델 — `neo-agent serve` (2026-08-19 확정)

**`CLI-INTERFACE.md` §2가 못박은 계약 중 상주 금지 부분을 좁힌다.**

- **바뀌는 것**: 상주 데몬이 없다는 항이 **명시적 `serve` 명령일 때만 상주한다**로 좁혀진다.
- **안 바뀌는 것**: 단일 프로세스는 그대로다. `serve`는 **포그라운드 프로세스**이고 스스로 데몬화하지 않으며 fork·detach·pidfile을 만들지 않는다. 수명 관리는 프로세스 밖(systemd·tmux)의 일이다.

**왜 데몬화하지 않는가** — 데몬화는 프로세스 수명을 우리가 소유한다는 뜻이고, 그러면 재시작·로그 로테이션·중복 기동 방지가 전부 이 패키지로 끌려 들어온다. VPS에는 이미 그것을 하는 것(systemd)이 있다. `DISTRIBUTION.md` §2가 배포에서 같은 판단을 했다 — 남이 이미 하는 일을 우리 표면으로 들이지 않는다.

**기동 시퀀스의 순서가 계약이다** — `CLI-INTERFACE.md` §2의 순서를 그대로 상속하고 뒤에 둘을 더한다: 설정 동결 → 크리덴셜 fail-closed → 경계 생성 → 저장소 → 세션 → Agent → **저장소 구독 먼저** → **서버 바인드** → 대기. **서버 바인드가 저장소 구독보다 뒤인 이유**는 CLI 렌더러가 나중인 이유와 같다 — 클라이언트가 붙어 이벤트를 받기 시작했는데 저장소가 아직 구독 전이면 그 이벤트는 영속되지 않는다.

**TTY 없이도 기동한다.** `DISTRIBUTION.md` §7이 TTY 부재 기동을 거부하기로 한 근거는 *승인 게이트가 물어볼 사람이 없는데 묻는 상태*였다. `serve`에서는 승인자가 TTY가 아니라 브라우저이므로 그 근거가 이 명령에서 죽는다 — **근거가 대상에서 죽으면 결론도 함께 죽는다.** 대신 §7의 fail-closed가 그 자리를 대신 진다.

## 4. 노출 — loopback 고정 (2026-08-19 확정)

**서버는 루프백에만 바인드한다. 원격 접속은 SSH 포트포워딩으로만 한다.**

- **바인드 주소는 설정 항목이 아니다.** `0.0.0.0`·LAN·공인 IP로 여는 옵션을 **만들지 않는다.** 만들지 않으면 잘못 켤 수 없다 — `SANDBOX.md`가 마운트 추가 설정을 안 만들어 검증 대상 자체를 없앤 것과 같은 수단이고, 그 선례가 `REUSE-MAP.md` §3의 샌드박스 행에 기록돼 있다.
- **그래서 이 문서는 인증·TLS·페어링·레이트리밋을 설계하지 않는다.** 네 가지 전부가 "신뢰할 수 없는 네트워크에서 오는 연결"을 전제하는데, 루프백 고정에서는 그 연결이 존재하지 않는다. 원격 접근의 인증은 **SSH가 이미 하고 있고 그것이 OS 경계다** — `SAFE-DEFAULTS.md` 머리가 유일한 경계를 OS로 선언한 것과 결이 같다.
- **강제 수단**: 바인드 호스트는 상수이고 설정·env·argv 어디서도 덮어쓸 수 없다. 이 성질은 계약이므로 테스트가 잰다.

**레퍼런스 대비** — OpenClaw는 바인드 모드가 다섯이고 기본이 루프백이며 컨테이너에서만 `0.0.0.0`으로 자동 전환된다. 그리고 `bind=lan` + 무인증 조합을 **시작 시점에 거부**하는 가드를 둔다. 우리는 **그 가드가 필요 없는 지점**을 골랐다 — 위험한 조합을 검사하는 대신 그 조합을 표현할 수 없게 한다. 다만 그 가드의 설계 자체는 §11에 재도입 후보로 남긴다.

**흔적만 남기는 것(🧬)**: 바인드 호스트를 상수로 두되 **서버 생성 함수의 인자로 받는 형태**로 만든다. 노출을 여는 날 그 인자의 출처만 바뀌면 되고 서버 본체는 재작성되지 않는다.

**재도입 트리거**: SSH 터널이 실사용에서 실제로 불편하다고 관측될 때 — 또는 브라우저가 아닌 클라이언트(모바일 등)를 붙이기로 판정할 때. 그때 열리는 것은 §11의 인증 설계이지 이 절의 상수가 아니다.

## 5. 전송 경계 — 정규화는 한 자리, 인코딩은 전송별 (2026-08-19 확정)

**레퍼런스 실독이 이 절의 근거를 전부 댔다.**

- OpenClaw는 코어↔게이트웨이 배선이 **11줄**이고 넘기는 것이 LLM 호출 함수 둘뿐이다. 코어 타입에 연결·소켓·세션 식별자가 **없다**. 변환은 2단이다 — 코어 이벤트를 전송 중립 콜백으로 바꾸는 **정규화가 한 자리**에 있고, 그 콜백을 실제 바이트로 바꾸는 **인코딩이 전송 수만큼 분산**된다.
- hermes는 그 경계가 없다. 게이트웨이가 에이전트 객체를 캐시하고 매 턴 콜백 속성을 대입하며, 그 클로저가 소켓 식별자를 캡처한다. 뒤늦게 타입드 이벤트 계층을 만들었으나 그것이 게이트웨이 안에만 적용되고 코어가 부르는 계약은 그대로 남았다.

**그래서 이 문서가 지키는 규칙 넷:**

1. **코어 이벤트 타입에 전송 식별자를 넣지 않는다.** `CORE-INTERFACE.md` §3의 `AgentEvent`는 이 문서 때문에 한 필드도 늘지 않는다.
2. **구독은 `subscribe()`로만 한다.** 코어 인스턴스에 콜백 속성을 대입하는 형태를 만들지 않는다 — CLI와 웹이 동시에 붙으면 두 리스너가 같은 슬롯을 두고 경합한다.
3. **웹은 기존 계약의 구현체를 하나 더 더하는 것으로 끝난다.** 계약을 웹 때문에 넓히지 않는다.
4. **인코딩은 `packages/serve` 안에만 산다.** 프레임을 만드는 코드가 `core`·`cli`에 들어가면 경계가 샌 것이다.

**우리는 이 규칙을 지킬 조건을 이미 갖췄다** — `CORE-INTERFACE.md` §3이 `AgentEvent`를 닫힌 유니온으로 고정했고 §9 불변 조건이 그것을 떠받친다. hermes가 실패한 지점은 두 번째 프런트엔드를 붙인 **뒤에** 계약을 고치려 한 것이고, 우리는 붙이기 **전**이다.

## 6. 와이어 프로토콜

**형식은 `REUSE-MAP.md` §3이 이미 판정했다** — 스키마 코드젠은 채택하지 않고 닫힌 객체 원칙만 가져온다. 2026-08-19 실독이 그 판정을 보강했다: 그 레포에서도 코드젠의 외부 언어 산출물을 실제로 소비하는 자리를 찾지 못했다. 우리는 소비자가 브라우저 하나이고 그 브라우저가 같은 저장소의 TypeScript 타입을 그대로 읽는다.

**프레임은 셋이고 판별자로 닫는다.**

```typescript
/** 클라이언트 → 서버. 사용자 개입(프롬프트 제출·steer·abort·승인 응답) */
type RequestFrame = { readonly type: "req"; readonly id: string; readonly method: string; readonly params?: unknown };
/** 서버 → 클라이언트. 요청 하나에 정확히 하나 */
type ResponseFrame = { readonly type: "res"; readonly id: string } & (
  | { readonly ok: true; readonly payload?: unknown }
  | { readonly ok: false; readonly error: { readonly code: string; readonly message: string } }
);
/** 서버 → 클라이언트. 에이전트 진행. `seq`는 연결마다 1부터 단조 증가 */
type ServerEventFrame = { readonly type: "event"; readonly seq: number; readonly event: AgentEvent };

type Frame = RequestFrame | ResponseFrame | ServerEventFrame;
```

- **에이전트 진행은 이벤트로 밀어내고 사용자 개입은 요청·응답으로 왕복한다.** 스트리밍과 명령이 프레임 타입 레벨에서 갈린다 — 레퍼런스가 같은 자리에서 같은 선택을 했고, 이 분리가 §7의 승인 설계를 성립시킨다.
- **모든 프레임 객체는 알려지지 않은 필드를 거부한다.** 오탈자 필드가 조용히 무시돼 서버가 빈 값으로 처리하는 실패를 파싱 시점 에러로 만든다. `params`·`payload`는 의도적으로 열린 필드이고 그 검증은 각 메서드가 진다 — **열려 있다는 사실 자체를 여기 적어 두는 이유는, 적지 않으면 다음이 그 자리를 검증된 것으로 읽기 때문이다.**
- **첫 프레임은 반드시 핸드셰이크다.** 서버는 프로토콜 버전이 정확히 일치할 때만 수락하고, 아니면 협상·다운그레이드 없이 연결을 닫는다. 소비자가 같은 저장소에서 오므로 버전이 갈리는 유일한 경우는 브라우저가 낡은 자산을 캐시한 것이고, 그때 옳은 처리는 재협상이 아니라 새로고침이다.
- **버전은 사람이 올린다.** 자동 증가·생성을 두지 않는다.

**이 프레임 셋은 전송을 모른다.** `Frame` 유니온의 어느 타입에도 전송 이름이 나타나지 않으며, 그것이 §2.1의 판정을 되돌릴 수 있게 하는 성질이다. 오늘의 전송 바인딩은 §2.1이 정한 SSE + POST이고, 거기서 이 절의 두 항은 이렇게 착지한다 — **버전은 스트림을 여는 요청이 싣고 불일치는 스트림이 열리기 전에 HTTP 상태로 거부된다**(연결을 닫는 것보다 강하다). **핸드셰이크 응답은 스트림의 첫 `ServerEventFrame`이다.**

## 7. 승인 왕복 — 연결이 아니라 프로세스에 귀속한다 (2026-08-19 확정)

**이 절이 이 설계의 유일한 진짜 난점이었다.** `CORE-INTERFACE.md` §7의 승인 훅은 Promise를 반환하고 §9 불변 조건 4가 그 훅을 우회하는 도구 실행을 금지한다. 승인자가 원격 브라우저면 그 Promise가 네트워크 왕복을 기다리게 되는데, 그 사이 연결이 끊기면 무엇이 되는지가 CLI에서는 물어질 수 없던 물음이다.

**답은 레퍼런스에 있었고 셋으로 요약된다:**

1. **코어는 승인을 모른다.** 레퍼런스의 에이전트 코어에는 승인 전용 타입이 없고, 사람을 기다리는 것은 도구 실행 Promise가 늦게 resolve되는 것으로만 표현된다. **코어 관점에서 느린 도구 호출과 사람 승인 대기는 구분 불가능하다.** 우리도 그렇게 한다 — `AgentEvent`에 승인 이벤트를 더하지 않는다(§5 규칙 1·3의 귀결).
2. **승인은 연결이 아니라 프로세스의 대기 레지스트리에 귀속한다.** 요청을 만든 연결이 사라져도 레코드는 남고, 붙어 있는 아무 클라이언트나 응답할 수 있다.
3. **아무도 응답하지 않으면 타임아웃으로 거부한다.** 만료의 기본값은 거부이지 허용이 아니다.

**계약**

```typescript
type PendingApproval = {
  readonly id: string;
  readonly display: string;        // 게이트가 만든 표시 문면. 서버가 가공하지 않는다
  readonly requestedAt: number;
  readonly expiresAt: number;
};

/** 만료의 기본값은 거부다. 무응답이 허용으로 읽히는 경로는 존재하지 않는다 */
type ApprovalOutcome = { readonly decision: "allow" | "deny"; readonly resolvedBy: "client" | "timeout" };
```

- **연결이 끊겨도 대기 중인 승인은 취소되지 않는다.** 재접속하거나 다른 탭이 붙으면 대기 목록을 그대로 받는다.
- **대기 목록은 핸드셰이크 응답에 실린다** — 붙자마자 무엇이 답을 기다리는지 알아야 한다.
- **표시 문면은 가공 없이 전달한다.** `CLI-INTERFACE.md` §9가 승인 프롬프트에 대해 같은 것을 요구했고, 소비자가 둘이 되었다고 그 계약이 갈라지지 않는다.
- **타임아웃 값은 세부다**(구현 시 확정). 계약인 것은 **유한한 만료가 존재한다는 것**과 **만료가 거부라는 것** 둘뿐이다.

## 8. 재접속과 상태 복구

- **이벤트를 재생하지 않는다.** 서버는 연결마다 이벤트에 단조 증가 번호를 매기고, 클라이언트는 번호가 건너뛰면 갭으로 판정한다. §2.1의 전송에서 이것은 **`Last-Event-ID` 요청 헤더를 읽지 않는다**로 착지한다 — SSE가 그 자리에 재생 기제를 마련해 두었으므로, 안 쓰는 것이 곧 이 계약이고 그래서 **명시적으로 적는다.** 적지 않으면 다음이 "표준이 주니까 켠다"로 읽는다.
- **갭의 처리는 재접속이다.** 부분 재전송 API를 두지 않는다 — 핸드셰이크 응답이 현재 상태 스냅샷(활성 세션·트랜스크립트·대기 중 승인)을 싣고, 그것이 곧 복구다. 버퍼를 들고 재전송하는 설계는 "얼마나 들고 있을 것인가"라는 답 없는 물음을 만든다.
- **클라이언트 연결이 끊겨도 진행 중인 런은 계속된다.** 런은 연결이 아니라 프로세스에 속한다. 레퍼런스도 소켓 종료 처리에서 런을 중단시키지 않으며, 우리 §7의 승인 귀속이 같은 원리의 다른 사례다.
- **프로세스 종료는 다르다.** `serve`가 내려가면 진행 중인 런은 중단되고 그 사실이 트랜스크립트에 남는다 — `CORE-INTERFACE.md` §9 불변 조건 2가 요구하는 완결된 이벤트 시퀀스가 여기서도 그대로 걸린다.
- **느린 소비자를 무한정 버퍼링하지 않는다.** 상한을 넘으면 연결을 닫는다. 닫힌 클라이언트는 재접속으로 스냅샷을 다시 받는다 — 위 규칙이 이미 그 경로를 정의했으므로 별도 처리가 필요 없다.

## 9. 화면 자산 — 반입 금지를 좁힌다 (`DISTRIBUTION.md` §10 미결 소비 · 2026-08-19 확정)

**`DISTRIBUTION.md` §10이 2026-08-17에 디자인 시스템 산출물을 아무것도 반입하지 않기로 닫았다. 이 절이 그 판정을 좁힌다 — 뒤집는 것이 아니다.**

그 판정이 든 배제 근거는 셋이었고 **이번에 둘이 소멸한다**:

| 그때의 근거 | 지금 |
|---|---|
| 토큰만 반입하는 갈래는 소비자가 0이다 (CLI가 터미널 제어뿐이라 CSS가 쓰일 자리가 없다) | **소멸** — 웹 UI가 그 소비자를 처음 만든다 |
| 웹 UI 착수 자체가 `ARCHITECTURE.md` §2.8에서 MVP 제외로 닫혀 있다 | **소멸** — 이번 개정이 연다 |
| 빌드 스텝 없음(`TECH-STACK.md` §2)과 의존성 예산 게이트가 프런트엔드 반입을 막는다 | **유지** — 아래 제약이 이것을 지킨다 |

**그래서 좁힌 판정은 이렇다:**

- **반입한다. 단 빌드 없는 형태만.** 브라우저가 직접 로드하는 것만 들어온다(표준 모듈 문법 JavaScript + 순수 CSS + HTML). 번들러·트랜스파일러·프레임워크 런타임을 들이지 않는다. **`TECH-STACK.md` §2는 개정되지 않는다** — 소스가 곧 실행물이라는 성질이 프런트엔드에서도 그대로 성립한다.
- **손으로 다듬지 않는다.** 원래 판정의 취지가 그것이었다 — 시안을 손질해 자산화하면 정본이 둘이 된다. 반입물은 외부 도구의 출력 그대로이고, 고칠 것이 있으면 **프롬프트를 고쳐 다시 뽑는다.**
- **정본은 여전히 원격이다.** 이 레포가 쥐는 것은 시안 프롬프트와 토큰이고, 반입된 화면 자산은 **파생물**이다. 파생물과 정본이 갈리면 정본이 이긴다.
- **재생성 가능성이 계약이다.** 반입된 자산은 어느 프롬프트에서 나왔는지를 기록으로 갖는다. 그것이 없으면 다시 뽑을 수 없고, 다시 뽑을 수 없으면 그 순간 손으로 유지되는 자산이 된다 — 원래 판정이 막으려던 바로 그 상태다.
- **서버는 이 자산을 정적 파일로 서빙한다.** 템플릿 엔진·서버 사이드 렌더링을 두지 않는다.

## 10. VPS 상주 (`DISTRIBUTION.md` §10 미결 소비 · 2026-08-19 확정)

**상주는 이 문서 §3이 정의한 `serve` 그대로이고, VPS라고 달라지는 것이 없다.**

- 프로세스 수명은 systemd가 진다. 이 레포는 유닛 파일을 자산으로 반입하지 않고 절차만 문서화한다 — 머신마다 경로가 다르고, 그것을 자산화하면 낡는다.
- **VPS에서도 루프백 고정이다**(§4). 원격 접근은 SSH 터널이며, 이는 VPS 시나리오에서 오히려 더 중요하다 — 공인 IP를 가진 호스트에서 바인드 주소를 여는 것과 랩톱에서 여는 것은 위험이 다르다.
- **크리덴셜 취급은 `SAFE-DEFAULTS.md` §3 그대로다.** 이 문서가 새 시크릿을 만들지 않는다 — 인증을 설계하지 않았으므로(§4) 저장할 토큰이 없다. **레퍼런스가 토큰과 서명 개인키를 평문으로 저장하는 자리에 우리는 저장할 것 자체가 없다.**
- 실행 트리가 워크스페이스일 때의 고지(`DISTRIBUTION.md` §6)는 `serve`에도 그대로 걸린다.

## 12. 미결 — 이 문서가 정하지 않은 것

- ~~**WebSocket 구현 수단**~~ — **2026-08-20 해소(§2.1).** WebSocket을 쓰지 않기로 정해 물음 자체가 사라졌다. 이 미결은 *"직접 파싱 대 의존성"*의 **이분법으로 적혀 있었고 그 이분법이 틀렸다** — 셋째 갈래(SSE + POST)가 둘의 비용을 다 안 내고 §6의 프레임 셋을 그대로 싣는다. 예산은 §2.2가 들고, 그 예산이 무엇을 강제하지 **못하는지**는 §2.3이 든다.
- **정적 자산의 서빙 경로 판정** — §2.2가 `node:fs`를 열었고 §9가 *"서버는 이 자산을 정적 파일로 서빙한다"*를 요구하는데, **URL 경로에서 파일 경로를 어떻게 얻는지**가 정해지지 않았다. 경로 조립이면 traversal이 검사 대상이 되고, 고정 매니페스트면 그 대상 자체가 없어진다 — §4가 바인드에서 쓴 수단과 같은 갈림이다. 이 물음은 아래 화면 자산 배치 항과 **입력이 겹치되 다른 판정**이다(저쪽은 배치·기록 형식, 이쪽은 서빙 계약).
- **포트 번호와 타임아웃 수치** — 세부. 기본값이 존재한다는 것이 계약이고 값은 아니다.
- **메서드 표의 초기 목록** — 프롬프트 제출·중단·개입·승인 응답·세션 조회가 최소 집합이나, 정확한 이름과 인자는 구현 시 확정.
- **CLI와 `serve`가 같은 세션을 동시에 여는 경우** — `SESSION-STORE.md` 미결이 두 CLI에 대해 이미 연 갈래를 이 문서가 **넓힌다**. 그 문서가 세션 락을 두지 않기로 판정했으므로 이 문서도 락을 두지 않고, **순서 보장은 여전히 정의되지 않는다.** 락 도입은 `SESSION-STORE.md`의 확정 판정을 뒤집는 일이라 별도 사이클이다. **트리거**: 두 소비자가 같은 세션을 동시에 쓰는 사례가 실제로 관측될 때.
- **화면 자산의 디렉터리 배치와 재생성 기록의 형식** — §9가 재생성 가능성을 계약으로 요구하되 그것을 어디에 어떤 형식으로 적을지는 정하지 않았다.
- **브라우저가 낡은 자산을 캐시했을 때의 안내 문면** — §6이 버전 불일치를 연결 종료로 처리하기로 했으나 사용자가 무엇을 보는지는 세부다. 침묵하지 않는다는 것만이 계약이다(`ARCHITECTURE.md` §2.6).
