# 메모리 — 프로즌 스냅샷

**이 문서의 지위**: neo-agent 메모리의 **정본 설계**다. 작성일 2026-08-09.
`ARCHITECTURE.md` §2.4가 확정 원칙에서 이미 전제한 "메모리는 세션 시작 시 프로즌
스냅샷으로 주입한다"의 실장 계약이며, MVP 이후 **네 번째 확장**이다(압축 §2.14 · 검색
§2.15 · 웹/샌드박스 §2.16 다음).

**불변(경계·계약)** — 저장 위치와 그것이 만드는 격리(§2), 스냅샷의 동결 시점과 주입
지점(§3), 쓰기 표면이 `remember` 1종·1액션이라는 것(§4), 오염 런 거부(§5), 예산이
유계이고 초과 시 모델이 아니라 사용자가 정리한다는 것(§6).

**조정 가능(구현 시)** — 문자 상한의 구체 수치(§6), 도구 설명문·에러 텍스트의 문구,
`/memory` 하위 명령의 이름과 표시 형식(§7).

---

## 1. 왜 지금, 그리고 왜 이 형태인가

**왜 지금** — 이 설계는 트리거 발동이 아니라 **격차 해소**다. `ARCHITECTURE.md` §2.4가
확정 원칙 안에서 메모리의 동작(프로즌 스냅샷·세션 중 쓰기는 디스크만)을 이미 규정하고,
`REUSE-MAP.md` §4가 "파일 기반 프로즌 스냅샷(hermes 기본형)만으로 시작"으로 방향까지
판정해 뒀는데, 정본 문서도 코드도 없었다. **원칙이 앞서 있고 설계만 빈 유일한 영역이었다.**

**왜 이 형태 — 읽기는 이미 공짜고, 문이 필요한 것은 쓰기뿐이다.**

이 한 줄이 설계의 대부분을 결정한다. 스냅샷이 시스템 프롬프트에 실려 있으므로 모델은
**도구를 부르지 않고** 메모리 전체를 이미 보고 있다. hermes·OpenClaw가 가진 조회·검색·
recall 표면은 우리에게 **해결할 문제가 없다**(§8 축소표). 남는 것은 "무엇을 새로 적을 것인가"
하나이고, 그래서 도구는 1종·1액션이다.

**대칭**: 사용자는 에디터로 메모리 파일을 자유롭게 편집한다. 에이전트는 문 하나를 통과한다.
이 비대칭이 우연이 아니라 §2가 설명하는 구조의 귀결이다.

## 2. 저장 위치 — denylist 재사용이 격리를 만든다

```
~/.neo-agent/memory/MEMORY.md      ← 메모리 정본. 사용자 편집 가능
```

**파일 하나로 시작한다.** hermes는 `MEMORY.md`(에이전트 관찰)와 `USER.md`(사용자 프로필)를
분리하고 예산도 따로 잡는다. 우리는 나누지 않는다 — 분리의 실익은 "누가 쓴 것인가"를
파일 경계로 표현하는 것인데, 우리 설계에서는 **양쪽이 같은 파일에 쓴다**(사용자는 에디터,
에이전트는 `remember`). 파일을 나누면 예산이 둘로 늘고 도구에 `target` 인자가 생기는데,
얻는 것이 마크다운 섹션 제목으로 얻을 수 있는 것과 같다.
> 분리 트리거: 사용자 프로필을 **에이전트가 갱신하기 시작**할 때. 그때는 "사용자에 관한
> 사실"과 "작업에 관한 메모"의 신뢰도·수명이 달라지므로 예산도 갈라야 한다.

### 2.1 왜 이 경로인가 — 새 기계 없이 우회로가 닫힌다

`TOOLS-INTERFACE.md` §3의 크리덴셜 denylist는 **`~/.neo-agent/` 전체**를 대상으로 하고,
**게이트와 무관하게 도구 자체가 강제한다**(승인으로도 해제 불가). 메모리를 이 아래 두면:

- `read_file`·`write_file`·`edit_file`이 메모리 파일에 **도달할 수 없다.** 따라서
  **`remember`가 에이전트에게 유일한 문**이고, 그 문이 예산(§6)과 표시(§7)를 강제한다.
- 이것은 `WEB-ACCESS.md` §1이 세운 구조 — *"감사 가능한 문 하나를 만들고 나머지를 닫는다"* —
  와 같은 형태를 **기존 denylist 재사용으로** 얻은 것이다. 새 계층·새 검증기·새 설정 키가
  없다(§2.5 사다리 1단).

**워크스페이스에 두는 대안은 검토가 아니라 배제 대상이다.** 거기 두면 `write_file` 한 번으로
예산·표시·오염 정책이 전부 우회되고, 다음 세션 시스템 프롬프트에 임의 내용이 실린다.
쓰기 표면을 좁히는 이 설계 전체가 무의미해진다.

**부수 귀결(의도한 것)**: 에이전트는 자기 메모리를 **도구로 읽을 수도 없다.** 읽을 필요가
없으므로(스냅샷이 프롬프트에 있다) 손실이 아니고, "쓰기만 되고 읽기는 프롬프트로"라는
비대칭이 스냅샷 동결과 정합한다 — 도구로 읽으면 라이브 상태가 보여 프롬프트와 어긋난다.

### 2.2 파일이 없을 때 · 못 읽을 때

| 상황 | 동작 | 근거 |
|---|---|---|
| 파일·디렉터리 없음 | 빈 메모리로 정상 기동. 파일을 미리 만들지 않는다 | 첫 `remember`가 만든다. 빈 파일은 "메모리가 있다"는 거짓 신호 |
| 파일 있고 읽힘 | 스냅샷 구성 | — |
| **파일 있고 못 읽음** | **기동 실패로 종료** — 로드 함수는 **던지고**, 종료는 CLI가 한다(2026-08-09 명확화) | hermes `_read_failed_error`의 계승. 빈 것으로 읽고 첫 쓰기에서 전체를 덮으면 **메모리가 조용히 소실된다**. `CLI-INTERFACE.md` §2 "시작 단계 실패는 원인과 다음 행동을 담은 에러로 종료"에 해당 |
| 권한이 600이 아님 | **경고만, 진행** | 메모리는 시크릿이 아니다. 크리덴셜의 fail-closed(SAFE-DEFAULTS §3)와 **의도적으로 다르다** — 같게 다루면 노출 위험이 다른 것에 같은 마찰을 물린다 |

`~/.neo-agent/memory/`가 심볼릭 링크면 **거부한다**(OpenClaw `root-memory-files.ts`의
심볼릭 링크 거부 계승). denylist는 경로로 판정하므로, 링크로 밖을 가리키면 "denylist 안에
있으면서 실체는 밖"이 되어 §2.1의 격리가 깨진다.

## 3. 스냅샷 — 동결 시점과 주입 지점

### 3.1 두 상태를 나란히 든다

hermes에서 그대로 가져오는 계약이다(`memory_tool.py:148-175`):

| 상태 | 정본 | 소비자 |
|---|---|---|
| **스냅샷** | 세션 시작 시 디스크에서 읽은 내용. 세션 중 **절대 불변** | 시스템 프롬프트 |
| **디스크** | `remember`가 즉시 반영. 세션 중 갱신됨 | 도구 응답, 다음 세션의 스냅샷 |

**도구 응답은 디스크 상태를 반영하고 시스템 프롬프트는 스냅샷을 반영한다.** 이 분리가
`ARCHITECTURE.md` §2.4(프롬프트 캐시 불가침)의 실체다. 모델은 `remember` 결과로 저장 성공을
알지만, **자기가 방금 쓴 내용이 시스템 프롬프트에 나타나지는 않는다** — 도구 설명문이 이를
명시한다(§4.2). 명시하지 않으면 모델이 프롬프트에서 자기 메모를 찾다 없다고 판단해 다시 쓴다.

### 3.2 주입 지점

`packages/cli/src/system-prompt.ts`의 `buildSystemPrompt()`가 스냅샷을 인자로 받아
**말미에 붙인다.** CLI가 조립 지점이므로(`CLI-INTERFACE.md` §1) 코어는 메모리의 존재를
모른다 — 검색(§2.15)과 같은 관계이고, 코어 공개 표면 추가는 **0**이다.

```
시스템 프롬프트 = [고정 스캐폴드] + [메모리 블록(있을 때만)]
```

- **블록은 내용이 있을 때만 붙는다.** 빈 메모리에 빈 헤더를 붙이면 모델에게 "메모리 기능이
  있는데 비어 있다"가 아니라 잡음이 된다.
- **블록은 말미에 온다.** hermes는 volatile band 배치에 공을 들이지만(`system_prompt.py:505`)
  그건 스킬·타임스탬프로 프롬프트가 턴마다 변하는 구조의 대응이다. 우리 시스템 프롬프트는
  세션 내내 한 바이트도 안 변하므로 **배치가 캐시에 영향을 주지 않는다.** 말미인 이유는
  캐시가 아니라 가독성이다.
- 블록 안의 항목 순서는 **파일 순서 그대로**다. 정렬·중복 제거를 하지 않는다 — 사용자가
  에디터에서 만든 순서가 사용자의 의도이고, 우리가 재배열하면 파일과 프롬프트가 어긋난다.

### 3.3 압축과의 관계 — 분기는 스냅샷을 물려받는다

**압축으로 세션이 분기해도 스냅샷은 재읽기하지 않는다.** 부모 세션의 스냅샷을 그대로
물려준다.

**근거 셋**:
1. **이미 코드가 그렇다** — `packages/cli/src/compact.ts`가 `systemPrompt: deps.systemPrompt`로
   같은 문자열을 넘긴다. 이 결정은 **구현 변경 0**이다.
2. **"프로즌"이 세션 단위라는 말의 의미가 압축으로 흔들리면 안 된다.** 압축은 사용자가
   시작한 새 대화가 아니라 같은 대화의 연속이다(`COMPACTION.md` — 사용자에게 체인은 하나의
   대화다). 여기서 메모리가 바뀌면 **사용자가 모르는 시점에 시스템 프롬프트 내용이 변한다.**
3. **hermes가 반대 경로의 대가를 실증했다.** hermes는 압축에서 프롬프트를 재빌드하므로
   `_cached_prompt_reflects_builtin_memory()`(`conversation_compression.py:210`)라는 판정기가
   필요하다 — "캐시된 프롬프트가 현재 메모리를 반영하는가"를 렌더링된 블록의 문자열 포함
   여부로 검사하고, 비워진 타깃의 잔여 헤더까지 확인한다. `MEMORY_BLOCK_HEADERS`를 모듈
   상수로 export하는 이유가 이 검사다. **우리 구조에는 이 판정기가 필요한 상황이 없다.**

**귀결(수용한다)**: 세션 중에 쓴 메모리는 그 세션에서 **압축을 거쳐도** 프롬프트에 나타나지
않고, **다음 세션부터** 반영된다. 이는 §2.4의 "프롬프트 상태를 바꾸는 명령은 기본이 지연
무효화(다음 세션부터)"와 정확히 같은 규칙이며, 예외가 아니라 이행이다.

## 4. 쓰기 표면 — `remember` 1종·1액션

### 4.1 계약

```ts
/** packages/memory — 신설. 이 패키지의 불변식: ~/.neo-agent/memory/ 안에만 쓴다 */
export interface MemoryToolDeps {
  /** 메모리 디렉터리. CLI가 배선한다(설정 표면이 아니다 — §9 M-2 닫힘) */
  readonly dir: string;
  /**
   * 이 런이 오염됐는가. 호스트가 `() => gate.isTainted()`로 배선한다.
   * **설정 표면이 아니라 호스트가 배선하는 함수 인자**이며, WEB-ACCESS §4가
   * `verify`·`resolveHostname` 주입을 승인한 것과 같은 성격이다.
   */
  readonly isRunTainted: () => boolean;
}

/** 모델에게 노출되는 유일한 메모리 표면 */
export function createRememberTool(deps: MemoryToolDeps): AgentTool;

/** 인자 스키마 — 닫힌 객체. 필드 하나가 계약이다 */
const rememberInput = z.object({
  content: z.string().min(1).max(MEMORY_ENTRY_MAX_CHARS),
});
```

**`content` 하나뿐이고 경로 인자가 없다.** 그래서 이 도구에는 **경로 traversal 표면이
아예 없다** — 대상 파일은 `deps.dir`로 고정이고 모델 입력에서 파생되지 않는다.
`TOOLS-INTERFACE.md` §3의 `resolve()` 봉쇄 판정이 이 도구에 없는 이유이고, 없어도 되는 이유다.

**추가·수정·삭제 중 추가만 있다.** `replace`/`remove`/`batch`/`target`은 전부 없다(§8).

### 4.2 도구 설명문에 반드시 있어야 하는 것

*"도구 결과는 프롬프트다"*(REUSE-MAP §2.3)의 적용이다. 문구는 재량이지만 **아래 세 사실은
계약**이다 — 빠지면 모델이 예측 가능한 방식으로 오작동한다:

1. **저장된 내용은 다음 세션부터 시스템 프롬프트에 나타난다.** 지금 프롬프트에는 안 나타난다.
   → 없으면 모델이 프롬프트에서 자기 메모를 찾다 실패하고 **같은 것을 반복 저장**한다.
2. **수정·삭제는 사용자가 한다.** 모델에게 정리 수단이 없다.
   → 없으면 모델이 존재하지 않는 `forget`·`replace`를 호출하려 시도한다.
3. **예산이 유계이고 가득 차면 저장이 실패한다.** 실패는 정상 상태이며 대화를 막지 않는다.
   → 없으면 모델이 실패를 자기 잘못으로 읽고 재시도 루프에 들어간다(hermes #42405).

### 4.3 결과 계약

| 상황 | `isError` | 반환 텍스트가 담을 것 |
|---|---|---|
| 저장 성공 | `false` | 저장됨 + **남은 예산** + "다음 세션부터 반영" |
| 예산 초과 | `true` | 현재 사용량·상한 + `/memory`로 사용자가 정리해야 함 + **재시도하지 말라** |
| 오염 런 (§5) | `true` | 오염 사실 + **사용자에게 직접 제안하라** |
| 중복 (기존 항목과 동일) | `false` | 이미 있음. **성공으로 보고한다** — 결과 상태가 의도와 같다 |
| 디스크 쓰기 실패 | `true` | 원인 + 저장되지 않았음을 명시 |

> **위 표의 `isError` 열은 결과의 성격을 가리키는 것이지 필드 이름이 아니다** (2026-08-09
> 각주 추가 — QA-A 지적). **`ToolResult`에 `isError` 필드는 없다.** 코어 계약은 *"실패는
> throw, 루프가 변환한다"*이므로(`CORE-INTERFACE.md` §6), `isError: true` 행들은 구현에서
> **throw로 번역**되고 값으로 돌아오는 것은 성공 2행(저장·중복)뿐이다.

`ToolResult.source`는 **항상 `"local"`**이다. 메모리는 디스크에서 오고, 오염 전파의
방향은 반대다(오염이 메모리 쓰기를 막지, 메모리가 런을 오염시키지 않는다).

**쓰기는 원자적이다** — 임시 파일 + rename. 부분 기록된 메모리 파일은 다음 세션 기동을
실패시키므로(§2.2) 여기서 막는다.

### 4.4 등록

`remember`는 **항상 등록된다**(조건부 아님 — `shell`과 다르다). 도구 목록 말미에 온다.
`CLI-INTERFACE.md` §2의 도구 등록 순서 고정 규칙 그대로이며, 시작 화면의 도구 목록에
나타난다.

패키지를 새로 만드는 이유: `packages/tools`의 불변식은 *"워크스페이스 경계를 강제하고
`~/.neo-agent/`를 거부한다"*이고, 메모리 도구는 **정확히 그 거부된 디렉터리 안에 쓰는
유일한 도구**다. 같은 패키지에 두면 패키지의 불변식이 거짓이 되어 예산 게이트로 표현할
수 없다. `packages/memory`의 예산: `node:fs` 허용, **네트워크·`child_process`·`node:sqlite`
금지**(`packages/web`·`packages/tools`의 대칭 규칙과 같은 형태).

## 5. 오염 정책 — 오염된 런에서는 쓰지 못한다

**`isRunTainted()`가 참이면 `remember`는 저장하지 않고 오염을 사유로 실패한다.**

**왜 승인이 아니라 거부인가** — 승인 프롬프트는 *"이 행동을 지금 허용할까"*를 묻는 장치인데,
메모리 쓰기의 효과는 지금이 아니라 **다음 세션부터의 시스템 프롬프트**에 나타난다. 즉 승인
단위(호출 1회)와 효과 범위(이후 모든 세션)가 어긋난다. 웹 페이지가 *"이것을 기억해 두라"*고
지시했을 때 사용자가 그 순간 승인 버튼을 누르는 것은 **자기가 무엇을 승인했는지 알 수 없는
승인**이다. 거부하면 모델은 사용자에게 말로 제안하게 되고, 그때는 사용자가 대화 문맥 안에서
판단한다.

**이것은 새 계층이 아니다.** `WEB-ACCESS.md` §5가 오염을 "기존 기계의 재사용"으로 설계한
것과 같은 자리이며, 강제 지점은 게이트가 아니라 **도구 자신**이다 — `TOOLS-INTERFACE.md`
§3의 크리덴셜 denylist가 "게이트가 꺼져 있어도 동작한다"는 것과 같은 이유로, 게이트 모드가
`off`여도 이 거부는 유효하다.

**게이트 측 필요 변경 2건**:

1. **`ApprovalGateHandle.isTainted(): boolean` 신설** (가산적) — 오염 상태는 이미 게이트가
   들고 있고 쓰기 메서드만 노출돼 있다. 읽기를 열 뿐이고 파이프라인 출구·계층은 늘지 않는다.
2. **게이트 도구 분류에 `memoryWrite` 추가** (`APPROVAL-GATE.md` §3·§4 개정) —
   **미등록 도구는 fail-closed로 항상 프롬프트**이므로, 등록하지 않으면 메모리 저장마다
   푸시버튼이 뜬다. 판정은 **자동 허용**이다.

**왜 자동 허용이 옳은가** — 승인 매트릭스(SAFE-DEFAULTS §1)가 승인을 요구하는 것은
**되돌리기 어렵거나 범위를 알 수 없는 행동**이다. 메모리 쓰기는 둘 다 아니다: 몇 KB 상한의
append이고(§6), 사용자가 에디터·`/memory`로 언제든 지울 수 있고, **CLI가 도구 호출과 결과를
그대로 렌더링하므로 사용자가 저장된 내용을 본다.** §2.6이 요구하는 것은 가시성이고
가시성은 이미 성립한다 — 마찰은 요구되지 않았다. `write_file`이 승인 대상인 이유(비가역
덮어쓰기)가 여기엔 없다.

> 이 두 변경은 지난 사이클의 `webFetch` 분류 누락과 **같은 종류의 계약 확장**이다. 그때
> 얻은 교훈대로 설계 단계에서 발견해 명시한다 — 구현 중에 발견하면 블로커가 된다.

## 6. 예산 — 유계이고, 정리는 사용자가 한다

| 상한 | 설계값 | 근거 |
|---|---|---|
| 파일 전체 | **4,000자** | hermes 2,200(+user 1,375)와 OpenClaw ~12KB/파일 사이. 매 API 호출에 실리는 비용이므로 작게 시작한다 |
| 항목 하나 | **400자** | 한 항목이 예산의 10%를 넘으면 그건 메모리가 아니라 문서다 |

두 수치는 **구현 시 실측으로 확정한다**(§9 M-1). 웹 fetch 상한을 실측 50건으로 2MB→4MB로
고친 전례와 같은 처리다.

**단, 이번 실측은 전례와 범위가 다르다** (2026-08-09 사용자 확정, 플랜 D-2). 웹 상한은
실제 조회 50건으로 곧바로 확정할 수 있었지만, 메모리의 **진짜 비용은 토큰**인데 우리에게
토크나이저 의존성이 없고(SDK가 번들하지 않는다) API 키도 없어 `count_tokens`를 부를 수
없다. 그래서 **문자 길이 분포만 실측하고 토큰은 미측정으로 명시한다** — 실측 리포트가
"무엇을 재지 못했는가"를 함께 적는 것이 계약이다. 못 잰 것을 잰 것처럼 쓰지 않는 것은
정직한 UA 비용(403 13%)을 기록만 하고 우회하지 않은 것과 같은 규율이며, `ARCHITECTURE.md`
§2.6의 적용이다. **토큰 실측 트리거**: API 키 확보 후, 또는 프롬프트 비용이 실사용에서
관측될 때.

**초과 시 모델이 정리하지 않는다.** 저장이 실패하고, 사유와 `/memory` 안내가 결과에 실린다.

**왜** — hermes는 반대로 갔고 대가를 문서화했다: 예산이 꽉 차면 모델에게 통합(consolidation)을
지시하는데, 실패한 replace/add가 턴을 반복해 **턴 예산을 소진하고 사용자 답변을 삼킨**
사고가 났다(issue #42405). 대응으로 턴당 실패 상한 3을 달았지만, 그 상한의 존재 자체가
**메모리 정리를 모델의 일로 만든 것이 잘못이었다는 증거**다. 정리는 판단이 필요한 일이고,
무엇을 기억할 가치가 있는지는 사용자가 안다.

**§2.6과의 관계**: "저장 실패"는 silent failure가 아니다 — 모델은 결과를 받고 사용자는
렌더링된 결과를 본다. 가장 나쁜 경로는 조용히 오래된 항목을 밀어내는 FIFO 회전이다.
**회전은 채택하지 않는다** — 사용자가 적은 항목이 예고 없이 사라진다.

## 7. 사용자 표면

### 7.1 시작 시 표시

세션 시작 화면에 **주입된 메모리의 규모**를 한 줄로 표시한다 — 항목 수와 사용량
(예: `메모리 7항목 · 1,240/4,000자`). 전문을 쏟지 않는다.

**왜 계약인가** — 시스템 프롬프트에 무엇이 들어갔는지가 화면에 안 보이면, 사용자는 자기
에이전트가 무엇을 알고 있다고 믿는지 모른 채 대화한다. `SANDBOX.md`가 `sandbox: "off"`의
매 기동 표시를 계약으로 삼은 것과 같은 판단이다(문구는 재량, **표시 여부가 계약**).
메모리가 비어 있으면 이 줄은 나오지 않는다.

### 7.2 `/memory` — 큐레이션은 여기 하나로 모인다

`CLI-INTERFACE.md` §5의 슬래시 중앙 레지스트리에 등록한다.

| 명령 | 동작 |
|---|---|
| `/memory` | 전체 표시 — 항목별 번호 + 사용량 + **파일 경로**. **스냅샷이 아니라 디스크 현재 상태** |
| `/memory remove <n>` | 항목 삭제 |

**`/memory edit`은 두지 않는다 — 경로 표시로 대체한다** (2026-08-09 사용자 확정, 플랜 D-1).
초판은 `$EDITOR`로 파일을 여는 `/memory edit`을 "사용자의 정리 수단 정본"으로 규정했으나,
구현 플랜의 실측이 **현재 예산에서 구현 불가**임을 드러냈다: `CLI-INTERFACE.md` §1이
`node:child_process`를 CLI 금지 모듈로 두고 있고(예산 게이트가 강제) 그 근거는 "프로세스
스폰은 tools(executor)의 본업"이다. 셸 도구 경유는 더 나쁘다 — 컨테이너 안이라 편집기도
TTY도 없고 승인 게이트를 탄다.

**경계 하나를 편의 한 단계에 내주지 않는 쪽을 택했다.** 잃는 것은 명령 한 번이고, §7.2의
실질 — *사용자가 자기 에디터로 편집하는 것이 큐레이션 정본* — 은 **경로만 알려주면 그대로
성립한다.** 그래서 `/memory`가 파일 경로를 함께 낸다.

- **`/memory` 표시는 디스크를 읽는다.** 세션 중 `remember`로 저장된 것이 여기서는 보이고
  프롬프트에는 없다 — 그 차이가 §3.1의 두 상태이고, 표시에 "이 세션의 프롬프트에는
  반영되지 않았음"을 함께 낸다.
- **`/memory add`는 두지 않는다** — 사용자는 대화로 "이거 기억해둬"라고 말하면 되고
  (모델이 `remember`를 부른다), 직접 쓰고 싶으면 표시된 경로를 에디터로 연다. 명령을
  늘리면 같은 일을 하는 경로가 셋이 된다.
- 편집·삭제 후 **다음 세션부터 반영**된다. `/memory` 결과가 이를 명시한다.
- 하위 동작은 **명령 1개 + 인자**로 둔다 — 슬래시 레지스트리의 닫힌 목록을 하나의
  관심사로 셋 늘리지 않는다(`CLI-INTERFACE.md` §5).

### 7.3 항목 경계 — 최상위 불릿 하나가 항목 하나

파일은 **사람이 읽고 고치는 마크다운**이고, `remember`는 `- ` 로 시작하는 최상위 불릿을
파일 말미에 **append**한다.

- **항목 = 최상위 `- ` 불릿 한 개.** 항목 수 표시(§7.1)와 `/memory remove <n>`의 번호가
  이것을 센다.
- **불릿이 아닌 줄(제목·설명·빈 줄)은 그대로 보존되고 항목으로 세지 않는다.** 사용자가
  파일에 구조를 준 것을 우리가 지우지 않는다.
- **예산(§6)은 파일 전체 문자 수로 센다** — 프롬프트에 실리는 것이 파일 전체이므로,
  불릿만 세면 예산이 실제 비용을 반영하지 않는다.
- **로드 시점에 파일을 고치지 않는다** — 정렬·중복 제거·형식 교정 전부 없다(hermes는
  로드할 때 중복을 제거한다). 중복 검사는 **쓰기 시점에만** 하고(§4.3), 이미 있으면
  추가하지 않는다. 사용자의 파일을 우리가 다시 쓰는 경로를 만들지 않는 것이 규칙이다.

이 형식 선택이 hermes의 **드리프트 문제를 소멸시킨다**(§8) — 구분자(`\n§\n`) 기반 파싱이
아니라 append이므로, 사용자가 파일에 무엇을 해도 "툴의 파서를 왕복하지 못하는 내용"이라는
상태가 생기지 않는다.

### 7.4 파싱·경계의 확정 판정 (2026-08-09 — QA-A 판정 A-1~A-18)

계약 테스트를 선행 작성하며 드러난 경계 18건이다. **하나를 빼면 전부 이미 쓰여 있는
원칙의 적용이고, 새 원칙은 없다** — 그래서 표로 닫는다. 근거 열이 비어 보이는 항목은
없다: 근거 없이 정한 것은 하나도 없다는 뜻이다.

| # | 경계 | 판정 | 근거 |
|---|---|---|---|
| A-1 | `chars`의 단위 | **UTF-16 코드 유닛**(`text.length`) | 진짜 비용은 토큰인데 우리는 못 잰다(§6). 코드 유닛과 코드 포인트 중 **어느 쪽이 토큰에 더 가깝다고 말할 근거가 없으므로**, 판정 기준은 정확성이 아니라 **예측 가능성**이다 — JS 기본값이고 순회 코드가 필요 없다. T-009 실측 리포트가 "코드 유닛으로 쟀다"를 명시한다 |
| A-2 | 600보다 **좁은** 권한(400 등) | **경고하지 않는다** | 크리덴셜 로더가 같은 판정을 이미 내렸다(`CLI-INTERFACE.md` §4): *"판정 기준은 노출 비트(group·other)의 존재이며 `0400`처럼 더 좁은 권한은 통과한다. 더 안전하게 잠근 사용자를 거부하는 것은 계약의 목적과 반대다."* 같은 기계를 쓴다 |
| A-3 | `MEMORY.md` **파일 자체**가 심볼릭 링크 | **거부한다** (디렉터리와 동일) | §2.2가 디렉터리 링크를 거부하는 근거는 *"링크로 밖을 가리키면 denylist 안에 있으면서 실체는 밖"*인데, 이는 파일에도 **그대로** 성립한다. 디렉터리만 막고 파일을 열어두면 **막으려던 것을 막지 못한다**. 링크로 관리하던 사용자는 막히지만, 그 구성은 격리를 스스로 깬 것이고 우리가 지원한다고 말한 적이 없다 — 에러가 이유를 밝힌다 |
| A-4 | 중첩 줄이 항목 `content`에 포함되나 | **포함하지 않는다** (첫 줄만) | §7.3이 중첩 불릿을 "항목이 아니다"로 이미 배제했다. A-13과 한 쌍 |
| A-5 | 본문이 빈 `- ` 줄 | **항목으로 센다** | 규칙은 "최상위 `- ` 불릿 하나 = 항목 하나"이고 본문 유무 조건이 없다. 조건을 더하면 **파서가 내용을 해석하기 시작한다**. 그리고 `remove <n>`의 번호는 사용자가 파일에서 세는 것과 같아야 하는데, 사용자는 `- ` 줄을 본다 |
| A-6 | CRLF 파일 | **인식하되 원본은 보존**(파싱 시 `\r` 관대 처리, 새 줄은 `\n`) | 정규화하면 §7.3의 "로드 시 무수정"을 어기고, 무시하면 CRLF 사용자의 항목이 프롬프트에서 **통째로 사라진다**(침묵 실패, `ARCHITECTURE.md` §2.6) |
| A-7 | 공백만 있는 파일에 블록을 붙이나 | **붙이지 않는다** | A-8과 같은 기준 — "내용이 있다"는 **trim 후 비어 있지 않은가**이다 |
| A-8 | §3.2의 "내용"이 항목인가 파일 텍스트인가 | **파일 텍스트** | §7.3이 *"불릿이 아닌 줄은 그대로 보존되고 항목으로 세지 않는다"*고 못박는다. 블록이 싣는 것은 **메모리 파일의 내용**이지 항목 목록이 아니다 — 사용자가 제목·문단만 써 뒀는데 프롬프트에서 사라지면 사용자 의도를 도구가 삼킨 것이다 |
| A-8b | §7.1 시작 표시의 유무 판정 기준 | **문자 수**(블록 부착과 같은 기준) | A-8의 귀결로 "불릿 0개인데 텍스트가 있는 파일"이 가능해진다. 표시 유무를 **항목 수**로 판정하면 프롬프트에는 실렸는데 화면에는 아무 줄도 안 나오는 상태가 생긴다 — 그것이 §2.6이 금지하는 것이다. `메모리 0항목 · 320/4,000자`는 어긋남이 아니라 **정직한 정보**다 |
| A-9 | 중복 판정의 정규화 범위 | **앞뒤 공백만** | 넓히면 "저장했는데 안 보인다"가 생기고, 좁히면 같은 메모가 쌓인다. 판정이 모호해지는 순간 전자가 생기므로 완전 일치 쪽에 붙인다 |
| A-10 | 예산 경계가 `<=`인가 `<`인가 | **`<=`** (정확히 상한이면 허용) | "4,000자 상한"의 자연어 의미가 "4,000자까지 된다"이다. `<`면 실제 상한이 3,999가 되어 **문서 수치와 동작이 1 어긋난다** |
| A-11 | 이전 크래시가 남긴 임시 파일 정리 | **정리하지 않는다** | 정리하려면 "무엇이 우리 임시 파일인가"를 판정해야 하고 그것이 새 표면이다. 그리고 오판하면 **도구가 사용자 파일을 지운다** — A-13과 같은 원칙 |
| A-12 | 마지막 항목 삭제 후 파일을 지우나 | **파일을 유지한다** | 사용자가 쓴 제목·문단이 남아 있을 수 있고 그것을 지우는 것은 A-13 위반이다. §2.2의 *"빈 파일은 거짓 신호"*는 **우리가 파일을 미리 만드는 것**을 금지한 문장이지, 사용자 편집의 결과로 비게 된 파일을 지우라는 요구가 아니다 |
| A-13 | 항목 삭제 시 딸린 중첩 줄 | **남긴다** | §7.3: *"불릿이 아닌 줄은 그대로 보존된다."* 고아 줄이 생기는 것은 수용한다 — 정리는 사용자다(§6). 지우는 쪽이 친절해 보이지만 실은 **도구가 사용자 파일을 다시 쓰는 경로**를 만드는 것이고 그것이 §7.3이 금지한 방향이다 |
| A-14 | 도구 설명문의 언어 | **영어** | `APPROVAL-GATE.md` §4의 확정 판정 *"텍스트의 수신자가 언어를 정한다"* 그대로 — 설명문을 읽는 것은 모델이다. CLI 표시(`/memory`·시작 표시)는 사용자 언어다 |
| EM-1 | `content`에 **줄바꿈**이 들어왔을 때 | **개행을 공백으로 접어 한 줄로 만들고, 그 사실을 결과에 밝힌다.** 설명문도 항목이 한 줄임을 선제적으로 알린다 | 그대로 쓰면 §7.3의 "항목 = 최상위 불릿 하나"가 깨지고, 둘째 줄부터는 파싱에서 항목으로 안 잡혀 **중복 판정이 영영 성립하지 않는다** — 같은 메모가 호출마다 다시 쌓여 예산을 태운다. 거부하는 안은 형식 기술상의 이유로 성공한 저장을 실패시키는 것이라 §4.2의 방향(모델이 메모리 도구와 싸우게 하지 않는다)과 반대다. **형식의 소유자가 자기 형식으로 정규화하는 것**은 사용자 파일을 다시 쓰는 것(§7.3이 금지한 것)과 **다른 자리**다 — 전자는 쓰기 경계에서 모델 입력을 받는 일이고 후자는 이미 디스크에 있는 사용자 글을 건드리는 일이다. 다만 **조용하면 안 된다**(`ARCHITECTURE.md` §2.6): 변형은 결과에 나타난다 |
| A-15~A-18 | 결과 텍스트의 문구 4건 | **재량** | 이 문서 머리의 조정 가능 범위 그대로. **사실의 존재는 계약이고 문장은 아니다**(§4.2) — 검사도 사실에 걸어야 하며, 문면에 걸면 재량이 재량이 아니게 된다(`APPROVAL-GATE.md` 판정 C-9와 같은 논리) |
